# Решения дефектов изоляции DSL

Дата: 2026-09-05. Основание: [дефекты S03-01–S03-03](RELEASE_REVIEW_STAGE_03.md).

Статус: варианты исследованы, выбран рекомендуемый набор изменений. Это результат отдельного запроса пользователя на анализ и выбор решения. Production-код не изменён, дефекты пока не закрыты, этап 4 не начат.

Проверяемая база: [57c3511](https://github.com/strangeman375/Morphant/commit/57c3511f3b98dd9360ce22bbd21136ffae83c9fa), дерево `1660aec1eec194df0dcb2c19fdf796b826bb103d`. Локальный эквивалент — `fc3c0ab3d467faffebc94f16d7a9982ccb3ac3c9`.

## 1. Выбор

Выбраны три взаимосвязанных изменения:

1. **S03-01:** ограничить общие расширения локальными мапперами через один internal-интерфейс сборки. Обычные независимые мапперы продолжат делить один набор расширений на пару типов.
2. **S03-02:** добавить в namespace construction/member-типов стабильную область текущей сборки. Сохранить человекочитаемые имена `DestinationConstruction`, `DestinationConstructorParameters`, `DestinationMembers` и фиксированные tuple-имена.
3. **S03-03:** поместить тип владельца конфигурации в ковариантный receiver. Дополнить это проверкой принадлежности связанного метода ожидаемой поверхности в генераторе.

Синтаксис `Configure(MapperBuilder builder)`, `builder.Map<S, D>()`, callback-перегрузки, target-typed `new(...)`, явные имена типов и обязательные параметры сохраняются. Дополнительный вызов наподобие `ForMapper(this)` пользователю не нужен. `base.Configure(builder)` по-прежнему означает только подключение конфигурации базы.

## 2. Почему не остальные варианты

| Вариант | Результат | Решение |
|---|---|---|
| Только уникальные имена generated-типов | Убирает `CS0436`; перегрузки, включая `Using`/`Convert`, остаются неоднозначными | Не самостоятельное исправление |
| Только ограничения `where` | Помогают исключить чужую сборку, но не выбрать одно из связанных семейств | Использовать только для assembly-изоляции shared-методов |
| Объединить связанные семейства по CLR-паре | Убирает часть дублей; может подменить tuple names, nullable или `dynamic` одной конфигурации представлением другой | Не использовать как общее исправление |
| Все методы делать отдельными для каждого маппера | Изолирует обычные мапперы, но сам по себе не решает bare-CRTP self; превращает 15 общих перегрузок в `15 × N` | Не выбирать повсеместно |
| Ковариантный receiver с номинальным владельцем | Сохраняет вывод типов и позволяет C# предпочесть производное семейство | Выбран вместе с проверкой binding и локальным маркером для shared |
| Generated builder на каждую конфигурацию либо `ForMapper(this)` | Позволяет передавать точный контекст декларации | Слишком большой redesign DSL для этих дефектов |
| Требовать `base.Configure`, `partial` у всех баз, убрать IVT или подавить `CS0436` | Меняет поддерживаемые сценарии либо скрывает дефект | Отклонён |
| Удаление DSL после компиляции, `EditorBrowsable`, `file` | Не решает исходную конкуренцию при компиляции; `file` также не подходит для C# 9 и межфайловых явных ссылок | Не относится к исправлению |

В compiler-пробе одного namespace было недостаточно: остался `CS0121`. Одного маркера было недостаточно: остался `CS0436`. При объединении tuple-семейств программа компилировалась, но все 15 вызовов производной конфигурации связывались с представлением базы.

## 3. Устройство расширений

### Общая инфраструктура

Добавить один пустой инфраструктурный интерфейс в runtime:

```csharp
public interface IMappingBuilder<out TOwner, TBuilder> { }
```

Существующий `MappingBuilder<TMapper, TSource, TDestination>` реализует:

```csharp
IMappingBuilder<TMapper, MappingBuilder<TMapper, TSource, TDestination>>
```

Ковариантен только владелец. Второй аргумент инвариантен и сохраняет точные self/source/destination для вывода типов и возвращаемого builder. Все расширения продолжают возвращать существующий `MappingBuilder<...>`; новый интерфейс не становится результатом fluent-вызова.

Номинальный владелец находится в типе параметра, поэтому участвует в сравнении перегрузок. Одни `where` этого не обеспечивают. Техническое основание — [variance conversion](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/interfaces#19233-variance-conversion) и [better function member](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#12643-better-function-member); применимость конкретной формы проверена компилятором C# 9 / Roslyn 4.4.0.

### Shared и локальный интерфейс сборки

Обычная закрытая пара независимого маппера получает receiver вида:

```csharp
// S и D здесь обозначают конкретные типы пары.
this IMappingBuilder<object, MappingBuilder<TMapper, S, D>> builder
// Ограничение метода:
where TMapper : TypeMapper<TMapper>, AssemblyScope.LocalMapper
```

`AssemblyScope.LocalMapper` — один пустой internal-интерфейс с уникальным полным именем в текущей сборке. Генератор добавляет его к partial-мапперам, которым нужна shared-поверхность. Если shared-поверхности нет, маркер не нужен. IVT раскрывает чужие методы, но не делает локальный маппер реализацией интерфейса чужой сборки.

Именно `object` служит общим владельцем receiver; маркер остаётся в ограничениях метода. Если использовать маркер как ковариантного владельца, он окажется несравним с допустимой non-partial базой, которой генератор не может добавить интерфейс.

### Семейства и наследующие мапперы

Для семейства receiver содержит объявляющий тип:

```csharp
this IMappingBuilder<
    Root<TMapper, T>,
    MappingBuilder<TMapper, Source<T>, Destination<T>>> builder
```

Производное семейство использует `Derived<TMapper, T>` в первом аргументе. При корректной лямбде C# выбирает более конкретный receiver. База продолжает связывать собственное тело `Configure` со своим receiver. Это не подключает её настройки или правила к производной конфигурации.

Правила выбора поверхности нужно уточнить:

- Любая reusable-база с bare self-параметром использует family-поверхность, даже для закрытой обычной пары. Ей не нужны `partial` и локальный маркер.
- Локальная декларация в маппере, наследующем пользовательскую конфигурационную базу, получает собственный номинальный receiver. Это необходимо и для обычной закрытой пары: у базы может быть другая nullability той же CLR-пары.
- Независимые обычные мапперы сохраняют shared-поверхность. Существующая необходимость отдельной поверхности для nullable, tuple и `dynamic` сохраняется.

Контрольный пример с non-partial nullable-базой, обычным производным маппером и независимым shared-маппером прошёл без предупреждений. Если убрать собственную поверхность производного маппера, 17 его вызовов выбирают базу и появляются `CS8620`.

Receiver теперь различает семейства в самой сигнатуре. Поэтому отдельные hash-контейнеры для одинаковых по сигнатуре, но разных по constraints семейств больше не требуются: проба размещает все номинальные методы в одном partial-контейнере. При внедрении это нужно подтвердить полными production-снимками.

### Проверка binding обязательна

Ковариантность задаёт предпочтение, но не исключает базовую перегрузку. Если лямбда неприменима к производной поверхности, C# может выбрать базовую.

Это воспроизведено: база регистрирует `(int Id, int Other)`, производная — `(int Code, int Other)`, а производная лямбда ошибочно обращается к `s.Id`. 11 вызовов компилируются через базовый метод без предупреждений. Одного отсутствия `CS0121` недостаточно.

Генератор должен проверять связанный метод против **назначенной этому месту конфигурации поверхности**: её owner, пары и полного presentation-контракта. При недопустимом откате к базе нужна диагностированная ошибка конфигурации и обычный typed stub. Уже выбранное корректное переиспользование базовой поверхности остаётся допустимым; равенство только CLR-пары недостаточно.

Дополнительно проверять принадлежность метода текущей compilation. Совпадения reserved-имени, сигнатуры и generated hint недостаточно: source reference чужой сборки тоже содержит syntax references. Не расширять `IsGeneratedMethod` до принятия произвольных metadata-методов. Это устраняет основание различать чужой source-backed метод и тот же метод из DLL при recovery.

## 4. Имена construction/member-типов

Выбран namespace с областью **генерирующей сборки**, а не сборки destination и не каждого маппера. Например:

```csharp
using Morphant.Generated.Types.A_OrdersMapping.N_Shared.Plans;

builder.Map<Source, Destination>()
    .Construct(s => new DestinationConstruction(s.Id));
```

Для tuple-планов аналогичная область находится под `Morphant.Generated.Tuples`, перед существующей идентичностью tuple. Leaf-имена остаются `TupleConstruction`, `TupleConstructorParameters`, `TupleMembers`.

Правила идентичности:

- Основа — простое имя текущей сборки; для подписанной сборки включить стабильный public key token.
- Кодирование assembly-компонента должно быть однозначным: сохранять читаемые буквы/цифры, экранировать разделители и пользовательские escape-последовательности, не заменять разную пунктуацию одним `_`.
- Не использовать version, MVID, TFM, абсолютные пути, состав зависимостей или порядок обнаружения мапперов. Не добавлять область только после обнаружения коллизии.
- Существующее различение namespace/type scopes, generic arity и полного tuple presentation сохраняется внутри этой области. Политика ограничения hint names остаётся отдельной.

Так одна сборка по-прежнему делит destination-типы между своими мапперами. Переименование leaf-типов хешами, копирование типов на каждый маппер и старые алиасы не нужны.

Пользовательский эффект: `new(...)` не меняется; явное `new DestinationConstruction(...)` сохраняется после обновления `using` либо полного имени. Полные имена generated-типов изменятся один раз. При внедрении надо обновить соответствующие правила `AGENTS.md`, literal snapshots и примеры явных ссылок; нынешние правила описывают старую раскладку.

## 5. Доказательства и границы

Воспроизводимый [compiler-прототип](release-review-stage-03/solutions/README.md) использует настоящие delegates и context-типы Morphant, но тестовые builders и минимальные construction/member-типы. Production generator не запускается этим прототипом. Проверяются C# binding, diagnostics, обязательный аргумент конструктора, явные типы и fluent-return; не выполнение маппинга и не полная реализация исправления.

Сохранены [результаты](release-review-stage-03/solutions/results.json): всего 53 сравнительных компиляции. Все 31 положительный сценарий выбранной формы прошли без warnings/errors и без расхождений выбранного владельца; проверен 601 callback-вызов. Входной язык — C# 9, Roslyn — 4.4.0, SDK — 10.0.100, host — net10.0/Linux. Reference shapes: `CSharpCompilationReference`, отдельно emitted DLL и reference assembly, с IVT и без него. Проверяется выбранный символ каждого callback-вызова, а не только успешная компиляция.

В положительную матрицу входят все 15 callback-перегрузок, shared/nullable/tuple/unrelated family между сборками, related generic families с одинаковыми и разными constraints, вложенная generic-подстановка, разные tuple names, `dynamic`/`object`, recursive nullability и non-partial базы. Отрицательные контроли сохраняют причины отклонения упрощённых вариантов.

Старый producer с неограниченными shared-методами и новый consumer всё ещё конфликтуют при IVT; это отдельно проверено во всех трёх reference shapes. Выбранная схема требует пересобрать взаимодействующие friend assemblies новым генератором. Не заявлять, что обновления только consumer достаточно. Отдельную ветку генерации для старой DSL-поверхности не выбираем: проект не поддерживает superseded generated designs как параллельный контракт.

Публичный runtime получает один пустой интерфейс; сборка со shared-поверхностью — не более одного пустого internal-интерфейса. Число shared callback-методов для `N` независимых мапперов одной полной пары остаётся 15. Отдельные методы у конфигурационных владельцев сохраняются там, где нужны корректные constraints/presentation и независимый binding. Фактические размеры binary/generated output после реализации ещё не измерены.

Не выполнены новым прототипом: production end-to-end исправление, runtime mapping, MSBuild consumer-проверка изменённого продукта, Roslyn 4.9.2, SDK 7, IDE и другие ОС. Прежние результаты этапа 3 не являются проверкой будущего исправления.

## 6. Порядок внедрения и критерии закрытия

1. Ввести единую assembly-идентичность generated-области и обновить имена всех трёх категорий обычных и tuple-типов. Проверить source/DLL/ref при IVT, включая bare-регистрацию и разные source с общим destination. Это отдельный checkpoint S03-02.
2. Добавить runtime receiver, локальный маркер, уточнённую scope policy и номинальные family/local receivers. Одни и те же правила, marker declarations и связи partial-мапперов должны применяться в augmented compilation и конечной генерации. Проверка соответствия связанного метода ожидаемой поверхности входит в этот же этап, а не откладывается после него.
3. Обновить строгую аутентификацию generated-методов и recovery; удалить ставшие ненужными family-контейнеры. Не связывать координацию DSL с наследованием настроек.
4. Механически обновить полные generated snapshots. Добавить usage/compiler регрессии по трём дефектам, смешанным shared/family сценариям и ошибочному откату лямбды к базе. Проверить, что required arguments, explicit type names, markers, nullable annotations и context-типы не ослаблены.
5. Выполнить affected categories на минимальном и новейшем валидированном Roslyn. Затем настоящие analyzer-backed MSBuild consumers и runtime-проверки независимых настроек/правил: разные результаты у базы и производного маппера, с `base.Configure` и без него. Перед закрытием общего исправления — Release build и оба test projects.

Дефекты можно закрыть только после production-проверок: исходные валидные воспроизведения должны собираться без предупреждений и Morphant-ошибок, callbacks должны связываться с назначенной поверхностью, неправильные callbacks должны диагностироваться, а настройки и результаты независимых конфигураций — оставаться независимыми. После измерения generated output проверить, что дополнительные типы/методы соответствуют описанным причинам.
