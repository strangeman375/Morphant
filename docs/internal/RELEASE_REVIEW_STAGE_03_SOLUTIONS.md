# Решения дефектов изоляции DSL

Дата: 2026-09-05. Основание: [S03-01–S03-03](RELEASE_REVIEW_STAGE_03.md).

Статус: пользователь утвердил отказ от shared-расширений и остальные решения ниже. Повторение одинаковых пар в независимых мапперах считается редким сценарием; оптимизация этого случая не оправдывает усложнение. Сначала внедряем исправления и повторяем затронутые проверки, затем возвращаемся к аудиту. Production-код пока не изменён, дефекты не закрыты, этап 4 не начат.

База нового эксперимента: [3628c23](https://github.com/strangeman375/Morphant/commit/3628c23bfc1dda5f140eb303c03dc2c93d1543f8), tree `efa929d974e4c5f99828f753a2e0e18a75acec95`. Предыдущий вариант с shared и assembly marker сохранён в истории этого файла; он больше не является рекомендуемой архитектурой.

## 1. Пересмотренный выбор

**Генерировать только специализированные расширения.** Сохранение shared экономит методы, когда несколько независимых мапперов повторяют одну пару, но требует отдельной scope policy, сборочного маркера и правил взаимодействия с family/local receivers. Для Morphant эта сложность не оправдана.

| Дефект | Что даёт отказ от shared | Что ещё нужно |
|---|---|---|
| S03-01: чужие расширения применимы через IVT | Прямой receiver содержит конкретный mapper; чужой метод не подходит | Маркер сборки не нужен |
| S03-02: одинаковые полные имена generated-типов | Сам по себе не устраняет совпадение имён | Стабильная область генерирующей сборки в namespace |
| S03-03: связанные CRTP-семейства | Сам по себе не устраняет конфликт: текущие family-методы уже специализированы | Номинальный family receiver и проверка выбранного binding |

Сохраняются `Configure(MapperBuilder builder)`, `builder.Map<S, D>()`, все применимые callback-перегрузки, обязательность аргументов, `new(...)` и явные generated-имена. Non-partial reusable-базы и отказ от `base.Configure(builder)` остаются поддерживаемыми.

## 2. Receivers без shared

### Обычные мапперы

Использовать существующий builder непосредственно:

```csharp
this MappingBuilder<OrderMapper, Source, Destination> builder
```

Для concrete generic mapper аналогично использовать `MappingBuilder<OrderMapper<T>, ...>`. Свободного общего `TMapper`, сборочного marker-интерфейса и новых интерфейсов на partial-мапперах здесь нет. Выбор receiver больше не зависит от наличия tuple, nullable или `dynamic` в паре.

### Reusable CRTP-семейства

У `Root<TMapper, T>` и `Derived<TMapper, T>` текущий receiver одинаков:

```csharp
this MappingBuilder<TMapper, Source<T>, Destination<T>> builder
```

Разница находится только в `where TMapper : Root<...>` / `Derived<...>`. В производной конфигурации оба ограничения выполняются. Отказ от shared это не меняет: два направленных контроля сохранили `CS0121` на всех 15 перегрузках производного семейства.

Для этих receivers остаётся один пустой runtime-интерфейс, но его можно упростить:

```csharp
public interface IMappingBuilder<out TMapper, TSource, TDestination> { }
```

`MappingBuilder<TMapper, TSource, TDestination>` реализует этот интерфейс со своими аргументами. Только mapper-параметр ковариантен. Family-расширение принимает:

```csharp
this IMappingBuilder<Root<TMapper, T>, Source<T>, Destination<T>> builder
```

Расширение производного семейства принимает `Derived<TMapper, T>` в первом аргументе. Return type остаётся `MappingBuilder<TMapper, Source<T>, Destination<T>>`; вывод self и остальных generic-параметров проверен C# 9, включая вложенную подстановку. Предыдущий двухпараметрический интерфейс с целым builder во втором аргументе больше не нужен: он обслуживал вывод свободного `TMapper` shared-методов.

Номинальный тип в receiver участвует в [сравнении перегрузок C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/expressions#12643-better-function-member). Смысл `base.Configure` остаётся конфигурационным: отсутствие вызова не мешает выбору расширения производного семейства.

Полностью убрать этот интерфейс одним отказом от shared нельзя. Для этого нужно отдельно менять способ передачи владельца конфигурации либо дизайн reusable-баз. Дополнительный `ForMapper(this)`, новые ограничения на generic-наследование и отдельные generated builders сейчас не рекомендуются.

### Проверка binding

Ковариантность определяет предпочтение, но оставляет базовую перегрузку применимой. Если производная лямбда ошибочна, C# может подобрать базовую: в пробе `(int Id, int Other)` / `(int Code, int Other)` ошибочное обращение к `s.Id` связывает 11 вызовов производного тела с базой без warnings/errors.

Генератор должен сопоставлять связанный метод с назначенной месту декларации поверхностью, включая owner и полное представление пары. Недопустимый откат должен давать ошибку конфигурации и typed stub. Уже назначенное корректное переиспользование базовой поверхности разрешено. Равенства CLR-пары недостаточно: объединение по нему может терять tuple names, nullable и `dynamic`.

Также проверять принадлежность метода текущей compilation; совпадения reserved-имени, сигнатуры и generated hint недостаточно для чужих source references. Эти проверки нужны и в более простой схеме.

## 3. Имена и объём генерации

Construction/member-типы остаются общими внутри генерирующей сборки, когда destination-контракт совпадает. Отказ от shared-расширений не требует копировать эти типы на каждый маппер.

Для S03-02 добавить стабильную assembly-область в namespace, например:

```csharp
using Morphant.Generated.Types.A_OrdersMapping.N_Shared.Plans;

builder.Map<Source, Destination>()
    .Construct(s => new DestinationConstruction(s.Id));
```

Для tuples область находится под `Morphant.Generated.Tuples`, перед идентичностью tuple; имена `TupleConstruction`, `TupleConstructorParameters`, `TupleMembers` сохраняются. Основа области — простое имя генерирующей сборки и стабильный public key token для подписанной сборки. Кодирование должно различать пунктуацию и пользовательские escape-последовательности. Не включать version, MVID, TFM, пути и порядок обнаружения коллизий. Существующие namespace/type scopes, generic arity, tuple presentation и политика hint names сохраняются.

Явные `using`/полные имена потребуют обновления после внедрения. Короткие leaf-имена и поддержка явного `new DestinationConstruction(...)` остаются.

Цена специализации для полной пары с 15 перегрузками:

| Регистрации обычной пары | Сейчас shared | Только specialized |
|---|---:|---:|
| Один маппер | 15 | 15 |
| Два независимых маппера одной пары | 15 | 30 |
| Десять независимых мапперов одной пары | 15 | 150 |
| Разные пары, каждая объявлена одним маппером | Без изменения | Без изменения |

Это рост числа callback-методов на повторяющихся shared-парах, не оценка всего binary. Уже специализированные nullable/tuple/generic случаи не становятся дороже просто от удаления shared. Правила переиспользования поверхностей в конфигурационной иерархии могут отдельно менять их число; фактический output нужно измерить после внедрения. Hash-контейнеры семейств, которые различались только constraints, можно убрать после подтверждения уникальности номинальных signatures.

## 4. Проверка варианта

[Прототип и команды](release-review-stage-03/solutions/README.md), [результаты](release-review-stage-03/solutions/results.json). SDK 10.0.100, Roslyn 4.4.0, C# 9, net10.0/Linux.

Выполнены **39 сравнительных компиляций**. Все **34 положительных сценария** прошли без предупреждений и ошибок; у **652 callback-вызовов** проверен выбранный владелец. Матрица охватывает все 15 перегрузок, явные construction/member-имена, IVT on/off, source/DLL/ref, обычные/nullable/tuple пары, unrelated/related families, одинаковые/разные constraints, generic-подстановку, tuple names, `dynamic`/`object`, recursive nullability и non-partial базы.

Прямой receiver также прошёл три контроля нового consumer со старой неограниченной shared-поверхностью producer: identity conversion предпочла локальный метод. Прежнее требование обязательно пересобирать producer для устранения этой неоднозначности больше не следует из эксперимента. Это не полная проверка совместимости версий runtime/generator или NuGet-пакетов.

Прототип использует настоящие delegates/context-типы Morphant и тестовые builders/минимальные construction/member-классы. Он проверяет C# binding, а не production generation, runtime mapping или IDE. Семантическая защита от ошибочного отката в генераторе ещё не реализована. Старые результаты полного suite не являются проверкой будущего исправления.

## 5. Порядок внедрения

Каждую существенную контрольную точку публикуем в `main`. Вопросы, существенно меняющие публичный контракт или поведение относительно этого решения, согласуем с пользователем до реализации.

1. Ввести assembly-область имён для S03-02; сохранить destination-контракты и читаемые leaf-имена. Обновить соответствующие naming-правила `AGENTS.md`, explicit-name примеры и полные snapshots.
2. Удалить shared-ветку и связанные правила координации. Конкретным self-типам дать прямой receiver, bare CRTP self — простой ковариантный family receiver. Не добавлять сборочный маркер. Применять одинаковые правила в augmented compilation и конечной генерации.
3. В том же этапе внедрить проверку binding и принадлежности compilation, подтвердить recovery и независимость настроек. Удалить ненужные family-контейнеры после проверки signatures.
4. Проверить полные production snapshots и usage-regressions для трёх дефектов, обеих форм `new`, required arguments, markers, nullable/context-контрактов и ошибочного отката к базе. Запустить affected categories на минимальном и новейшем валидированном Roslyn.
5. Проверить реальные analyzer-backed MSBuild consumers и runtime-результаты независимых конфигураций с `base.Configure` и без него, измерить generated output. Перед закрытием исправления — Release build и оба test projects; совместимость пакетов проверить отдельно.

Это утверждённое решение заменяет предыдущую рекомендацию сохранять shared. Его внедрение не означает переход к этапу 4 аудита.
