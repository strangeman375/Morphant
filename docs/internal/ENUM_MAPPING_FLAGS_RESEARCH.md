# Flags enum: исследование и вопросы дизайна

Дата: 2026-09-23. Статус: исследование и предложения для обсуждения.
Пользователь вернулся к flags после согласования обычных enum.
Новые решения из этого документа ещё не утверждены; реализация не начата.

Основной контракт: [enum design](ENUM_MAPPING_DESIGN.md). Уже выбрано
автоматическое распознавание `[Flags]`, применение существующего `Members`
к отдельным битам и объединение результатов. Отдельные `Flags`, `Values`,
`MapValue` и новые настройки поведения без самостоятельной потребности
не предлагаются. Детали прежнего наброска в разделе 7 основного документа
остаются предложениями; здесь проверены их основания и выявлены конфликты.

### Mapperly: проверка маски отличается от проверки объявленности

При flags destination проверка имеет смысл `value == (value & allowedMask)`,
где allowedMask — OR всех объявленных destination-констант, включая составные.
Проверяется уже приведённое значение. Атрибут на source для этого не нужен.
В [тесте FlagsEnumToOtherEnumByValueCheckDefinedShouldCast](https://github.com/riok/mapperly/blob/f87d48b12a6010a224ca26ad112fb48c07cd6d5d/test/Riok.Mapperly.Tests/Mapping/EnumTest.cs)
ожидается именно такая генерация.

Следствия из [реализации EnumCastMapping](https://github.com/riok/mapperly/blob/f87d48b12a6010a224ca26ad112fb48c07cd6d5d/src/Riok.Mapperly/Descriptors/Mappings/Enums/EnumCastMapping.cs):
destination с единственным Pair = 3 принимает 0, 1, 2 и 3. All = -1 заполняет
всю маску, поэтому такая проверка больше не отсекает никакие биты соответствующей
ширины. Это осмысленный контракт «нет неизвестных битов», но он шире проверки
«число образовано объявленными значениями». Проверка после cast также не
заменяет выбранную в Morphant проверку математического диапазона до сужения.

[PR #510](https://github.com/riok/mapperly/pull/510) добавил оптимизацию
ByValueCheckDefined и поддержку flags. В просмотренном обсуждении нет
пользовательского обоснования, что именно такая строгость предпочтительна;
наличие реализации нельзя считать консенсусом пользователей.

### Строковый путь: полезная совместимость, нежелательные зависимости

Mapster выбирает подходящие объявленные значения от больших к меньшим,
включая составные, и собирает список имён. При остатке неизвестных битов
возвращает числовую строку всей исходной маски. Parser допускает числа.
В [тесте Flag_Enum_Is_Supported](https://github.com/MapsterMapper/Mapster/blob/cbc1e5f04e6e003744b04f83d4705670a85e459b/src/Mapster.Tests/WhenMappingEnums.cs)
6 форматируется как Six, 10 — как Two, Eight, а 7 — как число.
[Enum helper](https://github.com/MapsterMapper/Mapster/blob/cbc1e5f04e6e003744b04f83d4705670a85e459b/src/Mapster.Core/Utils/Enum.cs).

У встроенного AutoMapper аналогичную роль играют стандартные
[Enum.ToString](https://learn.microsoft.com/en-us/dotnet/api/system.enum.tostring?view=net-10.0)
и [Enum.TryParse](https://learn.microsoft.com/en-us/dotnet/api/system.enum.tryparse?view=net-10.0).
Flags-тест переводит One|Four|Eight между enum с одинаковыми именами и
позициями битов; это не проверка пользовательского переименования каждого бита.
[Тесты AutoMapper](https://github.com/LuckyPennySoftware/AutoMapper/blob/6e8697bc44f02fb54ef6a556a7d134e63485299e/src/UnitTests/Enumerations.cs).

Практическое следствие для дизайна: добавление имени ReadWrite к прежней
комбинации может заменить строку Read, Write на ReadWrite. Если у destination
такого имени нет, поведение меняется, хотя отдельные флаги не изменились.
Для Morphant предпочтительна независимость ByName от наличия имени у комбинации
и отсутствие скрытого перехода к числам. Строковый промежуточный слой не нужен.

## Взгляд за пределы мапперов

Enums.NET различает объявленное значение и комбинацию самостоятельных флагов.
Внутренняя маска allFlags собирается только из констант с одним установленным
битом. Без custom validator режим Default принимает либо комбинацию таких
битов, либо точно объявленное значение. Поэтому один Pair = 3 разрешает 3,
но не 1 или 2. Однако Pair = 3 вместе с Audit = 4 не разрешает 7 в этом режиме,
если 7 отдельно не объявлено: у Pair нет самостоятельных атомарных составляющих.
[Построение маски](https://github.com/TylerBrinkley/Enums.NET/blob/bdf10cebfa44727abe3dda63218e5410d8034263/Src/Enums.NET/Enums.cs),
[проверка Default и IsValidFlagCombination](https://github.com/TylerBrinkley/Enums.NET/blob/bdf10cebfa44727abe3dda63218e5410d8034263/Src/Enums.NET/EnumCache.cs).

Rust bitflags отдельно описывает известные и неизвестные биты. Известными
считаются биты, встречающиеся в объявленных флагах; составные флаги допустимы,
но документация предупреждает о неожиданностях, если их биты не объявлены
самостоятельно. Для внешнего протокола можно явно считать известными все биты
через безымянный флаг `_ = !0`.
[Документация bitflags](https://docs.rs/bitflags/latest/bitflags/index.html).

Полезный вывод: составное значение, набор известных битов и допустимое
значение — разные понятия. Их нужно определить в контракте, а не смешивать
в одном вызове Enum.IsDefined. Перенос неизвестных чисел уже выражается
через ByValueAllowUndefined; дополнительная настройка для этой цели не нужна.

## Набросок основного сценария Morphant

Ниже предлагаемый DSL, ещё не реализованный API enum mapping:

```csharp
[Flags]
enum DomainAccess
{
    None = 0, Read = 1, Write = 2, Execute = 4,
    ReadWrite = Read | Write
}

[Flags]
enum ApiAccess
{
    None = 0, Read = 8, Modify = 16, Execute = 32, Unknown = 64
}

// В Configure:
builder.Map<DomainAccess, ApiAccess>()
    .Members(flag => flag switch
    {
        DomainAccess.Write => ApiAccess.Modify,
        _ => ApiAccess.Unknown
    });
```

При ByName по умолчанию и предлагаемом fallback для отдельного бита:

| Вход | Результат | Причина |
|---|---|---|
| Read | Read = 8 | Совпадение имени; позиции битов могут различаться |
| Read\|Write | Read\|Modify = 24 | Конвенция для Read, явное правило для Write |
| ReadWrite | Read\|Modify = 24 | Это та же маска, имя комбинации не меняет её разбиение |
| Read\|(DomainAccess)8 | Read\|Unknown = 72 | Неизвестный source-бит дошёл до fallback |
| (DomainAccess)8 | Unknown = 64 | Неизвестный source-бит 8 не становится ApiAccess.Read только из-за совпадения чисел |

Один source-бит может дать ноль, один или несколько destination-битов.
Совпадение вкладов нескольких source-битов допустимо: OR объединяет их один раз.
Явное `Write => ApiAccess.None` удаляет Write. `throw` запрещает выбранный бит.
Никакого автоматического обратного преобразования из этого не следует.
Если source объявляет только Pair = 3 без имён для отдельных битов,
побитовая ByName-конвенция не может использовать имя Pair для чисел 1 и 2.
Для них понадобятся явные правила, fallback или иной способ преобразования.

Применение существующих контрактов, предлагаемое для этого побитового пути:

- Для каждого бита: локальные специальные правила → базовые правила → одна
  effective конвенция → ближайший fallback. Ранее принятый IncludeBase не
  становится цепочкой повторных преобразований результата.
- MemberSelection.Explicit отключает только неявную конвенцию. Auto()
  запрашивает конвенцию для текущего бита; неудача бросает исключение.
- ByName использует Ordinal, затем OrdinalIgnoreCase. Aliases одного
  физического бита не означают два вызова; неоднозначность имён решается
  по общим правилам aliases, не порядком объявления.
- Биты обрабатываются от младшего к старшему в точной ширине source type.
  Guards и locals выполняются для достигнутого уровня каждого бита.
  Нельзя предварительно запускать тот же Members на всей маске «для проверки».
- Using получает целый source один раз. Все побитовые правила видят один
  начальный result и прежний previous. Result не становится OR-накопителем
  и не добавляется к нему автоматически. Null фабрики завершает операцию.
- Явные результаты не получают скрытой проверки объявленности. Неизвестный
  бит не удаляется до выполнения правил. Пользовательские исключения не
  превращаются в отсутствие соответствия.

Эти пункты ещё не решают composite overrides и числовую композицию ниже.

## Что нужно согласовать

### 1. Members всегда обрабатывает бит или ещё и точную целую маску?

Случай: уже есть Read → View и Write → Edit, а пользователь добавляет
ReadWrite → Special. Должно ли это правило заменить результат View|Edit?

**Вариант A — единая побитовая семантика.** ReadWrite просто разбирается на
два бита; whole-mask алгоритм пишется в ConstructUsing/ResolveUsing с общим
null handling. Явно написанный недостижимый composite case в декларативном
побитовом switch должен диагностироваться, а не молча игнорироваться.
Это относится, например, к ReadWrite в switch непосредственно над текущим
битом; composite pattern над полным result или вычисленным выражением
сам по себе не является недостижимым.
Недостаток: исключение для всей комбинации нельзя выразить таким case.

**Вариант B — exact whole-mask overrides перед разбиением.** ReadWrite →
Special работает только для точной маски; ReadWrite|Audit его не использует.
Жадного поиска подходящих подмасок нет. Этот вариант был предварительным
предложением в основном дизайне, но не утверждённым решением.

У B есть две сложности. Во-первых, `or`, `when`, locals, switch над result
или tuple нельзя произвольно разделять на два прохода: изменятся порядок и
число пользовательских вычислений. Во-вторых, базовый whole-mask case не
должен незаметно обойти более приоритетное локальное правило для одного бита.
Простое «сначала все composite, потом все atomic» нарушает этот порядок.

Предварительно предпочитаю A: он сохраняет один смысл Members и уже выбранное
направление пользователя. Это предложение о границе DSL, не принятое
ограничение. Если whole-mask overrides нужны в том же switch, сначала следует
выбрать их точный приоритет и допустимые формы C#, затем проектировать генерацию.

### 2. Что означает строгий ByValue для flags destination?

Проверять только точное объявление слишком узко для обычного flags-сценария:
Read = 1 и Write = 2 обычно подразумевают допустимость Read|Write = 3.
При этом составные объявления делают критерий неоднозначным.

| Объявления destination и проверяемое число | Все биты встречаются в объявлениях: Mapperly | Комбинация объявленных одиночных битов или точное объявление: Enums.NET Default | OR целых объявленных значений: кандидат для Morphant |
|---|---|---|---|
| Read = 1, Write = 2; число 3 | Да | Да | Да |
| Только Pair = 3; число 1 | Да | Нет | Нет |
| Только Pair = 3; число 3 | Да | Да | Да |
| Pair = 3, Audit = 4; число 7 | Да | Нет | Да |
| Только All = -1; число 1 | Да | Нет | Нет |
| Только All = -1; число -1 | Да | Да | Да |

Здесь сравниваются проверки принадлежности уже представимого значения,
без effects пользовательских правил и без ошибок диапазона. Zero во всех
трёх моделях допустим как пустая комбинация; включать его в Morphant нужно
согласовать отдельно ниже.

Рекомендация для обсуждения — третий критерий: допустимы OR-комбинации целых
объявленных значений, включая пустую. Pair можно включить целиком, но нельзя
выдернуть из него не объявленный самостоятельно бит. All = -1 не делает
каждое число допустимым. Это собственное предложение, не контракт Mapperly
или Enums.NET. Более узкий прежний кандидат Morphant соответствует второму
столбцу; расширение пока не утверждено.

Этот критерий не требует перебирать все подмножества: для проверяемой маски x
можно объединить все объявленные c, целиком содержащиеся в x, и сравнить
результат с x. Все операции выполняются в фиксированной ширине destination.
Но выбор критерия сам по себе не решает, на каком этапе проверять число.

### 3. Как совместить числовой контракт с побитовыми Members?

Два примера, на которых нельзя подменить решение удобной реализацией:

1. Destination содержит только Pair = 3. Целое число 3 допустимо даже по
   наиболее строгому варианту с признанием объявленных значений, но проверка
   отдельных чисел 1 и 2 этого соответствия не находит.
2. Source основан на int, destination — на sbyte. Число -1 помещается в оба
   типа. Однако среди отдельных битов 32-битной source-маски есть, например,
   положительное число 256, которое в sbyte не помещается. Побитовый checked
   cast не эквивалентен сохранению математического числа всей маски.

**Проверять независимо каждый бит** просто и согласуется с source/Auto()
внутри Members. Но тогда ByValue может отвергать допустимую целую маску,
включая Pair = 3. Даже AllowUndefined не устраняет пример с диапазоном.
Такое ограничение требует отдельного согласия, его нельзя объявлять уже
выбранным следствием строгого режима.

**Проверять целую числовую маску или совокупность её конвенционных вкладов**
сохраняет эти числовые сценарии. Но надо определить, как при этом учитываются
явные overrides, когда запускается fallback и что возвращает Auto() в одном
битовом правиле. Проверка итогового OR вслепую непригодна: она стала бы
скрытой проверкой явно написанных результатов. Переставлять или повторять
пользовательские вычисления ради накопления тоже нельзя.

Предпочтение — сохранить возможность числового переноса допустимой целой
маски и ранее принятые гарантии диапазона. Полный алгоритм сочетания с
побитовыми overrides пока не выбран. Временный ручной путь — Using над
полной маской; он не доказывает полноту автоматического дизайна.
Этот вопрос следует решать вместе с единицей обработки Members, до реализации.
Отдельный EnumFlagsStrategy или EnumOverflowHandling его не решает.

### 4. Fallback одного бита или всей операции?

При входе Read|unknown и `_ => ApiAccess.Unknown` возможны разные ответы:

| Единица fallback | Результат |
|---|---|
| Отдельный бит | Read\|Unknown; перевод известной части сохранён |
| Вся маска | Только Unknown; один непереведённый бит заменил весь результат |

Для единого побитового Members рекомендую первый вариант: `_ => None`
тогда намеренно удаляет только неподдерживаемые биты. Без fallback сбой
одного бита бросает исключение всей операции; частичный результат не
возвращается, уже произошедшие effects не откатываются.
Для второго намерения можно написать whole-mask Using. Если в вопросе 3
будет выбрана агрегированная числовая конвенция, реакцию на её неуспех надо
описать отдельно; нельзя незаметно сменить смысл `_` при другой стратегии.

### 5. Zero и nullable результат

**Zero.** Предлагаю один отдельный проход правил с source = 0 только при
нулевом входе. Явное None → Unknown может изменить результат; иначе неявная
конвенция возвращает 0 даже без объявления None. Это отсутствие выбранных
флагов, а не требование совпадения нулевых имён. В Explicit автоматический
шаг пропускается: нужны правило, Auto() или fallback; иначе исключение.
Нулевое правило не применяется к каждому ненулевому входу.

**Nullable.** Null не следует превращать в нулевую маску. Предлагаю, чтобы
возврат null из битового правила завершал всю nullable mapping операцию с
null, без выполнения следующих битов. Альтернатива — lifted OR с вычислением
оставшихся правил; она отличается наблюдаемыми effects. Это самостоятельный
выбор, общего nullable контракта обычных enum для него недостаточно.

### 6. Где автоматическое разбиение применимо?

Предлагаемая граница — flags enum → flags enum. При атрибуте только с одной
стороны сохранять whole-value семантику пары; не предполагать, что обычный
enum допускает OR. Integer → flags enum использует целое число и выбранную
в вопросе 2 проверку destination; это не обход побитового Members по integer.
Flags → integer также переносит число всей маски.

Числовые flags → string стратегии форматируют всю маску. Список имён flags
и обратный parsing пока вне согласованного объёма. Если захотим их добавить,
нужно отдельно определить canonical composite names, aliases, порядок,
разделитель и неизвестные биты; переносить ToString/Parse молча нельзя.

## Проверки перед реализацией

Новые настройки в этом наброске не требуются. UnmappedMemberValidation
остаётся compile-time проверкой покрытия; он не выбирает runtime fallback
или допустимость неизвестных чисел. Для flags предстоит определить покрытие
atomic/composite declarations без перебора всех возможных масок.

Проверки выбранного контракта должны включать различные позиции битов,
aliases, неизвестные биты, ноль, composite-only enums, All = -1, signed high
bit и разные ширины; отдельно — сочетание explicit и automatic contributions,
Auto/Explicit, nullable, Using, ленивые уровни IncludeBase и число вычислений
locals/guards. Identity E → E не должно обходить выбранную стратегию.

Предлагаемый порядок обсуждения: сначала единица обработки Members и место
числовой конвенции (вопросы 1–3), затем fallback и zero/null. Границы направлений
преобразования можно согласовать независимо. До этого нельзя считать прежний
эскиз «разбить и сделать OR» полным контрактом flags.
