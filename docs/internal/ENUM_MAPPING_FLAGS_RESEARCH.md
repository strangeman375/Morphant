# Flags enum: исследование и решения дизайна

Дата: 2026-09-23. Статус: исследование и согласованные решения.
Пользователь утвердил FlagsMappingMode с ByBit по умолчанию и явным ByMask,
ByName целой маски, строгую числовую допустимость, zero/null, применимость,
порядок битов и границу диагностики. Реализация не начата.

Канонический контракт режимов находится в [enum design](ENUM_MAPPING_DESIGN.md).
Flags распознаются по атрибуту, оба режима используют существующий Members.
Отдельные callbacks Flags/Values и цепочки MapValue не вводятся.
Прежний вывод, что отдельная настройка не нужна, снят: FlagsMappingMode
выбирает единицу обработки, а EnumMappingStrategy — критерий соответствия.

### Mapperly: проверка маски отличается от проверки объявленности

При flags destination проверка имеет смысл `value == (value & allowedMask)`,
где allowedMask — OR всех объявленных destination-констант, включая составные.
Проверяется уже приведённое значение. Атрибут на source для этого не нужен.
В [тесте FlagsEnumToOtherEnumByValueCheckDefinedShouldCast](https://github.com/riok/mapperly/blob/f87d48b12a6010a224ca26ad112fb48c07cd6d5d/test/Riok.Mapperly.Tests/Mapping/EnumTest.cs)
ожидается именно такая генерация.

Следствия из [реализации EnumCastMapping](https://github.com/riok/mapperly/blob/f87d48b12a6010a224ca26ad112fb48c07cd6d5d/src/Riok.Mapperly/Descriptors/Mappings/Enums/EnumCastMapping.cs):
destination с единственным Pair = 3 принимает 0, 1, 2 и 3. All = -1 заполняет
всю маску, поэтому такая проверка больше не отсекает никакие биты соответствующей
ширины. Это осмысленный контракт «нет неизвестных битов», но он шире проверки
«число образовано объявленными значениями». Проверка после cast также не
заменяет выбранную в Morphant проверку математического диапазона до сужения.

[PR #510](https://github.com/riok/mapperly/pull/510) добавил оптимизацию
ByValueCheckDefined и поддержку flags. В просмотренном обсуждении нет
пользовательского обоснования, что именно такая строгость предпочтительна;
наличие реализации нельзя считать консенсусом пользователей.

### Строковый путь: полезная совместимость, нежелательные зависимости

Mapster выбирает подходящие объявленные значения от больших к меньшим,
включая составные, и собирает список имён. При остатке неизвестных битов
возвращает числовую строку всей исходной маски. Parser допускает числа.
В [тесте Flag_Enum_Is_Supported](https://github.com/MapsterMapper/Mapster/blob/cbc1e5f04e6e003744b04f83d4705670a85e459b/src/Mapster.Tests/WhenMappingEnums.cs)
6 форматируется как Six, 10 — как Two, Eight, а 7 — как число.
[Enum helper](https://github.com/MapsterMapper/Mapster/blob/cbc1e5f04e6e003744b04f83d4705670a85e459b/src/Mapster.Core/Utils/Enum.cs).

У встроенного AutoMapper аналогичную роль играют стандартные
[Enum.ToString](https://learn.microsoft.com/en-us/dotnet/api/system.enum.tostring?view=net-10.0)
и [Enum.TryParse](https://learn.microsoft.com/en-us/dotnet/api/system.enum.tryparse?view=net-10.0).
Flags-тест переводит One|Four|Eight между enum с одинаковыми именами и
позициями битов; это не проверка пользовательского переименования каждого бита.
[Тесты AutoMapper](https://github.com/LuckyPennySoftware/AutoMapper/blob/6e8697bc44f02fb54ef6a556a7d134e63485299e/src/UnitTests/Enumerations.cs).

Практическое следствие для дизайна: добавление имени ReadWrite к прежней
комбинации может заменить строку Read, Write на ReadWrite. Если у destination
такого имени нет, поведение меняется, хотя отдельные флаги не изменились.
Для Morphant в ByBit наличие имени у комбинации не меняет разбиение.
Для ByMask выбран поиск по имени целого значения, без сборки по именам
битов. Скрытого перехода от отсутствующего имени к числу нет; строковый
промежуточный слой не нужен.

## Взгляд за пределы мапперов

Enums.NET различает объявленное значение и комбинацию самостоятельных флагов.
Внутренняя маска allFlags собирается только из констант с одним установленным
битом. Без custom validator режим Default принимает либо комбинацию таких
битов, либо точно объявленное значение. Поэтому один Pair = 3 разрешает 3,
но не 1 или 2. Однако Pair = 3 вместе с Audit = 4 не разрешает 7 в этом режиме,
если 7 отдельно не объявлено: у Pair нет самостоятельных атомарных составляющих.
[Построение маски](https://github.com/TylerBrinkley/Enums.NET/blob/bdf10cebfa44727abe3dda63218e5410d8034263/Src/Enums.NET/Enums.cs),
[проверка Default и IsValidFlagCombination](https://github.com/TylerBrinkley/Enums.NET/blob/bdf10cebfa44727abe3dda63218e5410d8034263/Src/Enums.NET/EnumCache.cs).

Rust bitflags отдельно описывает известные и неизвестные биты. Известными
считаются биты, встречающиеся в объявленных флагах; составные флаги допустимы,
но документация предупреждает о неожиданностях, если их биты не объявлены
самостоятельно. Для внешнего протокола можно явно считать известными все биты
через безымянный флаг `_ = !0`.
[Документация bitflags](https://docs.rs/bitflags/latest/bitflags/index.html).

Полезный вывод: составное значение, набор известных битов и допустимое
значение — разные понятия. Их нужно определить в контракте, а не смешивать
в одном вызове Enum.IsDefined. Перенос неизвестных чисел уже выражается
через ByValueAllowUndefined; дополнительная настройка для этой цели не нужна.

## Набросок основного сценария Morphant

Ниже предлагаемый DSL, ещё не реализованный API enum mapping:

```csharp
[Flags]
enum DomainAccess
{
    None = 0, Read = 1, Write = 2, Execute = 4,
    ReadWrite = Read | Write
}

[Flags]
enum ApiAccess
{
    None = 0, Read = 8, Modify = 16, Execute = 32, Unknown = 64
}

// В Configure:
builder.Map<DomainAccess, ApiAccess>()
    .Members(flag => flag switch
    {
        DomainAccess.Write => ApiAccess.Modify,
        _ => ApiAccess.Unknown
    });
```

При согласованном ByBit по умолчанию, стратегии ByName и fallback для бита:

| Вход | Результат | Причина |
|---|---|---|
| Read | Read = 8 | Совпадение имени; позиции битов могут различаться |
| Read\|Write | Read\|Modify = 24 | Конвенция для Read, явное правило для Write |
| ReadWrite | Read\|Modify = 24 | Это та же маска, имя комбинации не меняет её разбиение |
| Read\|(DomainAccess)8 | Read\|Unknown = 72 | Неизвестный source-бит дошёл до fallback |
| (DomainAccess)8 | Unknown = 64 | Неизвестный source-бит 8 не становится ApiAccess.Read только из-за совпадения чисел |

Один source-бит может дать ноль, один или несколько destination-битов.
Совпадение вкладов нескольких source-битов допустимо: OR объединяет их один раз.
Явное `Write => ApiAccess.None` удаляет Write. `throw` запрещает выбранный бит.
Никакого автоматического обратного преобразования из этого не следует.
Если source объявляет только Pair = 3 без имён для отдельных битов,
побитовая ByName-конвенция не может использовать имя Pair для чисел 1 и 2.
Для них понадобятся явные правила, fallback или иной способ преобразования.

Применение существующих контрактов к выбранному ByBit:

- Для каждого бита: локальные специальные правила → базовые правила → одна
  effective конвенция → ближайший fallback. Ранее принятый IncludeBase не
  становится цепочкой повторных преобразований результата.
- MemberSelection.Explicit отключает только неявную конвенцию. Auto()
  запрашивает конвенцию для текущего бита; неудача бросает исключение.
- ByName использует Ordinal, затем OrdinalIgnoreCase. Aliases одного
  физического бита не означают два вызова; неоднозначность имён решается
  по общим правилам aliases, не порядком объявления.
- Guards и locals выполняются для достигнутого уровня каждого бита.
  Нельзя предварительно запускать тот же Members на всей маске «для проверки».
  Утверждён порядок битов от младшего к старшему в точной ширине source.
- Using получает целый source один раз. Все побитовые правила видят один
  начальный result и прежний previous. Result не становится OR-накопителем
  и не добавляется к нему автоматически. Null фабрики завершает операцию.
- Явные результаты не получают скрытой проверки объявленности. Неизвестный
  бит не удаляется до выполнения правил. Пользовательские исключения не
  превращаются в отсутствие соответствия.

## Что закрыто выбором режимов

Пользователь утвердил независимый выбор ByBit/ByMask, побитовый library
default и обычное наследование с продолжающим поиск Default. Единый
эффективный режим применяется ко всем Members итоговой пары после IncludeBase.
Using работает с полной маской по прежнему lifecycle в обоих режимах.

Режим снимает прежние конфликты единиц обработки:

- Точные composite cases работают над source в ByMask. Предложение проверять
  целую маску, затем запускать те же Members на битах снято. Guards, locals
  и правила IncludeBase не делятся между двумя проходами.
- Fallback относится к биту в ByBit и к операции целиком в ByMask. Смена
  EnumMappingStrategy не меняет единицу fallback или вход Members.
- Числовая проверка относится к выбранной единице. При единственном
  destination Pair = 3 целое 3 имеет соответствие в ByMask; отдельные 1 и 2
  в строгом ByBit его не имеют. Перенос целого -1 между int и sbyte относится
  к ByMask; per-bit проверка диапазона не обещает того же результата.

Такой default продолжает основной сценарий: одно переименование бита
автоматически действует во всех комбинациях. ByMask позволяет явно выбрать
алгоритм над целой маской, сохранив DSL-конвенцию и общее null handling.
Критерий строгой допустимости неназванной целой комбинации выбран отдельно ниже.

## Остальные согласованные решения

### ByName для полной маски

Для ByMask пользователь выбрал сопоставление имён целых объявленных
значений. Рассмотренные варианты:

| Вариант | Следствие |
|---|---|
| **Выбрано:** сопоставлять целые именованные значения | Именованный ReadWrite может найти одноимённое значение; неназванная ненулевая комбинация остаётся без соответствия |
| Не выбрано: также собирать результат по именам составляющих битов | Неназванный Read\|Write мог бы получить маску из одноимённых destination-битов; потребовался бы дополнительный приоритет относительно целых имён и aliases |

Выбранный вариант сохраняет одну единицу сопоставления: целое значение.
Он намеренно не сочетает whole-mask overrides с автоматическим переводом
остальных неназванных комбинаций по именам битов. Общие aliases и exact-first
правила остаются применимы. Исключение для пустой маски описано в
[каноническом контракте](ENUM_MAPPING_DESIGN.md#нулевая-маска-и-nullable-результат).

### Строгий ByValue для целой flags-маски

Проверять только точное объявление слишком узко для обычного flags-сценария:
Read = 1 и Write = 2 обычно подразумевают допустимость Read|Write = 3.
При этом составные объявления делают критерий неоднозначным.

| Объявления destination и проверяемое число | Все биты встречаются в объявлениях: Mapperly | Комбинация объявленных одиночных битов или точное объявление: Enums.NET Default | OR целых объявленных значений: выбранный контракт Morphant |
|---|---|---|---|
| Read = 1, Write = 2; число 3 | Да | Да | Да |
| Только Pair = 3; число 1 | Да | Нет | Нет |
| Только Pair = 3; число 3 | Да | Да | Да |
| Pair = 3, Audit = 4; число 7 | Да | Нет | Да |
| Только All = -1; число 1 | Да | Нет | Нет |
| Только All = -1; число -1 | Да | Да | Да |

Здесь сравниваются проверки принадлежности уже представимого значения,
без effects пользовательских правил и без ошибок диапазона. Zero во всех
трёх моделях допустим как пустая комбинация; для Morphant это также утверждено.

Пользователь выбрал третий критерий. Он позволяет включить Pair целиком,
не объявляя его отдельные биты самостоятельными допустимыми значениями.
При этом Pair можно сочетать с Audit без нового объявления для каждого OR.
All = -1 не делает любое число допустимым. Это контракт Morphant, а не
заимствование числовой проверки Mapperly или Enums.NET. Более узкий прежний
кандидат, соответствовавший второму столбцу, снят.

Применение к ByMask и integer-to-flags, проверка диапазона и способ проверки
без перебора подмножеств описаны в
[основном дизайне](ENUM_MAPPING_DESIGN.md#строгая-допустимость-целой-числовой-маски).
Явные результаты не получают скрытой валидации; ByBit сохраняет отдельную
проверку каждого бита.

### Zero, null, применимость и вычисления

Остальные вопросы также закрыты; подробные контракты находятся в основном
дизайне:

| Решение | Обоснование |
|---|---|
| [Zero проходит правила один раз; затем конвенция даёт 0](ENUM_MAPPING_DESIGN.md#нулевая-маска-и-nullable-результат) | Позволяет переопределить None, сохраняя пустую маску без обязательного объявления; Explicit отключает этот автоматический шаг |
| [Null битового правила сразу завершает операцию](ENUM_MAPPING_DESIGN.md#нулевая-маска-и-nullable-результат) | Nullable результат отличается от удаления бита; следующие вычисления не выполняются |
| [FlagsMappingMode только для flags-to-flags](ENUM_MAPPING_DESIGN.md#применимость-flagsmappingmode) | Обычный enum, integer или string не получает подразумеваемого объединения результатов через OR; применимость settings проверяется по общему контракту |
| [Биты от младшего к старшему, signed high bit последним](ENUM_MAPPING_DESIGN.md#фабрика-result-и-вычисления) | Порядок effects определён и не зависит от объявлений и aliases; ширина source сохраняется |
| [Warning о доказанно недостижимом composite case](ENUM_MAPPING_DESIGN.md#диагностика-недостижимых-composite-cases) | Помогает обнаружить ошибку режима без blanket-запрета правил над полным result или вычисляемым значением; правило может наследоваться также для ByMask |

Список flags-имён и обратный parsing остаются вне согласованного объёма.
Потенциальное расширение потребует отдельного контракта canonical names,
aliases, порядка, разделителя и неизвестных битов; это не блокирующие
вопросы выбранного дизайна.

## Проверки перед реализацией

Согласованная FlagsMappingMode отвечает за единицу обработки.
Дополнительные переключатели fallback или числового overflow не вводятся.
UnmappedMemberValidation остаётся compile-time проверкой покрытия; он не
выбирает runtime fallback или допустимость неизвестных чисел. Реализация
flags coverage должна соблюдать [общий контракт](ENUM_MAPPING_DESIGN.md#6-проверка-покрытия-через-unmappedmembervalidation)
и границу доказуемости для atomic/composite declarations, без перебора всех масок.

Проверки выбранного контракта должны включать различные позиции битов,
aliases, неизвестные биты, ноль, composite-only enums, All = -1, signed high
bit и разные ширины; отдельно — сочетание explicit и automatic contributions,
Auto/Explicit, nullable, Using, ленивые уровни IncludeBase и число вычислений
locals/guards. Нужны различия ByBit/ByMask, независимость от стратегии и
наследование одного режима для всей пары. Identity E → E не должно обходить
