# EnumMappingStrategy: выбор стратегии по умолчанию

Дата: 2026-09-22. Статус: исследование; рекомендация принята пользователем.
Зафиксировано решение дизайна; production API не меняется.
Действующий набросок и принятые решения: [enum design](ENUM_MAPPING_DESIGN.md).

## Вывод для Morphant

`ByName` принят как default для enum-to-enum, включая одинаковые типы,
и для enum-to-string. В этих направлениях числовые режимы остаются явным
выбором для пар или проектов, где идентичность задаётся числовым кодом.
Integer-to-enum имеет отдельный строгий default `ByValue`, поскольку source
не имеет имени; применимость общего `ByName` описана в
[дизайне](ENUM_MAPPING_DESIGN.md#4-существующие-настройки--основа-enum-mapping).
Это вывод из сценариев и уже выбранной модели Morphant,
а не установленное предпочтение большинства пользователей других мапперов.

## Что делают другие мапперы

Ниже речь о разных enum-типах. Источники проверены на дату исследования;
документация и исходники проверены отдельно от исторических issues.
Сравнительные запуски библиотек и benchmarks не выполнялись.

| Инструмент | Default для enum-to-enum | Что подтверждает источник |
|---|---|---|
| AutoMapper, встроенный mapper | Сначала строковое представление с ignore-case parsing, затем числовое преобразование | В [EnumToEnumMapper](https://github.com/LuckyPennySoftware/AutoMapper/blob/main/src/AutoMapper/Mappers/EnumToEnumMapper.cs) видны `ToString`, `TryParse` и fallback cast. Для обычных именованных значений это имя, затем число; parsing также принимает числовую строку |
| AutoMapper.Extensions.EnumMapping | `ByValue`; `ByName` включается явно | [Документация расширения](https://docs.automapper.io/en/stable/Enum-Mapping.html). Это отдельный настраиваемый путь, не описание default встроенного mapper |
| Mapster | `ByValue`; можно выбрать `ByName` | [Документация](https://github.com/MapsterMapper/Mapster/wiki/Data-types#enums) и [EnumAdapter](https://github.com/MapsterMapper/Mapster/blob/master/src/Mapster/Adapters/EnumAdapter.cs). Числовой путь продолжает primitive conversion, путь по имени использует преобразование в строку и parsing |
| Mapperly | `ByValue`; отдельно доступны `ByName` и `ByValueCheckDefined` | [Документация enum mapping](https://mapperly.riok.app/docs/configuration/enum/). Критерий соответствия и проверка допустимости результата различаются |
| MapStruct, Java | По имени | [Reference guide](https://mapstruct.org/documentation/stable/reference/html/#mapping-enum-types): отсутствующее source-соответствие требует явного правила или приводит к ошибке генерации; overrides задаются через `ValueMapping` |
| Chimney, Scala | По именам вариантов sealed/enum | [Supported transformations](https://chimney.readthedocs.io/en/stable/supported-transformations/#between-sealedenums): соответствия должны покрывать source-варианты; целевой тип может иметь дополнительные варианты |

Единого default даже внутри C# нет. Нельзя считать встроенный AutoMapper
ещё одним голосом за чистый `ByValue`, смешав его с расширением.
Java/Scala дают полезную модель сопоставления вариантов по смысловым именам,
но их enum/ADT не равнозначны C# enum с произвольным underlying integer.
Сравнение не является подсчётом голосов независимых одинаковых систем.

## Что говорят пользователи и авторы

### Mapperly: прямой спор о default

В [issue #1581, 2024](https://github.com/riok/mapperly/issues/1581) пользователь
просит default `ByName`. Его gRPC enum содержит начальный `Unknown`,
а domain enum начинается с `User`. Числовой mapping превращает первый
вариант в другой смысловой статус. Пользователь описывает цепочку
gRPC → DTO → domain → projection → DTO → REST, где наборы значений отличаются.

Автор Mapperly [отвечает](https://github.com/riok/mapperly/issues/1581#issuecomment-2458889985),
что в его проектах примерно 60% случаев требуют `ByValue`, и спрашивает
об основаниях считать `ByName` более распространённым. Это оценка его
проектов, не статистика сообщества. Собеседник описывает противоположный
опыт и необходимость общего default для множества проектов.

Вывод: реальная развилка — смысловые варианты разных моделей либо один
числовой контракт в разных типах. Обе потребности подтверждаются; issue
не устанавливает победителя и не доказывает первоначальную причину выбора
default авторами Mapperly.

### AutoMapper: числовой fallback может скрывать проблему

В [issue #3562, 2021](https://github.com/LuckyPennySoftware/AutoMapper/issues/3562)
предлагается отказаться от fallback по числу после несовпадения имён:
поведение названо запутывающим, числовой mapping предлагается выбирать явно.
Issue закрыт, но проверенный текущий встроенный mapper сохраняет числовой
fallback. Поэтому нельзя представлять запрос как принятое изменение.

Вывод для Morphant: не вводить скрытое «имя, а если не получилось — число»
в `ByName`. Оно может поглотить случай, для которого пользователь написал
завершающий fallback или ожидает исключение.

### Mapster: важен понятный scope настройки

В [issue #402](https://github.com/MapsterMapper/Mapster/issues/402) и
[обсуждении](https://github.com/MapsterMapper/Mapster/issues/402#issuecomment-1509985039)
пользователи ожидают mapping по имени, задав стратегию на паре содержащих
объектов; ответы объясняют настройку enum-пары либо общего default.
Это свидетельство затруднения с областью настройки, не опрос о default.

Morphant уже имеет pair/mapper/MSBuild уровни. Другой default должен
задаваться там, где нужен общий выбор, без повторения правил для каждого
значения и без изменения контракта явного nested mapping.

### Проверка покрытия полезна, но не выбирает смысл соответствия

[Mapperly #325](https://github.com/riok/mapperly/issues/325) запрашивает
compile-time-проверку полноты enum mapping; автор предлагает diagnostics
с настраиваемой severity. Это подтверждает отдельную потребность в coverage.
Она не доказывает предпочтительность `ByName` или `ByValue` и не распознаёт
ошибочный смысл пары, если все значения уже получили соответствия.

Прямого исторического объяснения выбора default в просмотренных источниках
Mapster и AutoMapper.Extensions.EnumMapping не найдено. Простота cast и
соответствие числовым протоколам — аргументы нашего анализа, а не приписанная
авторам мотивация. Issues показывают сценарии и неудобства; по их количеству
нельзя оценить долю пользователей каждой стратегии.

## Какие ошибки делает каждый default

Собственный пример: source объявляет `Draft = 0, Active = 1, Cancelled = 2`,
destination — `Active = 0, Cancelled = 1, Draft = 2`.

| Source | `ByName` | `ByValue` |
|---|---|---|
| `Draft` (`0`) | `Draft` (`2`) | `Active` (`0`) |
| `Active` (`1`) | `Active` (`0`) | `Cancelled` (`1`) |
| `Cancelled` (`2`) | `Cancelled` (`1`) | `Draft` (`2`) |

Если одинаковые имена обозначают одинаковые состояния, числовой результат
неверен, хотя все destination-числа объявлены и обе стороны полностью
покрыты. Проверка объявленности или `UnmappedMemberValidation.Strict`
не обнаружит эту перестановку. Это вывод из примера, не результат запуска
ещё не реализованного Morphant enum mapping.

Обратный сценарий: `Active = 10` и `STATUS_ACTIVE = 10` представляют один
протокольный код. `ByValue` сразу даёт правильный результат; `ByName`
потребует настройки или explicit правила. Общий выбор `ByValue` здесь
удобнее множества одинаковых overrides. Имена также могут измениться при
сохранении стабильных кодов, поэтому `ByName` не является универсально
правильным или доказательством смысловой совместимости.

Различие рисков: отсутствие имени приводит к обычному fallback/throw,
а случайно совпавшее число может дать правдоподобный неверный статус.
Явный blanket fallback способен скрывать изменения и при `ByName`;
поведение неизвестных значений и coverage остаются отдельными решениями.

## Почему для Morphant выбран ByName

1. Конвенции Morphant уже используют имена, включая tuple mapping без
   позиционного подбора. Сопоставление enum по именам продолжает эту модель.
2. `Members` описывает отличающиеся смысловые случаи, а остальные заполняет
   конвенция. Независимая нумерация domain/API не должна превращать такие
   случаи в длинный список переноса одинаковых имён.
3. Предпочтительнее потребовать явного выбора числового контракта, чем
   молча сопоставить разные состояния по случайно одинаковым кодам.
   Пользователь, которому нужен `ByValue`, может выбрать его для пары,
   mapper или через общий MSBuild default.
4. Настройка Morphant распространяется также на enum-to-string. Для
   именованного `Active = 1` default `ByName` даёт `"Active"`, `ByValue` —
   `"1"`. У Mapster enum-to-string идёт отдельным путём независимо от
   настройки enum-to-enum; у Mapperly имена строк задаются отдельной
   `EnumNamingStrategy`. Их числовой default нельзя переносить на более
   широкую настройку Morphant без этого последствия.
5. Автоматическое разбиение flags не требует менять критерий соответствия:
   имя бита может сохранять смысл при другой позиции в target mask.
   Для общих числовых масок применяется `ByValue`. Атрибут `[Flags]`
   не должен сам переключать стратегию.

Это решение для нового first-class API, у которого ещё нет legacy
default, требующего сохранения совместимости. Единственная новая настройка
остаётся `EnumMappingStrategy`; остальные согласованные settings сохраняют
свою ответственность. Глобальный `ByValue` честно влияет и на enum-to-string;
для исключений используется обычный pair-level override. В enum-to-enum и
enum-to-string нет скрытого default поверх явно выбранной стратегии.
Применимость `ByName` к integer-to-enum имеет отдельный согласованный контракт.

Скорость не решает вопрос без дополнительных данных. Cast может быть дешевле
runtime string conversion, но Morphant может сгенерировать `ByName` как
switch по enum-константам без `ToString`/parsing. Позднее пользователь выбрал
строгий `ByValue` и отдельный режим сохранения неназванных чисел; flags-семантика
отложена. Поэтому нельзя обещать, что числовая стратегия всегда сводится
к одному cast. Подробности — в [числовом исследовании](ENUM_MAPPING_NUMERIC_RESEARCH.md).

## Границы решения

Сохраняются принятые exact-first/ignore-case правила, приоритет explicit
веток перед конвенцией и конвенции перед fallback, а также действие
`MemberSelection.Explicit`. Сам выбор default не определял числовую
допустимость: два числовых режима, destination-only строгость, same-type
и управление переполнением согласованы отдельно. Применимость числовых режимов
к integer-to-enum со строгим default также утверждена. Слияние `IncludeBase`
ещё обсуждается;
zero/composite flags отложены вместе с остальной flags-семантикой.
Обратный числовой parsing string-to-enum остаётся вне текущего предложения.

Будущие проверки должны различать перестановку чисел при одинаковых именах,
одинаковые коды при разных именах, вставку
нового enum-значения, разные позиции одноимённых flags, строковые имена
и числа, а также наследование и переопределение стратегии на обычных уровнях.
