## 1. Объявление маппера, подключение и вызов

Сильные стороны: маппер — обычный класс с внедрением зависимостей через
конструктор; `ITypeMapper<TSource, TDestination>` — типизированный контракт,
который можно реализовать вручную; ошибки объявления подробно диагностируются;
атрибут `[MorphantMapper]` даёт быстрый поиск мапперов в генераторе и отличает
конечный маппер от переиспользуемой базы.

### 1.1. Вложенные вызовы всегда идут через DI — Принято

Сгенерированный код вызывает любой вложенный `Map`/`Create`/`Update` через
`context.Mapper`, то есть через `IServiceProvider`, даже если пара объявлена в
том же маппере. Последствия:

- вложенный маппинг выполняет ту конфигурацию пары, которая зарегистрирована в
  DI, а не ту, что объявлена в этом маппере; при одной паре в двух мапперах
  результат зависит от DI-композиции или даёт `AmbiguousMappingException`;
- standalone-вызов через `ITypeMapper` ищет вложенную пару в том же маппере,
  то есть один маппер ведёт себя по-разному в зависимости от способа вызова;
- каждую вложенную пару приходится регистрировать в DI;
- каждый вложенный вызов — поиск в контейнере, перечисление и аллокации,
  в коллекциях — на каждый элемент.

**Решение.** Пара, которую реализует тот же маппер, вызывается напрямую. Через
`IMapper` идут только пары, которых маппер не реализует. Пары базового
маппера, подключённые через `base.Configure`, сейчас доступны только для
`IncludeBase` и не реализуются производным маппером; их статус решается в
пункте 9.

### 1.2. Ручная регистрация каждой пары в DI — Отложено

Каждая пара регистрируется отдельной строкой; новая пара без регистрации
проявляется только `MappingNotFoundException` во время выполнения. Варианты,
рассмотренные в ревью:

- композитный `IMapper` над набором мапперов (`new Mapper(mapperA, mapperB)`):
  регистрируются мапперы, а не пары; работает и без DI;
- сгенерированное расширение `services.AddXxxMapper()` при ссылке на
  `Microsoft.Extensions.DependencyInjection.Abstractions`;
- одна сгенерированная регистрация всех мапперов сборки.

Тема регистрации в DI отложена до завершения основных функций.

### 1.3. Нет ранней проверки регистраций — Отложено

Генератор знает внешние пары, нужные каждому мапперу, и может выдать данные
для проверки при старте без рефлексии. Отложено вместе с 1.2.

### 1.4. Забытый `[MorphantMapper]` не диагностируется — Принято

Генератор находит мапперы только по атрибуту, анализаторов нет. Без атрибута
голый `Map` компилируется без результата, а `.Members(...)` даёт
вводящую в заблуждение `CS1061`.

Пользовательский сценарий, при котором неабстрактный наследник `TypeMapper`
не должен генерироваться, найден один: наследник уже сгенерированного маппера
(например, тестовый двойник). Он получает реализацию от базы.

**Решение.** Добавить ошибку с отдельным ID: неабстрактный класс, производный
от `TypeMapper`, без `[MorphantMapper]` у него и у всех базовых классов.
Исправление — добавить атрибут или сделать класс `abstract`.

Error, а не warning: единственный законный сценарий исключён правилом, других
не найдено, исправление тривиально. Все правила Morphant, кроме предупреждений
о полноте маппинга (`MORPH0047`, `MORPH0048`), — ошибки. При ложном
срабатывании severity понижается через `.editorconfig`.

### 1.5. Два способа вызова — Не проблема (DI-часть отложена)

`IMapper.Map` намеренно упрощён под привычную по другим мапперам модель;
`ITypeMapper` конкретнее и разделяет операции `Create` и `Update`. Разные
глаголы на разных уровнях не считаем проблемой. Двухаргументный generic Create
(`Map<TSource, TDestination>(source)`) рассматривается в пункте 2.

Невозможность межмапперных вызовов без DI и сложность quick start относятся
к регистрации и отложены вместе с 1.2.

### 1.6. Время жизни мапперов не объяснено — Отложено

Документация везде использует `AddScoped` без объяснения. Маппер без
зависимостей можно сделать singleton, а scoped `IMapper` нельзя внедрить в
singleton. Отложено вместе с 1.2.

### 1.7. DSL-методы вызываются вне конфигурации — Принято при условии

`Map`, `Create`, `Update`, `Auto`, `Ignore`, `Value`, `ByConvention` — это
`protected static` члены `TypeMapper`; методы билдеров и сгенерированные
расширения доступны как обычные методы. Вызов вне `Configure` компилируется
и бросает `RuntimeInvocationNotSupportedException` во время выполнения.

**Решение.** Добавить анализатор, если он надёжен, прост и дёшев. Оценка
ревью:

- целевые методы определяются по символу (содержащий тип — `TypeMapper<>`,
  `MapperBuilderBase<>`, `MappingBuilder<,,>` или сгенерированный класс
  расширений), без эвристик по именам;
- проверка — operation action на вызов и ссылку на метод с подъёмом до
  содержащего метода; допустим только override `TypeMapper.Configure`, включая
  вложенные лямбды; некорректные позиции внутри `Configure` по-прежнему
  диагностирует генератор (`MORPH0033`);
- стоимость: сравнение символов на каждый вызов, без состояния на всю
  компиляцию; поддерживается конкурентное выполнение;
- анализатор поставляется в том же пакете и может использоваться также для 1.4.

Правило получает отдельный ID, а не `MORPH0033`. У них разные причина и
исправление: `MORPH0033` — API в неподдерживаемой позиции внутри конфигурации,
новое правило — вызов вне `Configure`, который бросит исключение во время
выполнения. Их выдают разные компоненты, и severity каждого настраивается
отдельно. Правило покрывает DSL-хелперы `TypeMapper`, методы билдеров и
настроек и сгенерированные расширения. Номера новых ID назначаются при
реализации.

### 1.8. CRTP `TypeMapper<TSelf>` — Принято

**Происхождение.** Self-тип появился в 0.5.0 вместе с кортежами. C# стирает
имена элементов кортежа, nullable-аннотации и различие `dynamic`/`object` из
CLR-идентичности типа, но они влияют на конвенции и типы callback-ов. Две
регистрации одной CLR-пары с разным представлением требуют разных
сгенерированных расширений `Members`/`Construct` на одном и том же receiver,
что ведёт к конфликту. Первая реализация кортежей диагностировала такие
конфликты (`MORPH0056`) и откладывала mapper scope как редкий escape hatch.
Затем scope по мапперу стал обязательным для всех мапперов: receiver
`MappingBuilder<TMapper, TSource, TDestination>` и расширения,
специализированные для каждого маппера.

**Что даёт CRTP:**

- одна CLR-пара с разными именами элементов кортежа или аннотациями в разных
  мапперах одной сборки;
- независимые поверхности для пересекающихся открытых generic-пар в
  несвязанных семействах мапперов;
- отсутствие конфликтов с внутренними расширениями другой сборки, видимыми
  через `InternalsVisibleTo`.

**Чего стоит CRTP:**

- для пользователя: повтор имени класса в `TypeMapper<ApplicationMapper>`;
  для переиспользуемой базы — рекурсивное ограничение
  `where TMapper : CommonMapper<TMapper>`; длинные типы в IntelliSense и
  ошибках;
- новые ограничения, порождённые scope: `MORPH0058` (неверный self-тип),
  `MORPH0060` (каждый параметр семейства обязан входить в каждую пару),
  требование доступности маппера для namespace-level кода (`MORPH0059`);
- для генератора: расширения на каждую пару каждого маппера вместо одного
  набора на пару, вычисление scope семейств, общая поверхность для
  пересекающихся базовых и производных scope.

**Оценка ревью.** Выгода касается редкого сценария: одна CLR-пара с разным
представлением в разных мапперах одной сборки. Цена ложится на каждого
пользователя с первой строки и на каждую будущую функцию генератора. CRTP
того не стоит.

**Решение — компромисс.**

- Вернуть необобщённый базовый класс `TypeMapper` и общую для сборки поверхность
  на каждую CLR-пару.
- Внутри сборки у CLR-пары одно представление: имена элементов кортежей,
  вложенные nullable-аннотации и `dynamic` должны совпадать у всех мапперов.
  Расхождение — `MORPH0056` с исправлением «используйте те же имена или
  отдельный DTO». Верхнеуровневые аннотации в представление не входят (см.
  ниже).
- Обычные кортежи остаются полноценными: несколько входов, несколько выходов,
  данные вызова, конвенции по именам элементов в одном представлении.
- Открытые generic-пары получают generic-расширения по своим параметрам;
  неоднозначное пересечение несвязанных открытых пар диагностируется.
- Видимые через `InternalsVisibleTo` расширения другой сборки для той же пары
  диагностируются вместо неоднозначности `CS0121`.
- Отдельный opt-in scope маппера не добавляется: два стиля объявления
  усложнили бы дизайн. К нему можно вернуться, если реальное использование
  покажет потребность.

`MORPH0058` и ограничение `MORPH0060` уходят; требование доступности
`MORPH0059` пересматривается. Изменение ломает API 0.5.0; миграция
механическая — убрать self-тип и рекурсивные ограничения.

**Верхнеуровневые nullable-аннотации нормализуются.** Аннотация ссылочного типа
на верхнем уровне source и destination не входит в представление пары:
`Map<Source?, Destination?>` и `Map<Source, Destination>` — одна пара в любом
маппере сборки. Сейчас аннотация source на сгенерированные сигнатуры не влияет,
а аннотация destination определяет тип возврата `Convert`, `ConstructUsing` и
`ResolveUsing` и аннотацию реализуемого `ITypeMapper<,>`. После нормализации
генератор выдаёт одну форму независимо от записи.

Это соответствует текущему runtime API и модели AutoMapper: аннотацию
результата выбирает вызывающий через `TDestination`, а null handling от
аннотаций не зависит. В документации явно указать, что результат маппинга и callback-ов
может быть `null`; каноническое место — раздел о nullability результата на
странице null handling. `Nullable<T>` значимых типов — отдельный CLR-тип и не
нормализуется; вложенные аннотации входят в представление, как и прежде.

Нормализованная форма:

- `Convert`, `ConstructUsing` и `ResolveUsing` возвращают `Destination?`:
  `null` — их документированный результат, а при `Destination` он требовал бы
  `null!`. Предупреждение о случайном `null` теряется; возврат `null` из
  DSL-лямбды редок;
- параметры source не меняются: `Source` для декларативных и `Using`-callback-ов,
  `Source?` для `Convert`;
- маппер реализует `ITypeMapper<Source, Destination>` без аннотаций —
  обычную форму регистрации в DI.

## 2. Runtime API и модель вызова

Сильные стороны: небольшой типизированный API; поиск только точной пары
`ITypeMapper<TSource, TDestination>`, без подстановки базовых типов и без
зависимости от порядка регистрации; Update возвращает результат, что
поддерживает замену destination и значимые типы; исключения несут операцию и
типы пары, а исключения пользовательского кода не оборачиваются; данные вызова
передаются типизированно через кортеж-source; использование `context.Mapper`
после завершения вызова обнаруживается.

### 2.1. Create требует обоих аргументов типа — Отложено

C# не выводит часть аргументов типа, поэтому в `mapper.Map<OrderDto, Order>(dto)`
source повторяется, хотя известен из аргумента. Особенно длинно для кортежей и
generic-типов:

```csharp
var dto = mapper.Map<
    (Order Order, Customer Customer, decimal TaxRate),
    OrderDto>((order, customer, taxRate));
```

Внутри DSL source выводится (`Map<Address>(source.Address)`), в runtime-коде и
в callback-ах через `context.Mapper` — нет.

Варианты:

- оставить: пара видна на месте вызова;
- добавить расширение `mapper.From(source).To<TDestination>()`. Source —
  статический тип выражения, как при любом выводе типов C#. Вызов делегирует
  `Map<TSource, TDestination>`, поэтому моки `IMapper` не меняются. Имя `From`,
  а не `Map`, чтобы незавершённый вызов не выглядел результатом:
  `return Ok(mapper.Map(dto))` сериализовал бы промежуточный объект;
- сделать такую форму единственной: теряются method group
  (`Select(context.Mapper.Map<OrderDto, Order>)`) и простые моки.

Предложение ревью — второй вариант. Расширения для упрощения работы с маппером
запланированы, но отложены до реализации основных функций, включая
first-class поддержку коллекций, с которой они могут быть связаны.

### 2.2. `context.Mapper` не следует решению 1.1 — Принято

Обычные callback-и (`Convert`, `ConstructUsing`, `ResolveUsing`) вызывают
вложенные маппинги только через `context.Mapper`, а он всегда ищет пару в DI.
После 1.1 в одном маппере `Map<Address>(...)` в `Members` выполнит
собственную пару напрямую, а `context.Mapper.Map<AddressDto, Address>(...)` в
`Convert` — пару из DI, возможно чужую. Для пользовательского кода регистрация
собственных пар остаётся обязательной. В standalone-режиме `context.Mapper` уже
ищет пару в текущем маппере.

**Решение.** Одно правило для всех вложенных вызовов, сгенерированных и
пользовательских: пару, объявленную в текущем маппере, выполняет сам маппер,
остальные идут в `IMapper` приложения.

### 2.3. Результат Update можно молча потерять — Принято при условии

`mapper.Map(dto, order);` компилируется, но результат теряется, когда Update
возвращает не переданный объект:

- `order` равен `null`, а `NullDestinationHandling` по умолчанию `Create`:
  созданный объект выбрасывается, upsert молча ничего не делает;
- `Resolve`, `ResolveUsing` или `Convert` вернули замену;
- destination — значимый тип: изменённая копия теряется всегда.

Документация требует всегда сохранять результат, но компилятор не помогает.

Варианты:

- предупреждение анализатора на любой отброшенный результат Update
  (`IMapper.Map(source, destination)`, `ITypeMapper.Update`, расширение
  `Update`); явный `_ =` его снимает. Совпадает с документированным правилом и
  ловит все три случая; шум для in-place обновления, исправление тривиально;
- предупреждение только для значимых destination: без ложных срабатываний, но
  `null` и замену не ловит;
- только документация, как сейчас.

**Решение.** Warning только там, где потеря результата известна на месте
вызова, если диагностика проста и дешева. Оценка ревью:

- достоверных случаев два: destination известного значимого типа (включая
  `Nullable<T>` и параметр типа с ограничением `struct`) и destination —
  константа `null` или `default`;
- `null` в переменной и замена через `Resolve`, `ResolveUsing` или `Convert`
  не диагностируются: на месте вызова через `IMapper` это не известно;
- у значимого destination ссылочные объекты, обновлённые вложенным Update на
  месте, сохраняют изменения, но изменения самого значения теряются;
  предупреждение говорит именно о потере возвращённого значения;
- проверка — operation action на вызов в позиции expression statement:
  сравнение символа метода (`IMapper.Map(source, destination)`,
  `ITypeMapper.Update`, расширение `Update`), признак значимого типа у
  аргумента типа и константное значение аргумента. Без анализа потока данных и
  состояния на компиляцию; общая инфраструктура с анализатором 1.7.

Условие выполнено.

### 2.4. В `MappingContext` нет пользовательского состояния — Отложено

Аналога `Items` из AutoMapper нет. Данные вызова передаются типизированно через
кортеж-source, окружение запроса — через зависимости маппера. Цена: данные,
нужные глубоко во вложенном маппинге, приходится протаскивать через кортежи
промежуточных пар. Нетипизированный словарь противоречит типизированному DSL;
типизированный контекст — новая сущность с вопросами времени жизни и передачи
во вложенные вызовы.

Предложение ревью: не проблема. Отложено до реальной потребности.

### 2.5. Поиск в DI на каждый вызов — Отложено

Каждый вызов через `IMapper` разрешает `IEnumerable<ITypeMapper<,>>` и
перебирает его, чтобы отличить 0, 1 и 2+ регистраций; это аллокации на каждый
вызов. После 1.1 это касается только верхнеуровневых вызовов и пар других
мапперов. Неоднозначность — ошибка конфигурации, которую дешевле проверить один
раз (1.3).

Работа над производительностью этого места запланирована и отложена ради более
приоритетных функций.

## 3. Философия DSL: обычный C# против C#-подобного декларативного языка

Сильные стороны: конфигурация — типизированный C# с IntelliSense,
переименованием, переходом к определению и ошибками типов, без строк и
`nameof`; правила членов записываются одним object initializer-ом в форме
результата; пользовательские выражения, locals и ветви переносятся в
сгенерированный код с сохранением структуры, отдельно написанные выражения
вычисляются отдельно, а результат можно посмотреть; `Using`-callback-и и
`Convert` — явный выход в обычный C#; нарушения правил DSL диагностируются при
компиляции.

Цена подхода: код выглядит как C#, но это диалект. `Configure` не
выполняется, лямбды — шаблоны, а вместо реальных типов стоят
`Member<T>`, `ConstructorParameter<T>` и сгенерированные типы конструирования.
Неожиданности возникают на границе между C# и диалектом.

### 3.1. `Member<T>` и `ConstructorParameter<T>` принимают не всё — Отложено

Обёртки принимают значения через пользовательские implicit-конвертации, а C#
применяет их не всегда. Проверено компиляцией копии обёрток с теми же
операторами (2026-11-18):

| Значение | Результат |
|---|---|
| Значение интерфейсного типа, включая результат LINQ (`IEnumerable<T>`), даже в член того же интерфейса или `object` | `CS0029`: конвертации из интерфейсов не рассматриваются |
| Лямбда, method group | `CS1660`, `CS0428` |
| Collection expression | `CS9174` |
| Target-typed `new() { ... }` | Связывается с `Member<T>`: `CS0122`, `CS0117` |
| Обычные классы, массивы, числа, `null`, кортежные литералы, `switch` | Работают; nullability сохраняется |

Например, `Names = source.Items.Select(item => item.Name)` для члена
`IEnumerable<string>` не компилируется. Исправление — `Value<T>(...)` или явный
тип, но ошибка компилятора говорит о внутреннем `Member<T>`, а документация
упоминает `Value<T>` только для точного типа и collection expressions.

Варианты:

- оставить обёртки; добавить code fix «обернуть в `Value<T>`» для этих ошибок
  компилятора на цели DSL и перечислить случаи в каноническом разделе
  `Value<T>`. DSL не меняется. Code fix требует отдельной сборки в пакете:
  генератор и анализатор не должны ссылаться на Workspaces;
- сопровождать ошибку компилятора диагностикой Morphant с объяснением: две
  ошибки на одно место, хуже code fix;
- перепроектировать поверхности так, чтобы значения связывались без
  пользовательских конвертаций: реальные типы членов и маркеры через `dynamic`
  или явные generic-маркеры. Убирает класс проблем, но `dynamic` отключает
  проверку типов вокруг маркеров и требует `Microsoft.CSharp`, а явные маркеры
  удлиняют каждый `Auto()`.

**Решение.** Первый вариант: DSL не меняется, code fix «обернуть в
`Value<T>`» добавляется позже. Сейчас отложено.

### 3.2. `new(...)` в `Construct` и `Resolve` — не конструктор destination — Отложено

`new(source.Id)` создаёт сгенерированный `OrderConstruction`, а
`new Order(source.Id)` — `MORPH0062`. В смешанном условном выражении `Resolve`
C# выводит `new(...)` как `Order`, поэтому приходится писать имя
сгенерированного типа:
`previous.HasValue ? previous.Value : new OrderConstruction(source.Id)`.

Тип конструирования вынужден: маркеры как аргументы и required/init-члены,
заданные в `Members`, нельзя выразить через `new Order(...)` (для required-членов
это `CS9035`). `MORPH0062` объясняет исправление, форма `if`/`return` работает
без имени типа.

**Решение.** Дизайн не меняется. Смешанное условное выражение исправляется
code fix-ом, который заменяет `new(...)` на явный тип конструирования.
Отложено вместе с 3.1.

### 3.3. `Configure` выглядит как код, но является декларацией — Принято

`Configure` не выполняется: locals из него нельзя захватывать (кроме
констант), регистрации нельзя делать условно или в цикле, builder нельзя
сохранить или передать во вспомогательный метод. Обычные приёмы C#, включая
рефакторинг «Extract method», дают диагностику. Переиспользование идёт через
механизмы Morphant (пункт 9).

Это свойство compile-time подхода, и нарушения диагностируются. Но quick start
не говорит, что `Configure` не выполняется; это сказано только в руководстве
по декларативному маппингу.

**Решение.** Дизайн не меняется. В quick start добавить одно предложение о
том, что `Configure` читается генератором и не выполняется, со ссылкой на
правила.

### 3.4. Два вида callback-ов — Не проблема

Декларативные `Construct`, `Resolve`, `Members` (inline-лямбды, маркеры,
вложенный `Map`) и обычные `ConstructUsing`, `ResolveUsing`, `Convert`
(делегаты, `context.Mapper`) различаются правилами. Граница последовательна:
суффикс `Using` и `Convert` означают обычный C#. После 2.2 вложенные вызовы в
обоих видах подчиняются одному правилу; остаётся многословность
`context.Mapper.Map<TSource, TDestination>`, отложенная в 2.1.

## 4. Выбор способа создания destination

Сильные стороны: способы создания образуют систему 2×2: декларативные
`Construct` и `Resolve` против обычных `ConstructUsing` и `ResolveUsing`;
`Construct*` работают только без destination, `Resolve*` — на каждом Create и
Update. Суффикс `Using` последовательно означает обычный C#, `Convert` — полный
выход. Выбор конструктора не откатывается молча к другому конструктору, а
ничьи считаются ошибкой. `ByConvention()` переопределяет отдельные параметры, не
отказываясь от конвенции. `null` из фабрики — документированный окончательный
результат. Interface и abstract destination создаются фабрикой, а Update-only
маппинг работает без неё.

### 4.1. Шесть стратегий `ConstructorSelection` — Не проблема

`Explicit`, `Parameterless`, `Single`, `Unambiguous` (по умолчанию),
`Greediest`, `Largest`. Различия тонкие:

- `Single` отличается от `Unambiguous` только при одновременном наличии
  конструктора без параметров и одного параметризованного: ошибка вместо
  выбора параметризованного;
- `Largest` отличается от `Greediest` только тогда, когда самый большой
  конструктор нельзя вызвать: ошибка вместо выбора меньшего.

Каждую стратегию нужно документировать, тестировать и понимать, а сценарии
для `Single` и `Largest` в истории проекта не описаны: стратегии вводились
набором. Строгость, которую они дают, доступна через `Explicit` и явный
`Construct`.

Варианты:

- оставить шесть стратегий;
- оставить `Explicit`, `Parameterless`, `Unambiguous` и `Greediest`, убрать
  `Single` и `Largest`. Ломающее изменение до 1.0.

Предложение ревью было — второй вариант. **Решение:** оставить все стратегии.
Они опциональны и не усложняют путь по умолчанию; пользователь выбирает
подходящую.

### 4.2. `previous` — `Option<Destination>`, а не `Destination?` — Не проблема

`Resolve`, `Members`, `ResolveUsing` и `Convert` получают `previous` как
`Option<Destination>`. Обычный C# ожидал бы `Destination?` с `is { }` и `??`.

`Option` одинаково работает для ссылочных и значимых типов и в обобщённых
делегатах runtime API, где `T?` для неограниченного `T` не различает
отсутствие значения. Он никогда не содержит `null`, а его члены знакомы:
`HasValue` и `Value` — как у `Nullable<T>`, `TryGetValue` — как у словарей.
Форма `previous ?? new(source.Id)` не помогла бы и с `Destination?`: C# вывел
бы `new(...)` как destination (3.2).

Единая работа со ссылочными и значимыми типами — назначение `Option`; его
наличие оправдано.

## 5. Members: порядок вычислений и связь с конструктором

Сильные стороны: явный аргумент конструктора и правило члена ведут себя как
`new D(x) { P = y }` — оба вычисляются, initializer применяется после
конструктора. Правило члена задаёт и соответствующий автоматический аргумент
конструктора, поэтому у record-ов одно место настройки и одно вычисление.
Отдельно написанные выражения не объединяются. Правила, читающие `result`,
видят исходное состояние, поэтому обмен значениями работает; при этом
текстовый порядок вычислений сохраняется — проверено на сгенерированном коде
текущего `main` (2026-11-19). `Ignore()` для параметра конструктора опускает
только optional-параметр, для обязательного — ошибка `MORPH0037`.

### 5.1. `Ignore()` в `Members` не действует на автоматический аргумент конструктора — Принято

Значение и `Auto()` в `Members` передаются в связанный автоматический параметр
конструктора, а `Ignore()` — нет: параметр получает значение по конвенции.
Проверено генератором (2026-11-19):

```csharp
public sealed record OptionalPerson(string Name = "none");

builder.Map<PersonSource, OptionalPerson>()
    .Members(source => new() { Name = Ignore() });
// Create: new OptionalPerson(Name: source.Name); Update: без изменений.
```

Для settable-члена такое `Ignore()` осмысленно: Create задаёт значение через
конструктор, Update не перезаписывает его. Но для creation-only члена (init
или позиционного), который получает значение из автоматического параметра,
правило не действует ни в одной операции: Create берёт конвенцию, а Update
такой член не меняет. Пользователь видит «игнорировать», а значение
маппится. Диагностики нет; документация говорит лишь, что `Ignore()` действует
только там, где написан.

Варианты:

- ошибка, если `Ignore()` в `Members` не действует ни в одной включённой
  операции: член creation-only и получает значение из автоматического
  параметра конструктора. Исправление — правило для параметра в `Construct`
  (`ByConvention()` и `Ignore()` для optional-параметра) или удаление правила.
  Ложных срабатываний нет; ошибка, а не warning, по аналогии с явной
  настройкой без эффекта (`MORPH0023`);
- распространять `Ignore()` на связанный параметр: optional опускается,
  обязательный — ошибка;
- оставить и описать в документации.

Текущее поведение соответствует контракту: `Ignore()` действует только там,
где написан (`docs/api/members.md`, правило `Ignore()` каждой позиции в
`GENERATOR_CONTRACTS.md`). Поэтому это изменение контракта, а не исправление
ошибки генерации.

Поскольку `Members` воспринимается как свойства, применение его правил к
конструктору может быть неинтуитивным. Связь значений и `Auto()` с
автоматическим параметром конструктора уже существует, поэтому вопрос шире
`Ignore()`. Целостных моделей две:

- модель значений (текущая для значений и `Auto()`): правило `Members` задаёт
  значение члена, а Morphant передаёт его через автоматический конструктор или
  setter. Для record-а с переименованным свойством достаточно `Members`,
  значение вычисляется и записывается один раз. Цена: конструктор, который
  преобразует параметр, меняет и записанное значение, а связь определяется по
  имени и в IntelliSense не видна;
- модель initializer-а: `Members` — только присваивания после
  конструирования, а автоматический конструктор получает значения только по
  конвенции. Совпадает с буквальным чтением `new D(...) { Name = x }`, и
  текущее `Ignore()` в ней последовательно. Цена: record без одноимённого
  члена source не создать без `Construct`, а позиционное свойство
  записывается дважды — конструктором по конвенции и initializer-ом.

Неожиданность 5.1 возникает из смешения моделей.

**Решение.** Модель значений целиком, включая `Ignore()`: она богаче и удобнее.
`Ignore()` означает «игнорировать» и действует на связанный автоматический
параметр так же, как значение и `Auto()`:

- optional-параметр опускается и получает значение по умолчанию; setter не
  вызывается, Update член не перезаписывает;
- обязательный параметр без значения делает конструктор неприменимым, как
  любой параметр без значения. `Greediest` выбирает лучший из оставшихся
  применимых конструкторов; `Single`, `Unambiguous` и `Largest` не
  откатываются и выдают ошибку, если выбранный конструктор содержит такой
  параметр. Исправление — явный аргумент в `Construct` или удаление правила.
  У `Parameterless` связанных параметров нет;
- явное правило параметра в `Construct` не связано с правилом члена. Поэтому
  сценарий settable-члена «задать при создании, не перезаписывать при Update»
  выражается как `Construct(source => new(source.Name))` вместе с
  `Name = Ignore()`.

Связь сделать видимой: в IntelliSense члена поверхности `Members` указать, что
при автоматическом конструкторе значение передаётся в одноимённый параметр, а
в руководстве по `Members` сказать это одним предложением до таблицы. Обновить
контракт в `docs/api/members.md` и `GENERATOR_CONTRACTS.md`.

## 6. Конвенции

Сильные стороны: конвенции строгие и предсказуемые — точное имя и неявная
конверсия C# без предупреждений, без нормализации имён. У flattening явный
порядок приоритета, неоднозначность — ошибка `MORPH0051`, а nullable-путь даёт
`null`, а не выдуманное значение. `IncludeMembers` подключает вложенный source
явно; `MemberSelection.Explicit` и `Auto()` включают конвенцию точечно.

### 6.1. Совпавший по имени член молча не маппится — Принято

Проверено генератором с настройками по умолчанию (2026-11-19). Маппинг
`OrderDto -> Order`, где у каждого члена destination есть source-член с тем же
именем:

| Source | Destination | Почему конвенция не применяется |
|---|---|---|
| `string? Name` | `string Name` | предупреждение nullability |
| `int? Count` | `int Count` | нет неявной конверсии |
| `long Total` | `int Total` | нет неявной конверсии |
| `AddressDto Address` | `Address Address` | конвенция не запускает вложенный маппинг |
| `List<ItemDto> Items` | `List<Item> Items` | элементы коллекций не маппятся |
| `string code` | `string Code` | имена членов сравниваются с учётом регистра |

Сгенерированный Create — `new Order()`, Update возвращает destination без
изменений, диагностик нет: `UnmappedMemberValidation` по умолчанию `None`.
Совпадение имени — явный признак намерения, но результат молча пустой.

Варианты:

- warning по умолчанию, независимый от `UnmappedMemberValidation`: у
  destination-члена есть source-член с тем же именем (с точностью до регистра)
  или flattened-путь, но конвенция не может его использовать. Сообщение
  называет причину и исправление: `Map()`, явное выражение или `Ignore()`;
  явное правило снимает предупреждение;
- добавить причину в сообщение `MORPH0048`: при проверке, выключенной по
  умолчанию, ничего не изменится;
- оставить как есть.

**Решение.** Первый вариант: добавить предупреждение.

### 6.2. `UnmappedMemberValidation` по умолчанию выключен — Принято

Переименованный член (`FullName` в source, `Name` в destination) или забытое
правило оставляют destination-член пустым без предупреждения. В маппинге
Entity → DTO destination обычно подмножество source, и проверка destination
почти не шумит. В DTO → Entity она перечисляет члены, которые маппинг не
трогает, и это полезно для Update. Проверка source шумит для DTO с лишними
полями.

Варианты:

- по умолчанию `Destination`: `MORPH0048` как warning, проверка source остаётся
  opt-in, член с предупреждением 6.1 второго не получает. Новые предупреждения
  в существующих проектах ломают сборку только при `TreatWarningsAsErrors`;
- оставить `None`.

Как поступают другие мапперы (по их документации, проверено 2026-11-19):

| Маппер | Вид | Несмапленный destination | Несмапленный source |
|---|---|---|---|
| Mapperly | C#, compile-time | warning `RMG012` | warning `RMG020` |
| MapStruct | Java, compile-time | `WARN` | `IGNORE` |
| AutoMapper | C#, runtime | молча; opt-in `AssertConfigurationIsValid` проверяет destination | только с `MemberList.Source` |
| Mapster | C#, runtime | молча; opt-in `RequireDestinationMemberSource` и `Compile()` | не проверяется |

Compile-time мапперы по умолчанию предупреждают о несмапленном destination;
runtime-мапперы молчат при маппинге, но их проверка, если её включить, по
умолчанию тоже смотрит на destination. `Destination` по умолчанию совпадает с
MapStruct и мягче Mapperly; `None` слабее всех compile-time аналогов. Шум
ограничивают `Ignore()`, настройки маппинга, маппера и сборки и severity в
`.editorconfig`.

**Решение.** Первый вариант: `Destination` по умолчанию, только warning. Смену
значения по умолчанию отметить в changelog вместе с настройкой, которая
возвращает прежнее поведение.

### 6.3. Конвенции не запускают вложенный маппинг — Отложено

Для члена другого типа нужно писать `X = Map()`, а коллекции не маппятся
совсем. После 1.1 генератор знает пары текущего маппера, и конвенция могла бы
использовать их детерминированно и видимо в сгенерированном коде, как
AutoMapper использует зарегистрированные карты. Но это меняет
документированный принцип «вложенный маппинг всегда явный» и должно быть
согласовано с first-class коллекциями: маппинг элементов использует те же
пары.

Предложение ревью: отложить и решать вместе с first-class коллекциями; до тех
пор предупреждение 6.1 подсказывает `Map()`.

**Решение.** Отложено до first-class поддержки коллекций: без неё задачу не
решить согласованно. Вернуться к ней обязательно.

## 7. Create/Update и вложенные маппинги

Сильные стороны: две явные операции с общим API; Update возвращает результат
и может заменить destination; `previous` и `result` разделяют исходный и
выбранный destination; адаптивный `Map()` сохраняет идентичность уже
существующих вложенных объектов, а `Create` и `Update` выбирают операцию явно;
read-only члены обновляются на месте; `MappingMode` ограничивает операции
маппинга.

### 7.1. Update молча пропускает creation-only члены — Не проблема

Проверено генератором (2026-11-19) с `MappingMode` по умолчанию:

- для `record Person(string Name)` Update возвращает destination без
  изменений: `mapper.Map(dto, person)` ничего не делает;
- для класса с `init`-членом явное правило `Code = source.Code.ToUpper()`
  применяется при Create и молча пропускается при Update.

Документация говорит, что при переиспользовании creation-only члены сохраняют
значения, а автоматическая реконструкция immutable Update указана в
ограничениях. Но в коде маппинга нет никакого сигнала, что правило или весь
Update не действует.

Варианты:

- реконструкция immutable Update: если маппинг задаёт creation-only члены,
  Update строит замену, а параметр конструктора без правила получает значение
  одноимённого члена `previous` (для record — как `with`). Снимает ограничение
  и делает Update осмысленным для immutable-типов; это отдельная функция;
- warning, если Update включён, а явное правило `Members` задаёт
  creation-only член. Исправление — `MappingMode.Create`, замена в `Resolve`
  или удаление правила. Для record-DTO с `MappingMode` по умолчанию шумит на
  каждом явном правиле;
- оставить и описать в документации.

Первоначальное предложение ревью — первый вариант как целевой дизайн.

**Как поступают другие мапперы (исследование 2026-11-19).**

| Маппер | Update и init-only/immutable destination | Как объявляется Update |
|---|---|---|
| AutoMapper | `Map(source, destination)` меняет переданный объект и возвращает его. Член считается записываемым по `PropertyInfo.CanWrite` без особой обработки `init` (исходники `ReflectionHelper`), поэтому init-свойства record-а, судя по коду, меняются на месте через reflection | доступен для каждой карты |
| Mapperly | existing-target метод `void Map(source, target)` меняет объект на месте; сгенерированный C# не может присвоить init-член существующему объекту. Диагностика required/init-членов в таких методах менялась в 4.1.1 и 4.2.0; точное текущее поведение по документации не подтверждено | отдельный метод, объявляемый пользователем |
| MapStruct | `@MappingTarget` меняет объект на месте; член без setter-а — несмапленный target (`WARN` по умолчанию) | отдельный метод, объявляемый пользователем |

Выводы:

- привычная модель Update — изменение переданного объекта на месте.
  AutoMapper ради неё нарушает immutability, Mapperly и MapStruct
  ограничиваются тем, что можно изменить, и сообщают о несмапленном;
- молча пустого Update нет ни у кого, кроме ограничений, о которых сообщает
  диагностика;
- автоматическая реконструкция противоречит этой модели: Update вернёт новый
  объект, а пользователи по привычке `mapper.Map(dto, entity);` результат не
  сохраняют, и предупреждение 2.3 этот случай не ловит. Поэтому
  реконструкцию лучше не делать поведением по умолчанию;
- в Mapperly и MapStruct Update объявляется явно, поэтому диагностика о
  creation-only членах касается только Update-методов. В Morphant Update
  включён для каждой пары, и такая диагностика шумела бы на каждом record-DTO.

**Пересмотренное предложение ревью.** Явный отказ вместо молчаливого no-op,
без нового шума:

- если у destination нет членов, которые Update может изменить на месте, а
  маппинг не выбирает замену (`Resolve`, `ResolveUsing`, `Convert`), Update
  бросает `MappingOperationNotSupportedException` с объяснением; явный
  `MappingMode` с Update для такого маппинга — ошибка при компиляции;
- если такие члены есть, Update меняет их, а явное правило `Members` для
  creation-only члена при включённом Update даёт warning;
- реконструкция остаётся явной через `Resolve`; отдельный opt-in можно
  рассмотреть позже.

**Решение.** Оставить как сейчас. Update единообразно меняет то, что можно
изменить после конструирования, и для mutable, и для immutable типов:
creation-only члены сохраняют значения, а полностью immutable destination
возвращается без изменений. Запрет Update заставил бы настраивать `Resolve` для
каждого immutable-типа. Когда нужна замена, пользователь настраивает `Resolve`
сам. Поведение открыто: его видно в сгенерированном коде в IDE и в snapshot
`MorphantGitSnapshot`, а руководство по тестированию советует проверять Update
отдельно.

В руководстве Create/Update одним предложением сказать, что для
immutable-типа Update возвращает объект без изменений, а замену выбирает
`Resolve`.

### 7.2. Адаптивный `Map()` при Create вызывает вложенный Update — Принято

По контракту `Map()` для writable-члена созданного результата передаёт текущее
значение во вложенный Update, даже если оно `null`. Проверено генератором и
запуском (2026-11-19):

- вложенная пара с `MappingMode.Create`: сгенерированный внешний Create
  вызывает `Map(source.Address, destination: result.Address)` и для
  инициализированного члена, и для `null`-члена — во время выполнения это
  `MappingOperationNotSupportedException`, при компиляции диагностики нет;
- вложенный immutable-тип, который внешний тип инициализирует
  (`AddressRecord Address { get; set; } = new("")`): вложенный Update
  возвращает пустой объект без изменений, и Create молча теряет данные —
  запуск дал `City=''` вместо `City='Paris'`.

Варианты:

- после 1.1 — ошибка при компиляции, если вложенный вызов пары текущего
  маппера требует операции, выключенной её `MappingMode`. Исправление —
  `Create(...)` или включение Update. Потерю данных для immutable-типов
  устраняет реконструкция из 7.1;
- адаптивный `Map()` выбирает Create для `null`-члена. Снимает ловушку
  `MappingMode` для `null`-членов, но вложенная пара теряет возможность
  отклонить `null` через `NullDestinationHandling.Throw`; относится к пункту 8;
- оставить и описать в документации.

Первоначальное предложение ревью — первый вариант вместе с реконструкцией из
7.1.

**Как поступают другие мапперы (исследование 2026-11-19).**

- AutoMapper (исходники `TypeMapPlanBuilder.DestinationMemberValue`): если
  внешний destination передан (Update), во вложенную карту передаётся текущее
  значение члена, и непустой вложенный объект обновляется на месте, а `null`
  заменяется новым. Если внешний destination создаётся (Create), передаётся
  `default`, и вложенный объект создаётся заново, даже если конструктор
  внешнего типа его уже инициализировал. Исключения — read-only член и
  `UseDestinationValue()`;
- Mapperly: в existing-target маппинге вложенный объект всегда создаётся
  заново. Пользователи просят обновлять его на месте — открытый запрос
  [#1311](https://github.com/riok/mapperly/issues/1311) с дубликатами
  [#1484](https://github.com/riok/mapperly/issues/1484) и
  [#1865](https://github.com/riok/mapperly/issues/1865): замена вложенных
  сущностей ломает отслеживание изменений EF Core;
- у AutoMapper 5.x были такие же вопросы о вложенных объектах и EF
  (Stack Overflow, 2016); когда поведение изменилось, не установлено.

Выводы: пользователи ожидают, что Update обновляет существующие вложенные
объекты на месте, — текущий Morphant это делает, в отличие от Mapperly. Для
Create привычная модель AutoMapper — вложенный объект создаётся; Morphant же
передаёт во вложенный Update значение, подготовленное конструктором внешнего
типа, отсюда обе ловушки.

**Пересмотренное предложение ревью.** Адаптивный `Map()` следует тому, откуда
взят внешний destination:

- существующий destination (Update с переиспользованием) — вложенный Update
  текущего значения на месте;
- новый destination (Create, Update с `null`, замена из `Resolve`) —
  вложенный Create, даже если конструктор или фабрика уже заполнили член;
  обновить подготовленное значение можно явным `Update(source.X, result.X)`;
- read-only члены по-прежнему обновляются на месте;
- после 1.1 вложенный вызов пары текущего маппера, требующий выключенной
  `MappingMode` операции, — ошибка при компиляции.

Правило объясняется одной фразой, совпадает с AutoMapper и снимает обе
ловушки без реконструкции. Поведение `null`-члена при Update относится к
пункту 8.

**Обсуждение (2026-11-19).** Выбрасывать экземпляр, подготовленный
конструктором или фабрикой, неинтуитивно: фабрика могла подготовить его
намеренно. Поэтому текущая модель сохраняется — `Map()` обновляет
подготовленное значение. По решению 7.1 вложенный Update меняет только то, что
изменяемо после конструирования, и проблема сужается до двух случаев:

- вложенная пара не поддерживает Update (`MappingMode.Create`) — исключение во
  время выполнения;
- правила вложенной пары задают creation-only члены, которые Update изменить
  не может, — данные source теряются.

**Предложение ревью (третья редакция).** Поведение не меняется,
неоднозначность становится явной:

- после 1.1 — ошибка при компиляции, если вложенный вызов пары текущего
  маппера требует операции, выключенной её `MappingMode`. Исправление —
  `Create(...)` или включение Update;
- warning при внешнем Create, если адаптивный `Map()` передаёт значение
  writable-члена во вложенный Update пары текущего маппера, чьи правила задают
  creation-only члены вложенного destination. Исправление — `Create(...)`,
  чтобы заменить значение, или явный `Update(...)`, чтобы сознательно оставить
  подготовленный экземпляр. Если значение во время выполнения `null`,
  `Create(...)` даёт тот же результат, поэтому исправление безопасно;
- для пар других мапперов, найденных через DI, генератор этого не знает;
  поведение описывается в документации.

**Решение.** Третья редакция: поведение адаптивного `Map()` не меняется,
ошибка `MappingMode` и warning о creation-only членах вложенной пары делают
неоднозначность явной.
