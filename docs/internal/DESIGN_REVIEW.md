решения описывают будущую реализацию, а не текущее поведение; по итогам ревью

## 1. Объявление маппера, подключение и вызов

Сильные стороны: маппер — обычный класс с внедрением зависимостей через
конструктор; `ITypeMapper<TSource, TDestination>` — типизированный контракт,
который можно реализовать вручную; ошибки объявления подробно диагностируются;
атрибут `[MorphantMapper]` даёт быстрый поиск мапперов в генераторе и отличает
конечный маппер от переиспользуемой базы.

### 1.1. Вложенные вызовы всегда идут через DI — Принято

Сгенерированный код вызывает любой вложенный `Map`/`Create`/`Update` через
`context.Mapper`, то есть через `IServiceProvider`, даже если пара объявлена в
том же маппере. Последствия:

- вложенный маппинг выполняет ту конфигурацию пары, которая зарегистрирована в
  DI, а не ту, что объявлена в этом маппере; при одной паре в двух мапперах
  результат зависит от DI-композиции или даёт `AmbiguousMappingException`;
- standalone-вызов через `ITypeMapper` ищет вложенную пару в том же маппере,
  то есть один маппер ведёт себя по-разному в зависимости от способа вызова;
- каждую вложенную пару приходится регистрировать в DI;
- каждый вложенный вызов — поиск в контейнере, перечисление и аллокации,
  в коллекциях — на каждый элемент.

**Решение.** Пара, объявленная в том же маппере (включая конфигурацию,
подключённую через `base.Configure`), вызывается напрямую. Через `IMapper`
идут только пары, которых в маппере нет.

### 1.2. Ручная регистрация каждой пары в DI — Отложено

Каждая пара регистрируется отдельной строкой; новая пара без регистрации
проявляется только `MappingNotFoundException` во время выполнения. Варианты,
рассмотренные в ревью:

- композитный `IMapper` над набором мапперов (`new Mapper(mapperA, mapperB)`):
  регистрируются мапперы, а не пары; работает и без DI;
- сгенерированное расширение `services.AddXxxMapper()` при ссылке на
  `Microsoft.Extensions.DependencyInjection.Abstractions`;
- одна сгенерированная регистрация всех мапперов сборки.

Тема регистрации в DI отложена до завершения основных функций.

### 1.3. Нет ранней проверки регистраций — Отложено

Генератор знает внешние пары, нужные каждому мапперу, и может выдать данные
для проверки при старте без рефлексии. Отложено вместе с 1.2.

### 1.4. Забытый `[MorphantMapper]` не диагностируется — Принято

Генератор находит мапперы только по атрибуту, анализаторов нет. Без атрибута
голый `Map` компилируется без результата, а `.Members(...)` даёт
вводящую в заблуждение `CS1061`.

Пользовательский сценарий, при котором неабстрактный наследник `TypeMapper`
не должен генерироваться, найден один: наследник уже сгенерированного маппера
(например, тестовый двойник). Он получает реализацию от базы.

**Решение.** Добавить диагностику: неабстрактный класс, производный от
`TypeMapper`, без `[MorphantMapper]` у него и у всех базовых классов. Исправление —
добавить атрибут или сделать класс `abstract`. Открыто: severity (предлагается
warning, поскольку это допустимый C#).

### 1.5. Два способа вызова — Не проблема (DI-часть отложена)

`IMapper.Map` намеренно упрощён под привычную по другим мапперам модель;
`ITypeMapper` конкретнее и разделяет операции `Create` и `Update`. Разные
глаголы на разных уровнях не считаем проблемой. Двухаргументный generic Create
(`Map<TSource, TDestination>(source)`) рассматривается в пункте 2.

Невозможность межмапперных вызовов без DI и сложность quick start относятся
к регистрации и отложены вместе с 1.2.

### 1.6. Время жизни мапперов не объяснено — Отложено

Документация везде использует `AddScoped` без объяснения. Маппер без
зависимостей можно сделать singleton, а scoped `IMapper` нельзя внедрить в
singleton. Отложено вместе с 1.2.

### 1.7. DSL-методы вызываются вне конфигурации — Принято при условии

`Map`, `Create`, `Update`, `Auto`, `Ignore`, `Value`, `ByConvention` — это
`protected static` члены `TypeMapper`; методы билдеров и сгенерированные
расширения доступны как обычные методы. Вызов вне `Configure` компилируется
и бросает `RuntimeInvocationNotSupportedException` во время выполнения.

**Решение.** Добавить анализатор, если он надёжен, прост и дёшев. Оценка
ревью:

- целевые методы определяются по символу (содержащий тип — `TypeMapper<>`,
  `MapperBuilderBase<>`, `MappingBuilder<,,>` или сгенерированный класс
  расширений), без эвристик по именам;
- проверка — operation action на вызов и ссылку на метод с подъёмом до
  содержащего метода; допустим только override `TypeMapper.Configure`, включая
  вложенные лямбды; некорректные позиции внутри `Configure` по-прежнему
  диагностирует генератор (`MORPH0033`);
- стоимость: сравнение символов на каждый вызов, без состояния на всю
  компиляцию; поддерживается конкурентное выполнение;
- анализатор поставляется в том же пакете и может использоваться также для 1.4.

Открыто: новый ID или `MORPH0033`.

### 1.8. CRTP `TypeMapper<TSelf>` — Открыто

**Происхождение.** Self-тип появился в 0.5.0 вместе с кортежами. C# стирает
имена элементов кортежа, nullable-аннотации и различие `dynamic`/`object` из
CLR-идентичности типа, но они влияют на конвенции и типы callback-ов. Две
регистрации одной CLR-пары с разным представлением требуют разных
сгенерированных расширений `Members`/`Construct` на одном и том же receiver,
что ведёт к конфликту. Первая реализация кортежей диагностировала такие
конфликты (`MORPH0056`) и откладывала mapper scope как редкий escape hatch.
Затем scope по мапперу стал обязательным для всех мапперов: receiver
`MappingBuilder<TMapper, TSource, TDestination>` и расширения,
специализированные для каждого маппера.

**Что даёт CRTP:**

- одна CLR-пара с разными именами элементов кортежа или аннотациями в разных
  мапперах одной сборки;
- независимые поверхности для пересекающихся открытых generic-пар в
  несвязанных семействах мапперов;
- отсутствие конфликтов с внутренними расширениями другой сборки, видимыми
  через `InternalsVisibleTo`.

**Чего стоит CRTP:**

- для пользователя: повтор имени класса в `TypeMapper<ApplicationMapper>`;
  для переиспользуемой базы — рекурсивное ограничение
  `where TMapper : CommonMapper<TMapper>`; длинные типы в IntelliSense и
  ошибках;
- новые ограничения, порождённые scope: `MORPH0058` (неверный self-тип),
  `MORPH0060` (каждый параметр семейства обязан входить в каждую пару),
  требование доступности маппера для namespace-level кода (`MORPH0059`);
- для генератора: расширения на каждую пару каждого маппера вместо одного
  набора на пару, вычисление scope семейств, общая поверхность для
  пересекающихся базовых и производных scope.

**Оценка ревью.** Выгода касается редкого сценария: одна CLR-пара с разным
представлением в разных мапперах одной сборки. Цена ложится на каждого
пользователя с первой строки и на каждую будущую функцию генератора. CRTP
того не стоит.

**Предлагаемый компромисс.**

- Вернуть необобщённый базовый класс `TypeMapper` и общую для сборки поверхность
  на каждую CLR-пару.
- Внутри сборки у CLR-пары одно представление: имена элементов кортежей,
  вложенные nullable-аннотации и `dynamic` должны совпадать у всех мапперов.
  Расхождение — `MORPH0056` с исправлением «используйте те же имена или
  отдельный DTO».
- Обычные кортежи остаются полноценными: несколько входов, несколько выходов,
  данные вызова, конвенции по именам элементов в одном представлении.
- Открытые generic-пары получают generic-расширения по своим параметрам;
  неоднозначное пересечение несвязанных открытых пар диагностируется.
- Видимые через `InternalsVisibleTo` расширения другой сборки для той же пары
  диагностируются вместо неоднозначности `CS0121`.
- Отдельный opt-in scope маппера не добавляется: два стиля объявления
  усложнили бы дизайн. К нему можно вернуться, если реальное использование
  покажет потребность.

Изменение ломает API 0.5.0; миграция механическая — убрать self-тип и
рекурсивные ограничения.

Открыто: принять компромисс; считать ли верхнеуровневую nullable-аннотацию
source/destination частью представления (тогда `Map<Source?, D>` и
`Map<Source, D>` в разных мапперах конфликтуют) или нормализовать её.
