## 1. Объявление маппера, подключение и вызов

Сильные стороны: маппер — обычный класс с внедрением зависимостей через
конструктор; `ITypeMapper<TSource, TDestination>` — типизированный контракт,
который можно реализовать вручную; ошибки объявления подробно диагностируются;
атрибут `[MorphantMapper]` даёт быстрый поиск мапперов в генераторе и отличает
конечный маппер от переиспользуемой базы.

### 1.1. Вложенные вызовы всегда идут через DI — Принято

Сгенерированный код вызывает любой вложенный `Map`/`Create`/`Update` через
`context.Mapper`, то есть через `IServiceProvider`, даже если пара объявлена в
том же маппере. Последствия:

- вложенный маппинг выполняет ту конфигурацию пары, которая зарегистрирована в
  DI, а не ту, что объявлена в этом маппере; при одной паре в двух мапперах
  результат зависит от DI-композиции или даёт `AmbiguousMappingException`;
- standalone-вызов через `ITypeMapper` ищет вложенную пару в том же маппере,
  то есть один маппер ведёт себя по-разному в зависимости от способа вызова;
- каждую вложенную пару приходится регистрировать в DI;
- каждый вложенный вызов — поиск в контейнере, перечисление и аллокации,
  в коллекциях — на каждый элемент.

**Решение.** Пара, которую реализует тот же маппер, вызывается напрямую. Через
`IMapper` идут только пары, которых маппер не реализует. Пары базового
маппера, подключённые через `base.Configure`, сейчас доступны только для
`IncludeBase` и не реализуются производным маппером; их статус решается в
пункте 9.

### 1.2. Ручная регистрация каждой пары в DI — Отложено

Каждая пара регистрируется отдельной строкой; новая пара без регистрации
проявляется только `MappingNotFoundException` во время выполнения. Варианты,
рассмотренные в ревью:

- композитный `IMapper` над набором мапперов (`new Mapper(mapperA, mapperB)`):
  регистрируются мапперы, а не пары; работает и без DI;
- сгенерированное расширение `services.AddXxxMapper()` при ссылке на
  `Microsoft.Extensions.DependencyInjection.Abstractions`;
- одна сгенерированная регистрация всех мапперов сборки.

Тема регистрации в DI отложена до завершения основных функций.

### 1.3. Нет ранней проверки регистраций — Отложено

Генератор знает внешние пары, нужные каждому мапперу, и может выдать данные
для проверки при старте без рефлексии. Отложено вместе с 1.2.

### 1.4. Забытый `[MorphantMapper]` не диагностируется — Принято

Генератор находит мапперы только по атрибуту, анализаторов нет. Без атрибута
голый `Map` компилируется без результата, а `.Members(...)` даёт
вводящую в заблуждение `CS1061`.

Пользовательский сценарий, при котором неабстрактный наследник `TypeMapper`
не должен генерироваться, найден один: наследник уже сгенерированного маппера
(например, тестовый двойник). Он получает реализацию от базы.

**Решение.** Добавить ошибку с отдельным ID: неабстрактный класс, производный
от `TypeMapper`, без `[MorphantMapper]` у него и у всех базовых классов.
Исправление — добавить атрибут или сделать класс `abstract`.

Error, а не warning: единственный законный сценарий исключён правилом, других
не найдено, исправление тривиально. Все правила Morphant, кроме предупреждений
о полноте маппинга (`MORPH0047`, `MORPH0048`), — ошибки. При ложном
срабатывании severity понижается через `.editorconfig`.

### 1.5. Два способа вызова — Не проблема (DI-часть отложена)

`IMapper.Map` намеренно упрощён под привычную по другим мапперам модель;
`ITypeMapper` конкретнее и разделяет операции `Create` и `Update`. Разные
глаголы на разных уровнях не считаем проблемой. Двухаргументный generic Create
(`Map<TSource, TDestination>(source)`) рассматривается в пункте 2.

Невозможность межмапперных вызовов без DI и сложность quick start относятся
к регистрации и отложены вместе с 1.2.

### 1.6. Время жизни мапперов не объяснено — Отложено

Документация везде использует `AddScoped` без объяснения. Маппер без
зависимостей можно сделать singleton, а scoped `IMapper` нельзя внедрить в
singleton. Отложено вместе с 1.2.

### 1.7. DSL-методы вызываются вне конфигурации — Принято при условии

`Map`, `Create`, `Update`, `Auto`, `Ignore`, `Value`, `ByConvention` — это
`protected static` члены `TypeMapper`; методы билдеров и сгенерированные
расширения доступны как обычные методы. Вызов вне `Configure` компилируется
и бросает `RuntimeInvocationNotSupportedException` во время выполнения.

**Решение.** Добавить анализатор, если он надёжен, прост и дёшев. Оценка
ревью:

- целевые методы определяются по символу (содержащий тип — `TypeMapper<>`,
  `MapperBuilderBase<>`, `MappingBuilder<,,>` или сгенерированный класс
  расширений), без эвристик по именам;
- проверка — operation action на вызов и ссылку на метод с подъёмом до
  содержащего метода; допустим только override `TypeMapper.Configure`, включая
  вложенные лямбды; некорректные позиции внутри `Configure` по-прежнему
  диагностирует генератор (`MORPH0033`);
- стоимость: сравнение символов на каждый вызов, без состояния на всю
  компиляцию; поддерживается конкурентное выполнение;
- анализатор поставляется в том же пакете и может использоваться также для 1.4.

Правило получает отдельный ID, а не `MORPH0033`. У них разные причина и
исправление: `MORPH0033` — API в неподдерживаемой позиции внутри конфигурации,
новое правило — вызов вне `Configure`, который бросит исключение во время
выполнения. Их выдают разные компоненты, и severity каждого настраивается
отдельно. Правило покрывает DSL-хелперы `TypeMapper`, методы билдеров и
настроек и сгенерированные расширения. Номера новых ID назначаются при
реализации.

### 1.8. CRTP `TypeMapper<TSelf>` — Принято

**Происхождение.** Self-тип появился в 0.5.0 вместе с кортежами. C# стирает
имена элементов кортежа, nullable-аннотации и различие `dynamic`/`object` из
CLR-идентичности типа, но они влияют на конвенции и типы callback-ов. Две
регистрации одной CLR-пары с разным представлением требуют разных
сгенерированных расширений `Members`/`Construct` на одном и том же receiver,
что ведёт к конфликту. Первая реализация кортежей диагностировала такие
конфликты (`MORPH0056`) и откладывала mapper scope как редкий escape hatch.
Затем scope по мапперу стал обязательным для всех мапперов: receiver
`MappingBuilder<TMapper, TSource, TDestination>` и расширения,
специализированные для каждого маппера.

**Что даёт CRTP:**

- одна CLR-пара с разными именами элементов кортежа или аннотациями в разных
  мапперах одной сборки;
- независимые поверхности для пересекающихся открытых generic-пар в
  несвязанных семействах мапперов;
- отсутствие конфликтов с внутренними расширениями другой сборки, видимыми
  через `InternalsVisibleTo`.

**Чего стоит CRTP:**

- для пользователя: повтор имени класса в `TypeMapper<ApplicationMapper>`;
  для переиспользуемой базы — рекурсивное ограничение
  `where TMapper : CommonMapper<TMapper>`; длинные типы в IntelliSense и
  ошибках;
- новые ограничения, порождённые scope: `MORPH0058` (неверный self-тип),
  `MORPH0060` (каждый параметр семейства обязан входить в каждую пару),
  требование доступности маппера для namespace-level кода (`MORPH0059`);
- для генератора: расширения на каждую пару каждого маппера вместо одного
  набора на пару, вычисление scope семейств, общая поверхность для
  пересекающихся базовых и производных scope.

**Оценка ревью.** Выгода касается редкого сценария: одна CLR-пара с разным
представлением в разных мапперах одной сборки. Цена ложится на каждого
пользователя с первой строки и на каждую будущую функцию генератора. CRTP
того не стоит.

**Решение — компромисс.**

- Вернуть необобщённый базовый класс `TypeMapper` и общую для сборки поверхность
  на каждую CLR-пару.
- Внутри сборки у CLR-пары одно представление: имена элементов кортежей,
  вложенные nullable-аннотации и `dynamic` должны совпадать у всех мапперов.
  Расхождение — `MORPH0056` с исправлением «используйте те же имена или
  отдельный DTO». Верхнеуровневые аннотации в представление не входят (см.
  ниже).
- Обычные кортежи остаются полноценными: несколько входов, несколько выходов,
  данные вызова, конвенции по именам элементов в одном представлении.
- Открытые generic-пары получают generic-расширения по своим параметрам;
  неоднозначное пересечение несвязанных открытых пар диагностируется.
- Видимые через `InternalsVisibleTo` расширения другой сборки для той же пары
  диагностируются вместо неоднозначности `CS0121`.
- Отдельный opt-in scope маппера не добавляется: два стиля объявления
  усложнили бы дизайн. К нему можно вернуться, если реальное использование
  покажет потребность.

`MORPH0058` и ограничение `MORPH0060` уходят; требование доступности
`MORPH0059` пересматривается. Изменение ломает API 0.5.0; миграция
механическая — убрать self-тип и рекурсивные ограничения.

**Верхнеуровневые nullable-аннотации нормализуются.** Аннотация ссылочного типа
на верхнем уровне source и destination не входит в представление пары:
`Map<Source?, Destination?>` и `Map<Source, Destination>` — одна пара в любом
маппере сборки. Сейчас аннотация source на сгенерированные сигнатуры не влияет,
а аннотация destination определяет тип возврата `Convert`, `ConstructUsing` и
`ResolveUsing` и аннотацию реализуемого `ITypeMapper<,>`. После нормализации
генератор выдаёт одну форму независимо от записи.

Это соответствует текущему runtime API и модели AutoMapper: аннотацию
результата выбирает вызывающий через `TDestination`, а null handling от
аннотаций не зависит. В документации явно указать, что результат маппинга и callback-ов
может быть `null`; каноническое место — раздел о nullability результата на
странице null handling. `Nullable<T>` значимых типов — отдельный CLR-тип и не
нормализуется; вложенные аннотации входят в представление, как и прежде.

Нормализованная форма:

- `Convert`, `ConstructUsing` и `ResolveUsing` возвращают `Destination?`:
  `null` — их документированный результат, а при `Destination` он требовал бы
  `null!`. Предупреждение о случайном `null` теряется; возврат `null` из
  DSL-лямбды редок;
- параметры source не меняются: `Source` для декларативных и `Using`-callback-ов,
  `Source?` для `Convert`;
- маппер реализует `ITypeMapper<Source, Destination>` без аннотаций —
  обычную форму регистрации в DI.

## 2. Runtime API и модель вызова

Сильные стороны: небольшой типизированный API; поиск только точной пары
`ITypeMapper<TSource, TDestination>`, без подстановки базовых типов и без
зависимости от порядка регистрации; Update возвращает результат, что
поддерживает замену destination и значимые типы; исключения несут операцию и
типы пары, а исключения пользовательского кода не оборачиваются; данные вызова
передаются типизированно через кортеж-source; использование `context.Mapper`
после завершения вызова обнаруживается.

### 2.1. Create требует обоих аргументов типа — Отложено

C# не выводит часть аргументов типа, поэтому в `mapper.Map<OrderDto, Order>(dto)`
source повторяется, хотя известен из аргумента. Особенно длинно для кортежей и
generic-типов:

```csharp
var dto = mapper.Map<
    (Order Order, Customer Customer, decimal TaxRate),
    OrderDto>((order, customer, taxRate));
```

Внутри DSL source выводится (`Map<Address>(source.Address)`), в runtime-коде и
в callback-ах через `context.Mapper` — нет.

Варианты:

- оставить: пара видна на месте вызова;
- добавить расширение `mapper.From(source).To<TDestination>()`. Source —
  статический тип выражения, как при любом выводе типов C#. Вызов делегирует
  `Map<TSource, TDestination>`, поэтому моки `IMapper` не меняются. Имя `From`,
  а не `Map`, чтобы незавершённый вызов не выглядел результатом:
  `return Ok(mapper.Map(dto))` сериализовал бы промежуточный объект;
- сделать такую форму единственной: теряются method group
  (`Select(context.Mapper.Map<OrderDto, Order>)`) и простые моки.

Предложение ревью — второй вариант. Расширения для упрощения работы с маппером
запланированы, но отложены до реализации основных функций, включая
first-class поддержку коллекций, с которой они могут быть связаны.

### 2.2. `context.Mapper` не следует решению 1.1 — Принято

Обычные callback-и (`Convert`, `ConstructUsing`, `ResolveUsing`) вызывают
вложенные маппинги только через `context.Mapper`, а он всегда ищет пару в DI.
После 1.1 в одном маппере `Map<Address>(...)` в `Members` выполнит
собственную пару напрямую, а `context.Mapper.Map<AddressDto, Address>(...)` в
`Convert` — пару из DI, возможно чужую. Для пользовательского кода регистрация
собственных пар остаётся обязательной. В standalone-режиме `context.Mapper` уже
ищет пару в текущем маппере.

**Решение.** Одно правило для всех вложенных вызовов, сгенерированных и
пользовательских: пару, объявленную в текущем маппере, выполняет сам маппер,
остальные идут в `IMapper` приложения.

### 2.3. Результат Update можно молча потерять — Принято при условии

`mapper.Map(dto, order);` компилируется, но результат теряется, когда Update
возвращает не переданный объект:

- `order` равен `null`, а `NullDestinationHandling` по умолчанию `Create`:
  созданный объект выбрасывается, upsert молча ничего не делает;
- `Resolve`, `ResolveUsing` или `Convert` вернули замену;
- destination — значимый тип: изменённая копия теряется всегда.

Документация требует всегда сохранять результат, но компилятор не помогает.

Варианты:

- предупреждение анализатора на любой отброшенный результат Update
  (`IMapper.Map(source, destination)`, `ITypeMapper.Update`, расширение
  `Update`); явный `_ =` его снимает. Совпадает с документированным правилом и
  ловит все три случая; шум для in-place обновления, исправление тривиально;
- предупреждение только для значимых destination: без ложных срабатываний, но
  `null` и замену не ловит;
- только документация, как сейчас.

**Решение.** Warning только там, где потеря результата известна на месте
вызова, если диагностика проста и дешева. Оценка ревью:

- достоверных случаев два: destination известного значимого типа (включая
  `Nullable<T>` и параметр типа с ограничением `struct`) и destination —
  константа `null` или `default`;
- `null` в переменной и замена через `Resolve`, `ResolveUsing` или `Convert`
  не диагностируются: на месте вызова через `IMapper` это не известно;
- у значимого destination ссылочные объекты, обновлённые вложенным Update на
  месте, сохраняют изменения, но изменения самого значения теряются;
  предупреждение говорит именно о потере возвращённого значения;
- проверка — operation action на вызов в позиции expression statement:
  сравнение символа метода (`IMapper.Map(source, destination)`,
  `ITypeMapper.Update`, расширение `Update`), признак значимого типа у
  аргумента типа и константное значение аргумента. Без анализа потока данных и
  состояния на компиляцию; общая инфраструктура с анализатором 1.7.

Условие выполнено.

### 2.4. В `MappingContext` нет пользовательского состояния — Отложено

Аналога `Items` из AutoMapper нет. Данные вызова передаются типизированно через
кортеж-source, окружение запроса — через зависимости маппера. Цена: данные,
нужные глубоко во вложенном маппинге, приходится протаскивать через кортежи
промежуточных пар. Нетипизированный словарь противоречит типизированному DSL;
типизированный контекст — новая сущность с вопросами времени жизни и передачи
во вложенные вызовы.

Предложение ревью: не проблема. Отложено до реальной потребности.

### 2.5. Поиск в DI на каждый вызов — Отложено

Каждый вызов через `IMapper` разрешает `IEnumerable<ITypeMapper<,>>` и
перебирает его, чтобы отличить 0, 1 и 2+ регистраций; это аллокации на каждый
вызов. После 1.1 это касается только верхнеуровневых вызовов и пар других
мапперов. Неоднозначность — ошибка конфигурации, которую дешевле проверить один
раз (1.3).

Работа над производительностью этого места запланирована и отложена ради более
приоритетных функций.

## 3. Философия DSL: обычный C# против C#-подобного декларативного языка

Сильные стороны: конфигурация — типизированный C# с IntelliSense,
переименованием, переходом к определению и ошибками типов, без строк и
`nameof`; правила членов записываются одним object initializer-ом в форме
результата; пользовательские выражения, locals и ветви переносятся в
сгенерированный код с сохранением структуры, отдельно написанные выражения
вычисляются отдельно, а результат можно посмотреть; `Using`-callback-и и
`Convert` — явный выход в обычный C#; нарушения правил DSL диагностируются при
компиляции.

Цена подхода: код выглядит как C#, но это диалект. `Configure` не
выполняется, лямбды — шаблоны, а вместо реальных типов стоят
`Member<T>`, `ConstructorParameter<T>` и сгенерированные типы конструирования.
Неожиданности возникают на границе между C# и диалектом.

### 3.1. `Member<T>` и `ConstructorParameter<T>` принимают не всё — Отложено

Обёртки принимают значения через пользовательские implicit-конвертации, а C#
применяет их не всегда. Проверено компиляцией копии обёрток с теми же
операторами (2026-11-18):

| Значение | Результат |
|---|---|
| Значение интерфейсного типа, включая результат LINQ (`IEnumerable<T>`), даже в член того же интерфейса или `object` | `CS0029`: конвертации из интерфейсов не рассматриваются |
| Лямбда, method group | `CS1660`, `CS0428` |
| Collection expression | `CS9174` |
| Target-typed `new() { ... }` | Связывается с `Member<T>`: `CS0122`, `CS0117` |
| Обычные классы, массивы, числа, `null`, кортежные литералы, `switch` | Работают; nullability сохраняется |

Например, `Names = source.Items.Select(item => item.Name)` для члена
`IEnumerable<string>` не компилируется. Исправление — `Value<T>(...)` или явный
тип, но ошибка компилятора говорит о внутреннем `Member<T>`, а документация
упоминает `Value<T>` только для точного типа и collection expressions.

Варианты:

- оставить обёртки; добавить code fix «обернуть в `Value<T>`» для этих ошибок
  компилятора на цели DSL и перечислить случаи в каноническом разделе
  `Value<T>`. DSL не меняется. Code fix требует отдельной сборки в пакете:
  генератор и анализатор не должны ссылаться на Workspaces;
- сопровождать ошибку компилятора диагностикой Morphant с объяснением: две
  ошибки на одно место, хуже code fix;
- перепроектировать поверхности так, чтобы значения связывались без
  пользовательских конвертаций: реальные типы членов и маркеры через `dynamic`
  или явные generic-маркеры. Убирает класс проблем, но `dynamic` отключает
  проверку типов вокруг маркеров и требует `Microsoft.CSharp`, а явные маркеры
  удлиняют каждый `Auto()`.

**Решение.** Первый вариант: DSL не меняется, code fix «обернуть в
`Value<T>`» добавляется позже. Сейчас отложено.

### 3.2. `new(...)` в `Construct` и `Resolve` — не конструктор destination — Отложено

`new(source.Id)` создаёт сгенерированный `OrderConstruction`, а
`new Order(source.Id)` — `MORPH0062`. В смешанном условном выражении `Resolve`
C# выводит `new(...)` как `Order`, поэтому приходится писать имя
сгенерированного типа:
`previous.HasValue ? previous.Value : new OrderConstruction(source.Id)`.

Тип конструирования вынужден: маркеры как аргументы и required/init-члены,
заданные в `Members`, нельзя выразить через `new Order(...)` (для required-членов
это `CS9035`). `MORPH0062` объясняет исправление, форма `if`/`return` работает
без имени типа.

**Решение.** Дизайн не меняется. Смешанное условное выражение исправляется
code fix-ом, который заменяет `new(...)` на явный тип конструирования.
Отложено вместе с 3.1.

### 3.3. `Configure` выглядит как код, но является декларацией — Принято

`Configure` не выполняется: locals из него нельзя захватывать (кроме
констант), регистрации нельзя делать условно или в цикле, builder нельзя
сохранить или передать во вспомогательный метод. Обычные приёмы C#, включая
рефакторинг «Extract method», дают диагностику. Переиспользование идёт через
механизмы Morphant (пункт 9).

Это свойство compile-time подхода, и нарушения диагностируются. Но quick start
не говорит, что `Configure` не выполняется; это сказано только в руководстве
по декларативному маппингу.

**Решение.** Дизайн не меняется. В quick start добавить одно предложение о
том, что `Configure` читается генератором и не выполняется, со ссылкой на
правила.

### 3.4. Два вида callback-ов — Не проблема

Декларативные `Construct`, `Resolve`, `Members` (inline-лямбды, маркеры,
вложенный `Map`) и обычные `ConstructUsing`, `ResolveUsing`, `Convert`
(делегаты, `context.Mapper`) различаются правилами. Граница последовательна:
суффикс `Using` и `Convert` означают обычный C#. После 2.2 вложенные вызовы в
обоих видах подчиняются одному правилу; остаётся многословность
`context.Mapper.Map<TSource, TDestination>`, отложенная в 2.1.

## 4. Выбор способа создания destination

Сильные стороны: способы создания образуют систему 2×2: декларативные
`Construct` и `Resolve` против обычных `ConstructUsing` и `ResolveUsing`;
`Construct*` работают только без destination, `Resolve*` — на каждом Create и
Update. Суффикс `Using` последовательно означает обычный C#, `Convert` — полный
выход. Выбор конструктора не откатывается молча к другому конструктору, а
ничьи считаются ошибкой. `ByConvention()` переопределяет отдельные параметры, не
отказываясь от конвенции. `null` из фабрики — документированный окончательный
результат. Interface и abstract destination создаются фабрикой, а Update-only
маппинг работает без неё.

### 4.1. Шесть стратегий `ConstructorSelection` — Не проблема

`Explicit`, `Parameterless`, `Single`, `Unambiguous` (по умолчанию),
`Greediest`, `Largest`. Различия тонкие:

- `Single` отличается от `Unambiguous` только при одновременном наличии
  конструктора без параметров и одного параметризованного: ошибка вместо
  выбора параметризованного;
- `Largest` отличается от `Greediest` только тогда, когда самый большой
  конструктор нельзя вызвать: ошибка вместо выбора меньшего.

Каждую стратегию нужно документировать, тестировать и понимать, а сценарии
для `Single` и `Largest` в истории проекта не описаны: стратегии вводились
набором. Строгость, которую они дают, доступна через `Explicit` и явный
`Construct`.

Варианты:

- оставить шесть стратегий;
- оставить `Explicit`, `Parameterless`, `Unambiguous` и `Greediest`, убрать
  `Single` и `Largest`. Ломающее изменение до 1.0.

Предложение ревью было — второй вариант. **Решение:** оставить все стратегии.
Они опциональны и не усложняют путь по умолчанию; пользователь выбирает
подходящую.

### 4.2. `previous` — `Option<Destination>`, а не `Destination?` — Не проблема

`Resolve`, `Members`, `ResolveUsing` и `Convert` получают `previous` как
`Option<Destination>`. Обычный C# ожидал бы `Destination?` с `is { }` и `??`.

`Option` одинаково работает для ссылочных и значимых типов и в обобщённых
делегатах runtime API, где `T?` для неограниченного `T` не различает
отсутствие значения. Он никогда не содержит `null`, а его члены знакомы:
`HasValue` и `Value` — как у `Nullable<T>`, `TryGetValue` — как у словарей.
Форма `previous ?? new(source.Id)` не помогла бы и с `Destination?`: C# вывел
бы `new(...)` как destination (3.2).

Единая работа со ссылочными и значимыми типами — назначение `Option`; его
наличие оправдано.

## 5. Members: порядок вычислений и связь с конструктором

Сильные стороны: явный аргумент конструктора и правило члена ведут себя как
`new D(x) { P = y }` — оба вычисляются, initializer применяется после
конструктора. Правило члена задаёт и соответствующий автоматический аргумент
конструктора, поэтому у record-ов одно место настройки и одно вычисление.
Отдельно написанные выражения не объединяются. Правила, читающие `result`,
видят исходное состояние, поэтому обмен значениями работает; при этом
текстовый порядок вычислений сохраняется — проверено на сгенерированном коде
текущего `main` (2026-11-19). `Ignore()` для параметра конструктора опускает
только optional-параметр, для обязательного — ошибка `MORPH0037`.

### 5.1. `Ignore()` в `Members` не действует на автоматический аргумент конструктора — Принято

Значение и `Auto()` в `Members` передаются в связанный автоматический параметр
конструктора, а `Ignore()` — нет: параметр получает значение по конвенции.
Проверено генератором (2026-11-19):

```csharp
public sealed record OptionalPerson(string Name = "none");

builder.Map<PersonSource, OptionalPerson>()
    .Members(source => new() { Name = Ignore() });
// Create: new OptionalPerson(Name: source.Name); Update: без изменений.
```

Для settable-члена такое `Ignore()` осмысленно: Create задаёт значение через
конструктор, Update не перезаписывает его. Но для creation-only члена (init
или позиционного), который получает значение из автоматического параметра,
правило не действует ни в одной операции: Create берёт конвенцию, а Update
такой член не меняет. Пользователь видит «игнорировать», а значение
маппится. Диагностики нет; документация говорит лишь, что `Ignore()` действует
только там, где написан.

Варианты:

- ошибка, если `Ignore()` в `Members` не действует ни в одной включённой
  операции: член creation-only и получает значение из автоматического
  параметра конструктора. Исправление — правило для параметра в `Construct`
  (`ByConvention()` и `Ignore()` для optional-параметра) или удаление правила.
  Ложных срабатываний нет; ошибка, а не warning, по аналогии с явной
  настройкой без эффекта (`MORPH0023`);
- распространять `Ignore()` на связанный параметр: optional опускается,
  обязательный — ошибка;
- оставить и описать в документации.

Текущее поведение соответствует контракту: `Ignore()` действует только там,
где написан (`docs/api/members.md`, правило `Ignore()` каждой позиции в
`GENERATOR_CONTRACTS.md`). Поэтому это изменение контракта, а не исправление
ошибки генерации.

Поскольку `Members` воспринимается как свойства, применение его правил к
конструктору может быть неинтуитивным. Связь значений и `Auto()` с
автоматическим параметром конструктора уже существует, поэтому вопрос шире
`Ignore()`. Целостных моделей две:

- модель значений (текущая для значений и `Auto()`): правило `Members` задаёт
  значение члена, а Morphant передаёт его через автоматический конструктор или
  setter. Для record-а с переименованным свойством достаточно `Members`,
  значение вычисляется и записывается один раз. Цена: конструктор, который
  преобразует параметр, меняет и записанное значение, а связь определяется по
  имени и в IntelliSense не видна;
- модель initializer-а: `Members` — только присваивания после
  конструирования, а автоматический конструктор получает значения только по
  конвенции. Совпадает с буквальным чтением `new D(...) { Name = x }`, и
  текущее `Ignore()` в ней последовательно. Цена: record без одноимённого
  члена source не создать без `Construct`, а позиционное свойство
  записывается дважды — конструктором по конвенции и initializer-ом.

Неожиданность 5.1 возникает из смешения моделей.

**Решение.** Модель значений целиком, включая `Ignore()`: она богаче и удобнее.
`Ignore()` означает «игнорировать» и действует на связанный автоматический
параметр так же, как значение и `Auto()`:

- optional-параметр опускается и получает значение по умолчанию; setter не
  вызывается, Update член не перезаписывает;
- обязательный параметр без значения делает конструктор неприменимым, как
  любой параметр без значения. `Greediest` выбирает лучший из оставшихся
  применимых конструкторов; `Single`, `Unambiguous` и `Largest` не
  откатываются и выдают ошибку, если выбранный конструктор содержит такой
  параметр. Исправление — явный аргумент в `Construct` или удаление правила.
  У `Parameterless` связанных параметров нет;
- явное правило параметра в `Construct` не связано с правилом члена. Поэтому
  сценарий settable-члена «задать при создании, не перезаписывать при Update»
  выражается как `Construct(source => new(source.Name))` вместе с
  `Name = Ignore()`.

Связь сделать видимой: в IntelliSense члена поверхности `Members` указать, что
при автоматическом конструкторе значение передаётся в одноимённый параметр, а
в руководстве по `Members` сказать это одним предложением до таблицы. Обновить
контракт в `docs/api/members.md` и `GENERATOR_CONTRACTS.md`.

## 6. Конвенции

Сильные стороны: конвенции строгие и предсказуемые — точное имя и неявная
конверсия C# без предупреждений, без нормализации имён. У flattening явный
порядок приоритета, неоднозначность — ошибка `MORPH0051`, а nullable-путь даёт
`null`, а не выдуманное значение. `IncludeMembers` подключает вложенный source
явно; `MemberSelection.Explicit` и `Auto()` включают конвенцию точечно.

### 6.1. Совпавший по имени член молча не маппится — Принято

Проверено генератором с настройками по умолчанию (2026-11-19). Маппинг
`OrderDto -> Order`, где у каждого члена destination есть source-член с тем же
именем:

| Source | Destination | Почему конвенция не применяется |
|---|---|---|
| `string? Name` | `string Name` | предупреждение nullability |
| `int? Count` | `int Count` | нет неявной конверсии |
| `long Total` | `int Total` | нет неявной конверсии |
| `AddressDto Address` | `Address Address` | конвенция не запускает вложенный маппинг |
| `List<ItemDto> Items` | `List<Item> Items` | элементы коллекций не маппятся |
| `string code` | `string Code` | имена членов сравниваются с учётом регистра |

Сгенерированный Create — `new Order()`, Update возвращает destination без
изменений, диагностик нет: `UnmappedMemberValidation` по умолчанию `None`.
Совпадение имени — явный признак намерения, но результат молча пустой.

Варианты:

- warning по умолчанию, независимый от `UnmappedMemberValidation`: у
  destination-члена есть source-член с тем же именем (с точностью до регистра)
  или flattened-путь, но конвенция не может его использовать. Сообщение
  называет причину и исправление: `Map()`, явное выражение или `Ignore()`;
  явное правило снимает предупреждение;
- добавить причину в сообщение `MORPH0048`: при проверке, выключенной по
  умолчанию, ничего не изменится;
- оставить как есть.

**Решение.** Первый вариант: добавить предупреждение.

### 6.2. `UnmappedMemberValidation` по умолчанию выключен — Принято

Переименованный член (`FullName` в source, `Name` в destination) или забытое
правило оставляют destination-член пустым без предупреждения. В маппинге
Entity → DTO destination обычно подмножество source, и проверка destination
почти не шумит. В DTO → Entity она перечисляет члены, которые маппинг не
трогает, и это полезно для Update. Проверка source шумит для DTO с лишними
полями.

Варианты:

- по умолчанию `Destination`: `MORPH0048` как warning, проверка source остаётся
  opt-in, член с предупреждением 6.1 второго не получает. Новые предупреждения
  в существующих проектах ломают сборку только при `TreatWarningsAsErrors`;
- оставить `None`.

Как поступают другие мапперы (по их документации, проверено 2026-11-19):

| Маппер | Вид | Несмапленный destination | Несмапленный source |
|---|---|---|---|
| Mapperly | C#, compile-time | warning `RMG012` | warning `RMG020` |
| MapStruct | Java, compile-time | `WARN` | `IGNORE` |
| AutoMapper | C#, runtime | молча; opt-in `AssertConfigurationIsValid` проверяет destination | только с `MemberList.Source` |
| Mapster | C#, runtime | молча; opt-in `RequireDestinationMemberSource` и `Compile()` | не проверяется |

Compile-time мапперы по умолчанию предупреждают о несмапленном destination;
runtime-мапперы молчат при маппинге, но их проверка, если её включить, по
умолчанию тоже смотрит на destination. `Destination` по умолчанию совпадает с
MapStruct и мягче Mapperly; `None` слабее всех compile-time аналогов. Шум
ограничивают `Ignore()`, настройки маппинга, маппера и сборки и severity в
`.editorconfig`.

**Решение.** Первый вариант: `Destination` по умолчанию, только warning. Смену
значения по умолчанию отметить в changelog вместе с настройкой, которая
возвращает прежнее поведение.

### 6.3. Конвенции не запускают вложенный маппинг — Отложено

Для члена другого типа нужно писать `X = Map()`, а коллекции не маппятся
совсем. После 1.1 генератор знает пары текущего маппера, и конвенция могла бы
использовать их детерминированно и видимо в сгенерированном коде, как
AutoMapper использует зарегистрированные карты. Но это меняет
документированный принцип «вложенный маппинг всегда явный» и должно быть
согласовано с first-class коллекциями: маппинг элементов использует те же
пары.

Предложение ревью: отложить и решать вместе с first-class коллекциями; до тех
пор предупреждение 6.1 подсказывает `Map()`.

**Решение.** Отложено до first-class поддержки коллекций: без неё задачу не
решить согласованно. Вернуться к ней обязательно.

## 7. Create/Update и вложенные маппинги

Сильные стороны: две явные операции с общим API; Update возвращает результат
и может заменить destination; `previous` и `result` разделяют исходный и
выбранный destination; адаптивный `Map()` сохраняет идентичность уже
существующих вложенных объектов, а `Create` и `Update` выбирают операцию явно;
read-only члены обновляются на месте; `MappingMode` ограничивает операции
маппинга.

### 7.1. Update молча пропускает creation-only члены — Не проблема

Проверено генератором (2026-11-19) с `MappingMode` по умолчанию:

- для `record Person(string Name)` Update возвращает destination без
  изменений: `mapper.Map(dto, person)` ничего не делает;
- для класса с `init`-членом явное правило `Code = source.Code.ToUpper()`
  применяется при Create и молча пропускается при Update.

Документация говорит, что при переиспользовании creation-only члены сохраняют
значения, а автоматическая реконструкция immutable Update указана в
ограничениях. Но в коде маппинга нет никакого сигнала, что правило или весь
Update не действует.

Варианты:

- реконструкция immutable Update: если маппинг задаёт creation-only члены,
  Update строит замену, а параметр конструктора без правила получает значение
  одноимённого члена `previous` (для record — как `with`). Снимает ограничение
  и делает Update осмысленным для immutable-типов; это отдельная функция;
- warning, если Update включён, а явное правило `Members` задаёт
  creation-only член. Исправление — `MappingMode.Create`, замена в `Resolve`
  или удаление правила. Для record-DTO с `MappingMode` по умолчанию шумит на
  каждом явном правиле;
- оставить и описать в документации.

Первоначальное предложение ревью — первый вариант как целевой дизайн.

**Как поступают другие мапперы (исследование 2026-11-19).**

| Маппер | Update и init-only/immutable destination | Как объявляется Update |
|---|---|---|
| AutoMapper | `Map(source, destination)` меняет переданный объект и возвращает его. Член считается записываемым по `PropertyInfo.CanWrite` без особой обработки `init` (исходники `ReflectionHelper`), поэтому init-свойства record-а, судя по коду, меняются на месте через reflection | доступен для каждой карты |
| Mapperly | existing-target метод `void Map(source, target)` меняет объект на месте; сгенерированный C# не может присвоить init-член существующему объекту. Диагностика required/init-членов в таких методах менялась в 4.1.1 и 4.2.0; точное текущее поведение по документации не подтверждено | отдельный метод, объявляемый пользователем |
| MapStruct | `@MappingTarget` меняет объект на месте; член без setter-а — несмапленный target (`WARN` по умолчанию) | отдельный метод, объявляемый пользователем |

Выводы:

- привычная модель Update — изменение переданного объекта на месте.
  AutoMapper ради неё нарушает immutability, Mapperly и MapStruct
  ограничиваются тем, что можно изменить, и сообщают о несмапленном;
- молча пустого Update нет ни у кого, кроме ограничений, о которых сообщает
  диагностика;
- автоматическая реконструкция противоречит этой модели: Update вернёт новый
  объект, а пользователи по привычке `mapper.Map(dto, entity);` результат не
  сохраняют, и предупреждение 2.3 этот случай не ловит. Поэтому
  реконструкцию лучше не делать поведением по умолчанию;
- в Mapperly и MapStruct Update объявляется явно, поэтому диагностика о
  creation-only членах касается только Update-методов. В Morphant Update
  включён для каждой пары, и такая диагностика шумела бы на каждом record-DTO.

**Пересмотренное предложение ревью.** Явный отказ вместо молчаливого no-op,
без нового шума:

- если у destination нет членов, которые Update может изменить на месте, а
  маппинг не выбирает замену (`Resolve`, `ResolveUsing`, `Convert`), Update
  бросает `MappingOperationNotSupportedException` с объяснением; явный
  `MappingMode` с Update для такого маппинга — ошибка при компиляции;
- если такие члены есть, Update меняет их, а явное правило `Members` для
  creation-only члена при включённом Update даёт warning;
- реконструкция остаётся явной через `Resolve`; отдельный opt-in можно
  рассмотреть позже.

**Решение.** Оставить как сейчас. Update единообразно меняет то, что можно
изменить после конструирования, и для mutable, и для immutable типов:
creation-only члены сохраняют значения, а полностью immutable destination
возвращается без изменений. Запрет Update заставил бы настраивать `Resolve` для
каждого immutable-типа. Когда нужна замена, пользователь настраивает `Resolve`
сам. Поведение открыто: его видно в сгенерированном коде в IDE и в snapshot
`MorphantGitSnapshot`, а руководство по тестированию советует проверять Update
отдельно.

В руководстве Create/Update одним предложением сказать, что для
immutable-типа Update возвращает объект без изменений, а замену выбирает
`Resolve`.

### 7.2. Адаптивный `Map()` при Create вызывает вложенный Update — Принято

По контракту `Map()` для writable-члена созданного результата передаёт текущее
значение во вложенный Update, даже если оно `null`. Проверено генератором и
запуском (2026-11-19):

- вложенная пара с `MappingMode.Create`: сгенерированный внешний Create
  вызывает `Map(source.Address, destination: result.Address)` и для
  инициализированного члена, и для `null`-члена — во время выполнения это
  `MappingOperationNotSupportedException`, при компиляции диагностики нет;
- вложенный immutable-тип, который внешний тип инициализирует
  (`AddressRecord Address { get; set; } = new("")`): вложенный Update
  возвращает пустой объект без изменений, и Create молча теряет данные —
  запуск дал `City=''` вместо `City='Paris'`.

Варианты:

- после 1.1 — ошибка при компиляции, если вложенный вызов пары текущего
  маппера требует операции, выключенной её `MappingMode`. Исправление —
  `Create(...)` или включение Update. Потерю данных для immutable-типов
  устраняет реконструкция из 7.1;
- адаптивный `Map()` выбирает Create для `null`-члена. Снимает ловушку
  `MappingMode` для `null`-членов, но вложенная пара теряет возможность
  отклонить `null` через `NullDestinationHandling.Throw`; относится к пункту 8;
- оставить и описать в документации.

Первоначальное предложение ревью — первый вариант вместе с реконструкцией из
7.1.

**Как поступают другие мапперы (исследование 2026-11-19).**

- AutoMapper (исходники `TypeMapPlanBuilder.DestinationMemberValue`): если
  внешний destination передан (Update), во вложенную карту передаётся текущее
  значение члена, и непустой вложенный объект обновляется на месте, а `null`
  заменяется новым. Если внешний destination создаётся (Create), передаётся
  `default`, и вложенный объект создаётся заново, даже если конструктор
  внешнего типа его уже инициализировал. Исключения — read-only член и
  `UseDestinationValue()`;
- Mapperly: в existing-target маппинге вложенный объект всегда создаётся
  заново. Пользователи просят обновлять его на месте — открытый запрос
  [#1311](https://github.com/riok/mapperly/issues/1311) с дубликатами
  [#1484](https://github.com/riok/mapperly/issues/1484) и
  [#1865](https://github.com/riok/mapperly/issues/1865): замена вложенных
  сущностей ломает отслеживание изменений EF Core;
- у AutoMapper 5.x были такие же вопросы о вложенных объектах и EF
  (Stack Overflow, 2016); когда поведение изменилось, не установлено.

Выводы: пользователи ожидают, что Update обновляет существующие вложенные
объекты на месте, — текущий Morphant это делает, в отличие от Mapperly. Для
Create привычная модель AutoMapper — вложенный объект создаётся; Morphant же
передаёт во вложенный Update значение, подготовленное конструктором внешнего
типа, отсюда обе ловушки.

**Пересмотренное предложение ревью.** Адаптивный `Map()` следует тому, откуда
взят внешний destination:

- существующий destination (Update с переиспользованием) — вложенный Update
  текущего значения на месте;
- новый destination (Create, Update с `null`, замена из `Resolve`) —
  вложенный Create, даже если конструктор или фабрика уже заполнили член;
  обновить подготовленное значение можно явным `Update(source.X, result.X)`;
- read-only члены по-прежнему обновляются на месте;
- после 1.1 вложенный вызов пары текущего маппера, требующий выключенной
  `MappingMode` операции, — ошибка при компиляции.

Правило объясняется одной фразой, совпадает с AutoMapper и снимает обе
ловушки без реконструкции. Поведение `null`-члена при Update относится к
пункту 8.

**Обсуждение (2026-11-19).** Выбрасывать экземпляр, подготовленный
конструктором или фабрикой, неинтуитивно: фабрика могла подготовить его
намеренно. Поэтому текущая модель сохраняется — `Map()` обновляет
подготовленное значение. По решению 7.1 вложенный Update меняет только то, что
изменяемо после конструирования, и проблема сужается до двух случаев:

- вложенная пара не поддерживает Update (`MappingMode.Create`) — исключение во
  время выполнения;
- правила вложенной пары задают creation-only члены, которые Update изменить
  не может, — данные source теряются.

**Предложение ревью (третья редакция).** Поведение не меняется,
неоднозначность становится явной:

- после 1.1 — ошибка при компиляции, если вложенный вызов пары текущего
  маппера требует операции, выключенной её `MappingMode`. Исправление —
  `Create(...)` или включение Update;
- warning при внешнем Create, если адаптивный `Map()` передаёт значение
  writable-члена во вложенный Update пары текущего маппера, чьи правила задают
  creation-only члены вложенного destination. Исправление — `Create(...)`,
  чтобы заменить значение, или явный `Update(...)`, чтобы сознательно оставить
  подготовленный экземпляр. Если значение во время выполнения `null`,
  `Create(...)` даёт тот же результат, поэтому исправление безопасно;
- для пар других мапперов, найденных через DI, генератор этого не знает;
  поведение описывается в документации.

**Решение.** Третья редакция: поведение адаптивного `Map()` не меняется,
ошибка `MappingMode` и warning о creation-only членах вложенной пары делают
неоднозначность явной.

### 7.3. Read-only член требует имени сгенерированного типа из хешированного namespace — Принято

Найдено 2026-11-19 при проверке хелперов. Для get-only reference-члена,
обновляемого на месте, документирована только форма-инструкция:

```csharp
.Members((source, _) =>
{
    var members = new OrderMembers { Name = source.Name };
    Update(source.Address, members.Address);
    return members;
});
```

`OrderMembers` лежит в `Morphant.Generated.N_<hash>`, и документация просит
импортировать namespace, который покажет IDE. Пользовательский код зависит от
хеша сгенерированного namespace, а форма выбивается из обычного
initializer-а. `Address = Map()` для такого члена даёт `CS0200`: свойство
поверхности только для чтения (проверено генератором).

Предложение ревью: у члена, который можно обновить только на месте, свойство
поверхности `Members` получает setter, а `Address = Map()` (и явный
`Update(...)`) для него означает вложенный Update текущего значения на месте с
отбрасыванием результата — как в форме-инструкции и в адаптивной модели 7.2.
Форма-инструкция и имя сгенерированного типа в пользовательском коде больше не
нужны.

**Обсуждение (2026-11-19).** Setter у поверхности сейчас не добавлен намеренно:
чтобы не возникал вопрос, почему в модели член только для чтения, а DSL
разрешает запись. Подходы:

| Подход | Плюсы | Минусы |
|---|---|---|
| A. Как сейчас: `new OrderMembers { ... }` и `Update(source.Address, members.Address)` | честно по C#: read-only член только читается | имя сгенерированного типа из `Morphant.Generated.N_<hash>` в пользовательском коде; форма-инструкция вместо initializer-а |
| B. Setter и `Address = Map()` | единый initializer, без имён сгенерированных типов | выглядит как присваивание read-only члену; разрешены только маркеры `Map`/`Update`/`Ignore`, значение — ошибка, это особый случай. Частичный прецедент в C#: вложенный initializer `Address = { City = ... }` допустим для get-only свойства и заполняет существующий объект, но он записывается в фигурных скобках |
| C. `Update(source.Address, result.Address)` в теле `Members` | честно по C#: существующий объект результата обновляется, член читается; без имён сгенерированных типов | statement-лямбда с параметром `result`; член обновляется вне initializer-а. Сейчас это `MORPH0046`: генератору нужно определять член по обращению к `result` |

Пересмотренное предложение ревью: вариант C. Он сохраняет модель read-only
члена, читается как обычный C# («обновить существующий `Address` результата»)
и убирает хешированный namespace. B остаётся альтернативой, если важнее единый
initializer.

**Решение.** Вариант B. Обоснование:

- в `Members` знак `=` уже означает правило для члена, а не буквальное
  присваивание: `LegacyCode = Ignore()` ничего не присваивает;
- C# допускает get-only член в initializer-е: `Address = { City = ... }` и
  `Items = { 1, 2 }` заполняют существующий объект (проверено компиляцией
  2026-11-19). `Members` похож на initializer, поэтому read-only член в нём
  естественен.

Уточнения:

- у члена, который можно обновить только на месте, свойство поверхности
  `Members` получает setter; IntelliSense-описание свойства говорит, что
  `Map()` обновляет существующее значение на месте, а `Ignore()` оставляет его;
- допустимы `Map()` в своих формах и `Ignore()`; значение или `Create(...)`
  — ошибка Morphant с объяснением, что read-only член нельзя заменить, вместо
  `CS0200`;
- семантика прежняя: при `null` текущем значении вложенный вызов
  пропускается, результат вложенного Update отбрасывается;
- форма-инструкция с `new OrderMembers` и импортом хешированного namespace
  удаляется.

Вложенный initializer `Address = { City = source.Address.City }` как способ
задать правила вложенного объекта прямо в `Members` — отдельная идея, не
входящая в решение.

## 8. Null-семантика

Сильные стороны: null source и null destination настраиваются раздельно, с
понятными значениями и `Throw` для строгих сценариев. Flattening через
nullable-путь даёт `null`, а не выдуманное значение. Конвенция не использует
конверсии с предупреждением nullability. `Convert` сам отвечает за `null`.
Patch/merge-политика для `null`-значений исследована и отложена
(`NULL_ASSIGNMENT_HANDLING_RESEARCH.md`).

### 8.1. Update с `null` source по умолчанию возвращает `null` — Принято

`NullSourceHandling` по умолчанию `ReturnNull`, поэтому и Update возвращает
`default`. Проверено запуском (2026-11-19): `Update(null, existing)` вернул
`null`. Документированный шаблон `order = mapper.Map(dto, order)` при
`dto == null` теряет ссылку на существующий объект.

Как поступают другие: AutoMapper (`ExpressionBuilder.NullCheckSource`) при
`null` source и переданном destination возвращает этот destination
(коллекцию — очищенной); Mapperly для existing-target в документации этот
случай не описывает.

Варианты:

- по умолчанию `ReturnDestination`: Create возвращает `default`, Update —
  переданный destination. Вложенный Update с `null` source тоже оставляет
  текущее значение члена; очистить член можно явно:
  `Address = source.Address is null ? null : Map()`. Эта форма работает, но
  даёт ложное `CS8604` про `Member<Address?>` — ещё один случай 3.1. Смену
  значения по умолчанию отметить в changelog;
- оставить `ReturnNull` и подчеркнуть в документации.

Первоначальное предложение ревью — первый вариант.

**Как поступают другие мапперы (исследование 2026-11-19).**

| Маппер | Update с `null` source на верхнем уровне |
|---|---|
| AutoMapper | возвращает переданный destination, коллекцию — очищенной (`ExpressionBuilder.NullCheckSource`) |
| MapStruct | update-метод с типом возврата с 1.5.0.Beta2 всегда возвращает target; раньше возвращал `null`, и смену объявили ломающим изменением. `void` update-метод при `null` source просто выходит |
| Mapperly | existing-target метод `void`, ссылка вызывающего не теряется; обработка `null` source в документации не описана |
| Morphant | возвращает `null` |

На верхнем уровне ожидание однозначно: Update без данных оставляет destination
как есть. MapStruct пришёл к этому, отказавшись от поведения, которое сейчас у
Morphant.

Для вложенного члена при Update ожидания расходятся. AutoMapper при `null`
вложенном source по умолчанию записывает в член `null`; Mapperly записывает
`null` в nullable-член и пропускает присваивание для non-nullable. Пользователи
просят и очистку ([Mapperly #1163](https://www.github.com/riok/mapperly/discussions/1163)),
и сохранение значения для patch-сценариев
([AutoMapper #4627](https://github.com/LuckyPennySoftware/AutoMapper/issues/4627)).
В Morphant одна настройка пары управляет и верхним уровнем, и вложенным
`Map()`, поэтому `ReturnDestination` по умолчанию оставляет вложенный член без
изменений: nullable-член не очищается, хотя AutoMapper и Mapperly его очищают.

Варианты:

- `ReturnDestination` по умолчанию. Одно правило в духе 7.1: Update с `null`
  source нечего применить, destination не меняется — и на верхнем уровне, и
  для вложенного члена. Скаляр `Name = source.Name` по-прежнему получает
  `null`: это значение, а не пропущенный маппинг. Очистку вложенного члена
  задают явно — `ReturnNull` на вложенной паре или условием в `Members`.
  Ломающее изменение значения по умолчанию, отметить в changelog;
- оставить `ReturnNull` (очистка вложенных членов как в AutoMapper) и описать
  ловушку верхнего уровня в документации;
- разные значения для верхнего уровня и вложенного `Map()`: поведение зависит
  от места вызова, правило сложнее объяснить.

**Решение.** Первый вариант, на усмотрение ревью: `ReturnDestination` по
умолчанию. Цена — расхождение с AutoMapper и Mapperly для nullable вложенного
члена при Update. В changelog отметить смену значения по умолчанию и
настройку, которая возвращает прежнее поведение.

### 8.2. Вложенный `Map()` молча записывает `null` в non-nullable член — Принято

Проверено запуском (2026-11-19): при `null` вложенном source `Map()` записал
`null` в non-nullable член `Address Address { get; set; } = new()`, заменив
подготовленный экземпляр. Предупреждений нет ни для source `AddressDto?`, ни
для non-nullable source, равного `null` во время выполнения. Конвенция при этом
отказывается от конверсии `string?` в `string`, так что поведение
непоследовательно.

Как поступают другие: AutoMapper по умолчанию записывает `null`
(`AllowNullDestinationValues`); Mapperly для nullable source и non-nullable
target-свойства по умолчанию пропускает присваивание, а с
`ThrowOnPropertyMappingNullMismatch` бросает `ArgumentNullException`.

Варианты:

- warning nullability, если вложенный source по NRT может быть `null`, а
  член non-nullable; не выдаётся, если вложенная пара текущего маппера
  использует `NullSourceHandling.Throw`. Исправление — nullable-член, `Throw`,
  `source.Address is null ? Ignore() : Map()` или явное значение по умолчанию;
- как Mapperly, молча пропускать присваивание при `null` source для
  non-nullable члена. Скрытое поведение, и для required/init-членов
  неприменимо;
- оставить.

**Решение.** Первый вариант: warning nullability. Source, non-nullable по
аннотации, но `null` во время выполнения — нарушение NRT на стороне
пользователя, его не диагностируем.

### 8.3. `ReturnNull` для значимого типа возвращает `default` — Не проблема

Название говорит `null`, а для non-nullable значимого destination результат —
нулевое значение. Это описано в документации; destination обычно ссылочный.

Очевидное имя `ReturnDefault` конфликтует с членом `Default = 0`, который во
всех перечислениях настроек означает «наследовать». Варианты:

- `ReturnDefault` вместе с переименованием наследующего члена `Default` в
  `Inherit` во всех перечислениях настроек. Точнее и убирает двусмысленность
  `MappingMode.Default` («режим по умолчанию» или «наследовать»), но
  затрагивает всю систему настроек — решается в пункте 11;
- `ReturnNullOrDefault`: точно и без конфликтов, но длинно;
- оставить `ReturnNull`.

**Решение.** Оставить `ReturnNull`. Двусмысленность наследующего члена
`Default` можно рассмотреть отдельно в пункте 11.

## 9. Переиспользование конфигурации

Сильные стороны: механизмы явные. `base.Configure(builder)` подключает
настройки базового маппера, `IncludeBase` переиспользует правила одной пары.
Локальные правила заменяют унаследованные по членам, остальные сохраняются.
`IncludeBase` не переносит `ForDerived`: маршрутизация и переиспользование
независимы. Правила членов можно разделять через базовые типы и интерфейсы.
Ошибки подключения диагностируются (`MORPH0024`–`MORPH0028`). Рекурсивное
ограничение базового маппера уходит вместе с CRTP (1.8).

### 9.1. Пары базового маппера недоступны производному — Принято

Пара, объявленная в базовом маппере и подключённая через `base.Configure`,
не реализуется производным маппером и доступна только для `IncludeBase`.
Проверено генератором и запуском (2026-11-19): `Price = Map()` для пары
`Money -> MoneyDto` из базового маппера компилируется без диагностики и во
время выполнения бросает `MappingNotFoundException`. По C#-интуиции
наследник получает поведение базы, а `base.Configure` читается как «включить
конфигурацию базы». Это и есть вопрос, отложенный в 1.1.

Варианты:

- пары базового маппера становятся парами производного, как если бы были
  объявлены в нём: реализуются, вызываются напрямую по 1.1. Так уже работают
  пары-шаблоны для `IncludeBase`, объявленные в том же маппере: они
  обязаны быть валидными самостоятельно. Цена: шаблоны в базовом маппере,
  невалидные как самостоятельная пара (например, abstract destination без
  фабрики), начнут давать ошибки — ломающее изменение; несколько конечных
  мапперов с общей базой реализуют одну пару, что важно для регистрации в DI
  (1.2);
- пары базового маппера доступны производному только для вложенных вызовов
  напрямую и генерируются при использовании, но не становятся его публичными
  `ITypeMapper`. Без дублирования в DI, но вводит понятие «внутренней» пары;
- оставить и диагностировать вложенный вызов пары, объявленной только в
  подключённом базовом маппере.

Первоначальное предложение ревью — первый вариант.

**Обсуждение (2026-11-19).** Модель целостна: абстрактная база — это
конфигурация (настройки и шаблоны для `IncludeBase`), а реализованные пары
даёт конечный маппер. Если пара базы должна участвовать в маппинге, база
делается самостоятельным маппером. Конкретные риски текущего подхода:

- вложенный `Map()` к паре, которая видна в коде только в базе, компилируется
  и идёт через `IMapper`: без регистрации — `MappingNotFoundException` во
  время выполнения, а с регистрацией другого маппера выполняется его
  конфигурация, а не правила базы, которые пользователь видит. Генератор знает,
  что пара здесь только шаблон, но молчит;
- путь «сделать базу самостоятельным маппером и унаследоваться от неё» сейчас
  закрыт: генерируемый маппер, производный от генерируемого, даёт `MORPH0058`
  из-за CRTP (проверено 2026-11-19). После 1.8 он становится возможным, но его
  контракт не определён: считаются ли унаследованные реализованные пары
  собственными для прямых вызовов из 1.1. Композиция — отдельный маппер пары,
  найденный через `IMapper`, — работает и сейчас.

**Пересмотренное предложение ревью.**

- модель не меняется: пары абстрактной базы — шаблоны;
- определить контракт после 1.8: генерируемый маппер может наследоваться от
  генерируемого, а унаследованные реализованные пары считаются его парами для
  прямых вложенных вызовов (1.1);
- warning, если вложенный вызов идёт к паре, которая в подключённой
  абстрактной базе объявлена только как шаблон и не реализована текущим
  маппером. Исправление — объявить пару в маппере (с `IncludeBase`), сделать
  базу самостоятельным маппером или подавить предупреждение, если пару
  намеренно реализует другой маппер.

**Решение.** Пересмотренное предложение ревью.

### 9.2. Повторное объявление пары базы молча отбрасывает её правила — Принято

Проверено генератором и запуском (2026-11-19): производный маппер вызывает
`base.Configure` и объявляет ту же пару `Map<Money, MoneyDto>()` без
`IncludeBase`. Правило базы `Currency = source.Currency.ToUpperInvariant()`
не применяется: результат `Currency=usd`. Диагностики нет; пользователь может
и не знать, что база объявляет эту пару.

Варианты:

- повторное объявление пары, подключённой из базы, расширяет её, как
  `IncludeBase` той же пары: локальные правила заменяют унаследованные по
  членам. Согласуется с 9.1 (пары базы — пары производного) и с тем, что
  `base.Configure` наследует настройки автоматически. Полная замена
  выражается локальными правилами или `Convert`;
- ошибка или warning: повторное объявление без `IncludeBase` той же пары.
  Явно, но для намеренной замены нет синтаксиса, кроме подавления;
- оставить.

Первоначальное предложение ревью — первый вариант.

**Ожидания пользователя (2026-11-19).** Молчаливой замены не ждёт никто:

- C#: член производного класса, скрывающий член базы без `new`, даёт
  предупреждение `CS0108`; замена разрешена, но должна быть явной;
- AutoMapper: одна пара в нескольких профилях — по умолчанию
  `DuplicateTypeMapConfigurationException`; слияние включается явно через
  `AllowAdditiveTypeMapCreation`;
- в модели 9.1 шаблоны базы подключаются явно через `IncludeBase`;
  автоматическое расширение сделало бы ту же пару исключением из этого
  правила.

**Пересмотренное предложение ревью.** Warning по аналогии с `CS0108`: пара в
производном маппере скрывает конфигурацию той же пары из подключённой базы.
Исправление — `IncludeBase<TSource, TDestination>()`, чтобы переиспользовать
её правила; намеренную замену подтверждает подавление предупреждения.

**Решение.** Пересмотренное предложение ревью.

## 10. Полиморфизм

Сильные стороны: ветви перечисляются явно (`ForDerived`), без сканирования
типов; выбирается единственная самая специфичная ветвь, порядок регистрации
не влияет, неоднозначность — исключение; ограничения `ForDerived` проверяют
совместимость типов при компиляции. Маршрутизация (`ForDerived`) и
переиспользование правил (`IncludeBase`) независимы; унаследованные члены
derived-пара и так маппит по конвенции, поэтому `IncludeBase` нужен только для
явных правил базы. Update передаёт совместимый существующий destination, а
несовместимый даёт понятное исключение. Вложенные вызовы тоже
диспетчеризуются. `UseBaseMapping` по умолчанию сохраняет работу
lazy-loading-прокси, которые являются runtime-подтипами сущностей.

### 10.1. Абстрактный базовый DTO с настройками по умолчанию даёт непонятную ошибку — Принято

Проверено генератором (2026-11-19):

| Base source | Base destination | `UnknownDerivedTypeHandling` | Результат |
|---|---|---|---|
| abstract `Vehicle` | abstract `VehicleDto` | по умолчанию (`UseBaseMapping`) | `MORPH0035` |
| abstract `Vehicle` | abstract `VehicleDto` | `Throw` | компилируется |
| конкретный `Animal` | abstract `AnimalDto` | `Throw` | `MORPH0035`: точный экземпляр `Animal` использует базовый маппинг |

Самый частый полиморфный сценарий — абстрактная иерархия DTO — при настройках
по умолчанию упирается в «cannot create a destination», а справка `MORPH0035`
предлагает `Construct`, фабрику или `Convert` и не упоминает
`UnknownDerivedTypeHandling.Throw`.

Предложение ревью: если у пары есть ссылки `ForDerived`, сообщение и справка
`MORPH0035` называют полиморфную причину и исправление —
`UnknownDerivedTypeHandling.Throw` при абстрактном base source или фабрику для
базового случая. Поведение не меняется.

**Решение.** Предложение ревью.

### 10.2. Неизвестный подтип молча маппится базовым маппингом — Принято при условии

Проверено запуском (2026-11-19): для
`Map<Shape, ShapeDto>().ForDerived<Circle, CircleDto>()` экземпляр `Square`
без ссылки маппится в `ShapeDto`, данные `Square` теряются. Новый подтип,
добавленный позже, тоже молча уйдёт в базовый маппинг.

Как поступают другие: AutoMapper при отсутствии подходящей derived-карты
использует базовую; Mapperly в сгенерированном `switch` для неизвестного типа
бросает `ArgumentException`.

`Throw` по умолчанию сломал бы lazy-loading-прокси: прокси базовой сущности —
неточный runtime-тип без ссылки.

Варианты:

- warning для пары со ссылками `ForDerived`, если в текущей компиляции есть
  неабстрактный тип, производный от base source, без ссылки. Исправление —
  `ForDerived`, `Throw` или подавление, если базовый маппинг намерен.
  Runtime-прокси и типы из других сборок не видны, поэтому ложных
  срабатываний на прокси нет. Требует индекса производных типов компиляции;
  делать при условии, что это дёшево для инкрементальности;
- оставить и описать в документации.

**Решение.** Первый вариант при условии приемлемой стоимости.

## 11. Настройки как система

Сильные стороны: один набор настроек на трёх уровнях (сборка, маппер,
маппинг) с одинаковыми именами методов; порядок приоритета описан на одной
странице, каждая настройка разрешается независимо; базовый маппер и
включённый маппинг участвуют только через явные `base.Configure` и
`IncludeBase`; неверное значение MSBuild-свойства — ошибка `MORPH0022`;
унаследованные значения по умолчанию не дают ошибок на маппингах, где
неприменимы.

### 11.1. Явная настройка без эффекта диагностируется непоследовательно — Принято

Явная настройка маппинга, которая не может на него повлиять, в одних случаях
— ошибка `MORPH0023` (null handling, конструкторы и члены рядом с `Convert`;
`ConstructorSelection` у скаляра или кортежа), а в других молча
игнорируется: `NullDestinationHandling` при выключенном Update,
`ConstructorSelection` при явно выбранном конструкторе. Граница между
«неприменимо» и «не используется» для пользователя неочевидна: в обоих
случаях написанное не действует.

Варианты:

- одно правило: явная настройка уровня маппинга, которая не может повлиять на
  этот маппинг, — `MORPH0023`; унаследованные значения не диагностируются;
- оставить разделение и объяснить его в справке `MORPH0023`.

**Решение.** Первый вариант: всегда указывать на явную настройку, которая не
действует.

### 11.2. Повторная настройка на одном уровне молча перекрывается — Принято

Если настройка записана на одном уровне дважды, побеждает последняя, без
диагностики. Повторные методы destination, `Members` или `Convert` при этом —
ошибка `MORPH0019`. В декларативном `Configure`, где порядок вызовов в
остальном не важен, повтор почти наверняка ошибка копирования.

**Решение.** Ошибка для повторной настройки на одном уровне, по аналогии с
`MORPH0019`.

### 11.3. `MappingMode` маппинга задаётся аргументом `Map` — Не проблема

Все настройки маппинга задаются цепочкой (`.NullSourceHandling(...)`), а
`MappingMode` — только аргументом `Map<TSource, TDestination>(mappingMode)`;
на уровне маппера это обычный метод `builder.MappingMode(...)`. Единственное
исключение из общего вида.

Варианты:

- метод цепочки `.MappingMode(...)`, как у остальных настроек, вместо аргумента
  `Map`;
- оставить: `Map<OrderDto, Order>(MappingMode.Create)` короче и сразу виден в
  объявлении пары.

Предложение ревью было — первый вариант. **Решение:** оставить аргумент: он
уместен. `MappingMode` описывает, какие операции поддерживает пара, и
естественно читается в её объявлении.

### 11.4. `Default` означает «наследовать» — Не проблема

Член `Default = 0` во всех перечислениях настроек означает «продолжить на
следующем уровне». Поднято в 8.3. Название можно прочитать как «поведение по
умолчанию», но оба прочтения совпадают по смыслу: это значение по умолчанию с
внешнего уровня, а без переопределений — значение Morphant.

## 12. Кортежи

Сильные стороны: кортежи — полноценные source и destination; объединяют
несколько входов и данные вызова, возвращают несколько результатов.
Конвенции используют семантические имена элементов и никогда не сопоставляют
по позиции; безымянные элементы требуют явных правил `ItemN`. Поддерживаются
длинные кортежи и `System.Tuple`. Update `ValueTuple` возвращает изменённое
значение, а потеря результата для значимого destination диагностируется
по 2.3. Решение 1.8 (одно представление CLR-пары на сборку) делает имена
элементов однозначными в пределах сборки.

### 12.1. Имена элементов на месте вызова молча расходятся с объявлением — Принято

Имена элементов стираются из CLR-идентичности, поэтому вызов с другими
именами находит ту же пару и сопоставляет значения по позиции, вопреки
семантике объявления. Проверено запуском (2026-11-19):

```csharp
builder.Map<(int Id, int Count), StockDto>();

ITypeMapper<(int Count, int Id), StockDto> mapper = new ProbeMapper();
var dto = mapper.Create((Count: 5, Id: 1));
// Id=5, Count=1
```

Ни C#, ни Morphant не предупреждают: преобразование кортежей, различающихся
только именами, — тождественное.

**Решение.** Warning анализатора (общая инфраструктура с 1.7 и 2.3),
если на месте вызова runtime API (`IMapper.Map`, `ITypeMapper`, расширения
`Create`/`Update`) или при преобразовании к `ITypeMapper` имена элементов
кортежа отличаются от представления пары, объявленного в текущей
компиляции. Безымянные элементы на месте вызова не диагностируются. Пары из
других сборок не проверяются. Учесть при проектировании расширений 2.1:
выведенный из переменных кортеж `(order, customer)` получает имена переменных.

## 13. Диагностика, исключения, отладка

### 13.1. Runtime-хелперы в сгенерированном коде — Принято

Поднято пользователем 2026-11-19: хелперы сокращают повторяющийся код, но
ухудшают открытость и понятность сгенерированного кода.

Сейчас хелпера два, оба в публичном классе
`Morphant.RuntimeSupport.MappingHelpers` с `[EditorBrowsable(Never)]`, и оба
входят в проверку совместимости генератора и runtime
(`RuntimeContractManifest`):

- `UpdateInPlace` (четыре перегрузки) — read-only вложенный член: проверка
  `null`, ленивый source через `Func`, при необходимости проверка типа и
  `context.Mapper.Map`;
- `UpdateDerived` — ветвь полиморфного Update: проверка совместимости
  destination, исключение и вызов пары ветви.

Сгенерированные вызовы и их встроенные эквиваленты (проверено генератором):

```csharp
// сейчас
MappingHelpers.UpdateInPlace(result.Address, source, static s => s.Address, context);

// встроенно
if (result.Address is { } address)
{
    _ = context.Mapper.Map<AddressDto, Address>(source.Address, address);
}
```

```csharp
// сейчас
result = MappingHelpers.UpdateDerived<Shape, ShapeDto, Circle, CircleDto>(
    polymorphicSource, destination, context);

// встроенно
if (destination is not (null or CircleDto))
{
    throw PolymorphicDestinationTypeMismatchException
        .CreateForUpdate<Shape, ShapeDto, Circle, CircleDto>(polymorphicSource, destination);
}

result = context.Mapper.Map(polymorphicSource, (CircleDto?)destination);
```

Оценка ревью:

- кода хелперы почти не экономят: вызов не короче встроенной версии, у
  `UpdateDerived` — четыре аргумента типа;
- логика (пропуск `null`, проверка типа, исключение) скрыта в библиотеке,
  отладчик уходит в Morphant, а ленивый source добавляет делегат;
- публичные хелперы — часть контракта генератора и runtime, они ограничивают
  развитие и совместимость версий;
- хелперы вызывают `context.Mapper.Map`, а по 1.1 и 2.2 собственные пары
  вызываются напрямую. Сгенерированный код может вызвать свои методы
  `__Update` прямо, хелперу для этого нужны дополнительные параметры;
- фабрики исключений (`CreateForUpdate`, `Create`) — полезный публичный API:
  сообщения остаются единообразными, а исключения и так часть наблюдаемого
  контракта.

Предложение ревью: встроить обе операции в сгенерированный код и удалить
`MappingHelpers`. Правило в `GENERATOR_CONTRACTS.md`: логика маппинга пишется
в сгенерированном коде; runtime-хелпер допустим, только если встроенный код
был бы существенно больше и хуже читался, а фабрики исключений допустимы
всегда. Заменить нынешний раздел контракта, который называет `UpdateInPlace` и
`UpdateDerived`.

**Решение.** Предложение ревью.

### 13.2. Имена сгенерированных методов нумеруются по порядку объявления — Принято при условии

Проверено генератором (2026-11-19): закрытые методы маппинга называются
`__Create`, `__Create1`, `__Create2` (и `__Update…`) в порядке объявления пар.
Добавление пары в середину `Configure` переименовывает все следующие методы:
шумный diff в `MorphantGitSnapshot` и при ревью. В стеке вызовов виден
`__Create2`; пару подсказывает только соседний кадр явной реализации
`ITypeMapper<CDto, C>.Create`. После 1.1 сгенерированный код будет вызывать эти
методы напрямую, и `result.Address = __Create5(source.Address)` не скажет
читателю, какая пара вызывается.

Предложение ревью: стабильные читаемые имена от пары, не зависящие от порядка
объявления, например перегрузки `__Create(CDto source)` по типу source с
уточнением именем destination при совпадении source. Закрепить правило в
разделе имён `GENERATOR_CONTRACTS.md`.

**Решение.** Делать, если удастся обеспечить уникальность без перегруженных
имён. Если имена станут хуже или ненадёжными, оставить нумерацию.

### 13.3. Отладка идёт по сгенерированному коду, а не по `Configure` — Не проблема

`#line`-директив нет. Исключение в пользовательском выражении показывает в
стеке строку сгенерированного файла, а не строку лямбды в `Configure`
(проверено запуском 2026-11-19); точка останова в лямбде `Configure` не
срабатывает, потому что `Configure` не выполняется. Сгенерированный код
читаем и доступен (IDE, `MorphantGitSnapshot`), поэтому отлаживать можно, но
пользователь ставит точку останова там, где писал код.

Варианты:

- сопоставлять перенесённые пользовательские выражения с исходными строками
  через `#line`: точки останова в лямбдах `Configure` срабатывают во время
  маппинга, стек указывает на код пользователя. В C# 10+ доступна форма
  `#line` со span-ами, в C# 9 — только по строкам. Нужно исследовать шаг
  отладчика на границе пользовательского и синтезированного кода;
- оставить отладку по сгенерированному коду и описать её в
  `docs/generated-code.md`.

Предложение ревью было — исследовать первый вариант прототипом. **Решение:**
не усложнять. Пользователь должен понимать, что `Configure` не выполняется
(см. 3.3); для отладки точка останова ставится в сгенерированном коде.

## 15. Дизайн enum-маппинга (не реализован)

Рассмотрен `ENUM_MAPPING_DESIGN.md` (обновлён 2026-11-17) на уровне
пользовательской модели; сценарии и исследования не пересматривались.

Сильные стороны: одна знакомая форма правил — `switch` в `Members` — вместо
отдельных `Values`/`MapValue`; минимум новых настроек, без настроек fallback,
overflow и ignore-case; математически точная числовая семантика без усечения;
сопоставление имён Ordinal, затем OrdinalIgnoreCase, как у параметров
конструктора; aliases обрабатываются группой без зависимости от порядка;
проверка покрытия входа по умолчанию; без reflection, `Enum.Parse` и boxing;
заранее проверенная реализуемость на минимальном Roslyn и C# 9.

### 15.1. `_ =>` в mapping switch означает «после конвенции», а не «всё остальное» — Не проблема

По дизайну `status switch { Cancelled => Deleted, _ => Unknown }` выполняет
специальные ветки, затем конвенцию, и только при её неуспехе — `_`. В C# та
же запись значит «всё, кроме `Cancelled`, — `Unknown`». Дизайн называет это
осознанным отличием от C#, но читатель кода по умолчанию применит C#-смысл: это
противоречит цели DSL, близкого к C#, без неочевидного поведения.

Варианты:

- оставить: краткая форма «особые случаи, конвенция, fallback» для
  string/integer-входов;
- C#-смысл `_`: значения без подходящей ветки и без `_` получают конвенцию
  (там C# бросил бы исключение, противоречия нет); `_ => Unknown` означает
  `Unknown` для всех остальных; «конвенция, иначе fallback» записывается явно —
  например `_ => Auto() ?? Unknown` или `Auto(orElse: Unknown)`. Форму записи
  нужно проверить на типизацию; дизайн сейчас отклоняет `Auto(fallback: ...)`.
  Пересматривает часть сценариев (IncludeBase, ByBit, fallback).

Первоначальное предложение ревью — второй вариант. `Auto(orElse: ...)` и
`Auto(fallback: ...)` отклонены как некрасивые.

**Исследование лаконичной формы (2026-11-19).** Проверено компиляцией копий
маркеров:

| Запись | Компилируется | Цена |
|---|---|---|
| `_ => Auto<Api>() ?? Api.Unknown` | да, с нынешним `AutoMarker<T>` (неявная конверсия из `T`), для enum- и string-входа | аргумент типа в каждом fallback |
| `_ => Auto() ?? Api.Unknown` | нет (`CS0019`); да, если у `AutoMarker` есть неявная конверсия из `Enum` (для string/integer destination — из них) | C# пропускает и fallback чужого enum: проверку типа берёт на себя генератор |
| `.Fallback(Api.Unknown)` на builder пары | да | новый метод API ради одного случая |

Форма с `??` читается как обычный C#: «результат конвенции, а если его нет —
`Unknown`». Модель:

- ветки `switch` действуют как в C#; значение без ветки и без `_` получает
  конвенцию (C# бросил бы исключение, противоречия нет);
- `_ => Unknown` — `Unknown` для всех остальных значений, без конвенции;
- `Auto()` — оставшийся конвейер: унаследованные специальные ветки, затем
  конвенция; `Auto() ?? X` — `X`, если конвейер результата не дал, голый
  `Auto()` при неуспехе бросает;
- в IncludeBase локальный `_ => X` перекрывает унаследованные ветки для
  неперечисленных значений, а `_ => Auto() ?? X` продолжает к ним.

Пересмотренное предложение ревью: `Auto() ?? X` с конверсией маркера и проверкой
типа fallback в генераторе. Если перенос проверки типа в генератор
неприемлем — оставить дизайн как есть; типизированная форма длиннее, чем
выигрыш.

**Решение.** Оставить дизайн. Форму `Auto() ?? X` пользователь не найдёт без
документации, и с ней `MemberSelection` перестаёт влиять на `switch` с `_`.
Текущая модель согласована с `Members` объектов: ветки `switch` — явные
правила, как записи initializer-а; неперечисленные значения следуют
`MemberSelection`, как неупомянутые члены; `_` получает то, что осталось.
`MemberSelection.Explicit` выключает конвенцию и даёт `switch` точный смысл C#.
Эту аналогию объяснить в руководстве по enum-маппингу одним каноническим
разделом.

### 15.2. ByBit по умолчанию: параметр `Members` для flags — это один бит — Не проблема

При `FlagsMappingMode.ByBit` (по умолчанию) лямбда `Members` выполняется для
каждого установленного бита, а её параметр — отдельный бит, не значение
source. `access switch { Read | Write => All }` в этом режиме не совпадает
никогда. По C#-чтению параметр — это значение source целиком.

Для object/tuple → enum и вычисленных входов дизайн уже использует другую
модель: правила видят целую маску, а конвенция сама переводит биты.

Варианты:

- оставить ByBit по умолчанию;
- одна модель для всех входов: `Members` видит значение целиком, конвенция для
  несовпавшего значения переводит его биты; правила для каждого бита — явный
  режим `ByBit`. Повторного прохода пользовательских правил нет, как и сейчас
  для object/tuple → enum.

Первоначальное предложение ревью — второй вариант: правила видят значение
целиком, конвенция переводит биты несовпавшего значения, правила для каждого
бита — явный `ByBit`. Это не «всегда ByMask»: ByMask-конвенция сопоставляет
только целые объявленные имена.

**Исследование (2026-11-19).**

- AutoMapper (`EnumToEnumMapper`): `source.ToString()` и
  `Enum.TryParse(..., ignoreCase: true)`, иначе приведение по значению. Для
  flags `ToString()` даёт `"Read, Write"`, поэтому комбинация фактически
  маппится по имени каждого флага;
- Mapperly по умолчанию маппит по значению; поведение flags при ByName и
  `MapEnumValue` для комбинаций в документации не описано; поддержка flags
  упоминается для `ByValueCheckDefined`;
- пользовательских issue на эту тему не найдено.

Пользователь ожидает, что комбинация маппится по каждому флагу, а
переименование флага (`Admin => Administrator`) действует, когда флаг входит в
комбинацию. В модели «значение целиком» такое правило совпадает только с
точным `Admin`, и самая частая настройка flags потребовала бы явного `ByBit`.

Пересмотренное предложение ревью: оставить ByBit по умолчанию. Сделать
семантику видимой: сгенерированное IntelliSense-описание `Members` для
flags-пары говорит, что правила применяются к каждому установленному флагу, а
документация называет параметр `flag`. Окончательно — в итерации flags (15.5).

**Решение.** Пересмотренное предложение ревью: ByBit по умолчанию, семантика
видна в IntelliSense и документации.

### 15.3. Две настройки проверки покрытия с почти одинаковыми именами — Не проблема

`UnmappedMemberValidation` (члены объектов, после 6.2 — `Destination` по
умолчанию) и `UnmappedEnumMemberValidation` (значения enum, `Source` по
умолчанию, своя цепочка) различаются одним словом, хотя проверяют разное:
члены типа и значения enum.

Предложение ревью было — имя вроде `EnumValueValidation`. **Решение:**
оставить текущие имена: функции похожи, поэтому похожи и названия; разные
значения по умолчанию соответствуют разным настройкам.

### 15.4. Согласовать дизайн с решениями ревью — Принято

Дизайн написан до ревью и должен учесть: `ReturnDestination` по умолчанию
(8.1); `Destination` по умолчанию для `UnmappedMemberValidation` (6.2);
предупреждение о совпавшем по имени, но несмапленном члене (6.1) — для
enum-свойств разных типов оно подскажет `Map()`; прямые вызовы собственных пар
(1.1, 2.2); встроенный код вместо хелперов (13.1); конвенции через объявленные
пары (6.3) — тогда enum-пары смогут применяться к членам автоматически.

**Решение.** Обновить `ENUM_MAPPING_DESIGN.md` перед реализацией.

### 15.5. Объём первой версии — Принято

Дизайн и каталог сценариев занимают более 5 000 строк; основная сложность —
flags: побитовые правила, строковая токенизация, составные вычисленные входы.

**Решение.** Выпускать поэтапно: сначала enum без `Flags` (enum ↔ enum,
string, integer; правила, конвенция, покрытие), затем flags отдельной
итерацией. Пользователи
раньше получают основную ценность, а сложная часть проверяется отдельно.

## 16. Целостность и итог

### 16.1. Общая оценка

Сильные стороны дизайна в целом: типизированная конфигурация на C# с
IntelliSense и проверкой компилятором; строгие и предсказуемые конвенции;
явные механизмы вложенного маппинга, полиморфизма и переиспользования;
отдельные Create и Update с возможностью замены; открытый и читаемый
сгенерированный код; подробные диагностики со справкой; отсутствие runtime
reflection.

Повторяющиеся темы найденных проблем:

- **Молчаливое поведение** — самая частая тема: пустой маппинг при совпавших
  именах (6.1), потеря данных вложенного Create (7.2), `null` в non-nullable
  члене (8.2), шаблоны базы и скрытие пар (9.1, 9.2), неизвестный подтип
  (10.2), настройки без эффекта и повторы (11.1, 11.2), имена кортежей (12.1),
  отброшенный результат Update (2.3), забытый атрибут (1.4). Общее правило для
  будущих функций: если генератор знает, что написанное не подействует или
  результат расходится с очевидным чтением кода, он сообщает об этом.
- **Сложность ради редкого сценария** — CRTP (1.8).
- **Связь с DI** — вложенные вызовы (1.1, 2.2); регистрация отложена (1.2–1.6).
- **Границы близости к C#** — обёртки и типы конструирования (3.1, 3.2),
  read-only члены (7.3), enum `switch` (15.1). Отличия от C# допустимы, если
  они согласованы с моделью DSL и управляются понятной настройкой.

Предложение ревью — порядок реализации:

1. 1.8: удаление CRTP — самое большое изменение API, от него зависят
   поверхности и диагностики.
2. 1.1 и 2.2 вместе с 17.3, 13.1 и 13.2: прямые вызовы, производный контекст,
   встроенный код и имена методов меняют один и тот же сгенерированный код.
3. Семантика и диагностики генератора: 5.1, 6.1 (с учётом 17.5), 6.2, 7.2,
   7.3, 8.1, 8.2, 9.1, 9.2, 10.1, 10.2, 11.1, 11.2, 1.4.
4. Сборка анализаторов: 1.7, 2.3, 12.1.
5. Документация, changelog и инструкция миграции; политика и проверка
   совместимости 17.2 — до выпуска ломающих изменений.

Затем — возможности по плану: коллекции вместе с 6.3, enum без flags, flags.

**Решение.** Порядок пересмотрен с учётом второго прохода и вынесен в
[план реализации](DESIGN_REVIEW_IMPLEMENTATION.md), где отмечается
выполненное. Порядок выше — исходное предложение; действует план.

## 17. Второй проход

Проведён 2026-11-19 по просьбе пользователя перед реализацией: поиск
незатронутых областей и противоречий между принятыми решениями.

Дополнительная сильная сторона: правила `Members` и `Construct` могут
использовать члены маппера, в том числе зависимости из конструктора, поэтому
сервисы приложения доступны в правилах без отдельного механизма.

### 17.1. Большую конфигурацию нельзя разбить на части — Отложено

Проверено генератором (2026-11-19): вызов `ConfigureOrders(builder)` из
`Configure` — `MORPH0017`. Маппер со множеством пар — один длинный
`Configure`; другие способы — несколько мапперов, связанных через DI
(регистрация отложена, 1.2), или наследование, где пары абстрактной базы —
только шаблоны (9.1). У AutoMapper есть профили, у Mapperly — методы в любых
partial-частях.

Варианты:

- разрешить закрытые методы того же маппера, которые получают builder и
  безусловно вызываются из `Configure` или друг из друга, в том числе из других
  partial-файлов. Генератор обходит их так же, как `base.Configure`, с теми же
  правилами анализа; анализатор 1.7 и quick start (3.3) учитывают такие методы;
- оставить: части — отдельные мапперы.

Предложение ревью: первый вариант. **Решение:** полезно, но не приоритетно;
отложено на будущее.

### 17.2. Нет политики двоичной совместимости скомпилированных библиотек — Принято

Сгенерированный код зависит от runtime Morphant, а приложение может получать
его транзитивно. NuGet выбирает версию для приложения с учётом прямых и
транзитивных зависимостей. После обновления Morphant старая библиотека может
получить новый runtime. Обращение к удалённому типу или методу (1.8, 13.1,
изменения контекста для 1.1 и 2.2) может привести к `TypeLoadException`
или `MissingMethodException`. `MORPH0004` проверяет генератор и runtime
самого проекта.

**Решение (2026-11-19).** До 1.0 библиотеки и приложение используют одну
minor-линию Morphant. Начиная с 1.0 major должен совпадать, а minor библиотеки
может быть равен minor runtime или быть ниже. Patch-релизы внутри линии
совместимы. Публичную поверхность runtime, от которой зависит сгенерированный
код, следует держать минимальной (13.1).

`AssemblyVersion` выводится из `Version` как `major.minor.0.0`. Каждая
minor-версия с 0.1 по 0.5 уже имела свой номер и тот же ключ строгого имени.
Поэтому версия в ссылке на runtime позволяет проверить и выпущенные библиотеки
без дополнительного атрибута, в том числе библиотеки без мапперов.

В проекте с прямой ссылкой на пакет генератор выдаёт по одной ошибке
`MORPH0063` без привязки к строке на каждую несовместимую библиотеку.
Генерация мапперов проекта продолжается. Если библиотеке нужен более новый
runtime, компилятор также может выдать `CS1705`. При переходе на более новый
runtime SDK обычно подавляет предупреждения `CS1701` и `CS1702`.
Для `MORPH0004` сохраняется отдельная ревизия `Morphant.GeneratorContractVersion`.
На этапе удаления CRTP её нужно поднять до 3.

**Граница проверки (2026-11-20).** `MORPH0063` требует прямой ссылки на
Morphant в метаданных DLL, переданной компилятору. Для проекта, переданного
через `CompilationReference`, проверка откладывается. Roslyn может считать
сборку использованной из-за `nameof`, встроенной константы или транзитивной
зависимости, хотя в итоговой DLL ссылки на неё нет.

Для `ProjectReference` SDK обычно передаёт reference assembly. Зависимость
только в теле метода может быть видна лишь в DLL реализации. Проверка таких
DLL через MSBuild отложена вместе с проверкой транзитивных потребителей.

Решения по политике:

- с первого patch после 0.6.0 задавать `PackageValidationBaselineVersion`
  предыдущим выпуском той же линии: `MORPH0063` не видит поломку внутри линии
  с одинаковой `AssemblyVersion`;
- открытый вопрос к 1.0: подписанная сборка с `AssemblyVersion`, меняющейся с
  каждой minor, на .NET Framework может требовать `bindingRedirect`; фиксация
  версии на major лишит `MORPH0063` информации о minor.

### 17.3. Прямым вызовам нужен runtime API контекста — Принято

Конструктор `MappingContext` внутренний. Для прямого вложенного вызова (1.1)
сгенерированный код должен передать контекст с операцией вложенного вызова:
`Operation` определяется вызовом, и вложенный Create внутри Update должен
видеть Create. Для 2.2 контекст должен знать текущий маппер, чтобы
`context.Mapper` выполнял его пары напрямую. Сейчас это невозможно без
изменения runtime.

Предложение ревью: спроектировать минимальный публичный API — производный
контекст для вложенной операции и текущий маппер — в шаге 2 порядка
реализации (16.3). Это допустимая runtime-поверхность по правилу 13.1 и часть
контракта 17.2; аллокации на вложенный вызов не добавлять.

**Обсуждение (2026-11-19).** Пользователь не должен управлять контекстом:
прямые вызовы `ITypeMapper` в пользовательском коде не предполагаются, для
них есть расширения `Create`/`Update`, которые создают контекст сами.
Уточнение ревью: API нужен не пользователю, а сгенерированному коду. Он лежит
в сборке пользователя, поэтому `internal`-конструктор ему недоступен. API
скрывается из IntelliSense (`[EditorBrowsable(Never)]`), как сейчас
`MappingHelpers`, документируется как поддержка сгенерированного кода, а
пользовательская модель не меняется: контекст по-прежнему создаёт Morphant.

Требование пользователя: все вложенные операции одного вызова работают в одном
и том же `MappingScope`, а операция контекста указывается правильно.

Сейчас контекст создаётся только на входе в scope: в `MappingScope` и в
расширениях `Create`/`Update`. Каждый вложенный вызов идёт через
`context.Mapper`, то есть через тот же scope, который создаёт новый контекст с
операцией вызова. Прямой вызов (1.1) этот путь обходит, поэтому контекст должен
порождаться из входящего.

Предложение ревью:

- скрытый метод экземпляра `MappingContext`, условно
  `ForOperation(MappingOperation operation)`, возвращает копию с тем же scope и
  указанной операцией. Контекст можно только породить из существующего, но не
  создать заново, поэтому scope гарантированно тот же; default-контекст, как и
  сейчас, даёт `InvalidMappingContextException`. Копия структуры — без
  аллокаций;
- для 2.2 порождённый контекст несёт и текущий маппер. `context.Mapper`
  возвращает представление scope для этого маппера: его пары выполняются
  напрямую, остальные — через тот же scope. Представление создаётся не больше
  одного раза на маппер за scope, повторные обращения не аллоцируют;
- новые scope по-прежнему создаются только на входе: `IMapper.Map` и
  расширения `Create`/`Update`;
- операция: вложенный Create — `Create`, вложенный Update — `Update`, в том
  числе с `null` destination, как в текущем контракте; адаптивный `Map()`
  выбирает операцию по 7.2;
- член помечен `[EditorBrowsable(Never)]`, описан как поддержка
  сгенерированного кода и входит в контракт двоичной совместимости (17.2).

**Решение.** Предложение ревью; точное имя и форма — при реализации.

### 17.4. Enum-дизайн расходится с 11.1 и 11.2 — Принято

`ENUM_MAPPING_DESIGN.md` оставляет совместимую, но неактивную явную настройку
без диагностики («при Explicit совместимая настройка остаётся неактивной»;
стратегия рядом с `Using` без `Members`) и говорит, что последняя запись уровня
побеждает. Решения 11.1 и 11.2 требуют указывать на явную настройку без
эффекта и считать повтор на уровне ошибкой.

**Решение.** Привести всё к одному правилу: 11.1 и 11.2 входят в список
согласования 15.4.

### 17.5. 6.1 и 6.2 при `MemberSelection.Explicit` — Принято

- Предупреждение 6.1 говорит, что конвенция не может использовать совпавший
  по имени член. При `Explicit` конвенция для неупомянутых членов не
  применяется вовсе, поэтому предупреждение не имеет смысла.
- Проверка `Destination` по умолчанию (6.2) при `Explicit` сообщит о каждом
  неупомянутом члене.

Варианты для 6.2:

- сообщать: проверка смотрит на итоговый маппинг независимо от того, как член
  оказался пропущенным; при `Explicit` это список того, что не задано явно.
  Кому это не нужно, отключает проверку на том же уровне, где выбран
  `Explicit`;
- считать неупомянутые члены при `Explicit` намеренно пропущенными. Тогда
  значение по умолчанию работает иначе, чем то же значение, заданное явно, —
  скрытое правило.

Предложение ревью: 6.1 выдавать только там, где применяется конвенция; для 6.2
— первый вариант, отметить взаимодействие в документации настройки.

**Решение.** Предложение ревью.

### 17.6. Generic-мапперы не описаны в руководствах — Принято

`Map<Envelope<T>, Destination>()` в generic-маппере поддерживается, но
упоминается только в справке `MORPH0012` и `MORPH0014`. Как объявить
generic-маппер и зарегистрировать закрытые варианты в DI, руководства не
говорят. Основные generic-обёртки (`Page<T>`) упираются в коллекции.

**Решение.** Описать generic-мапперы в руководстве вместе с итерацией
коллекций; не забыть добавить в документацию.

### 17.7. Три значения слова `Map` — Не проблема

`builder.Map<S, D>()` регистрирует пару, `Map()` в правилах — вложенный
маппинг, `IMapper.Map` — вызов во время выполнения. Справка `Map` прямо
говорит, что это разные вещи, а контексты не пересекаются: builder, лямбда
правил и код приложения.
