# Template type development handoff

This document records the current design and testing decisions for Morphant's
generated template types. It is intended to let a new Work/Codex session
continue without reconstructing the project history from chat.

- Repository: `strangeman375/Morphant`
- Branch: `main`
- Last checkpoint commit before this document:
  `bdb16ef1a74a4ce50912063b47610b86d9ad5646`
  (`Complete template destination support coverage`)
- Baseline verification at that checkpoint: 139 of 139 tests passed.
- The next implementation task is to revise destination-type support:
  built-in C# types must stop producing template surface, while constructed
  generic destination types must become supported.

The current code still reflects the previous behavior: it generates templates
for `int` and `object`, and it rejects generic destinations. Corresponding tests
also encode that old behavior. Change those tests as part of the next task;
do not treat them as the desired contract.

## Relevant pipeline

Template type discovery currently flows through:

1. `MorphantGenerator`
2. `CompilationContextPipeline`
3. `TypeMapperConfigurePipeline`
4. `TemplateDestinationTypePipeline`
5. `TemplateTypePipeline`
6. `TemplateTypeModelBuilder`
7. `TemplateTypeEmitter`

User mappers are marked with `[MorphantMapper]`. Mapper discovery uses
`ForAttributeWithMetadataName`; do not replace it with a compilation-wide
syntax or symbol scan.

Template type tests use
`src/tests/Morphant.Generator.UnitTests/TestUtils/TestTemplateTypeGenerator.cs`.
That test generator intentionally registers only template type generation, not
template extension generation.

## Settled template surface design

- Generated template types are internal sealed records. A record is required
  because `with` expressions are part of the public mapping DSL.
- Template members are properties. Their bodies are:

  ```csharp
  get => null!;
  set { }
  ```

- Constructor-members helpers are classes with fields initialized to `null!`.
  Keep them as fields unless a concrete DSL requirement justifies changing
  them.
- The template exposes convention, factory, and supported destination
  constructors. Abstract classes and interfaces still get convention/factory
  surface so map-to-existing member configuration remains possible.
- Record infrastructure is intentionally minimized with explicit `Equals`,
  `GetHashCode`, `ToString`, and `PrintMembers` implementations. Do not add
  `EditorBrowsable(Never)` to these members without a demonstrated benefit.
- `// <auto-generated />` is used. `[CompilerGenerated]` is not added to every
  generated declaration.
- Generated output is deterministic: four-space indentation, CRLF line
  endings, and a trailing newline.
- Every generated file enables nullable annotations with `#nullable enable`.
  This is deliberate even when the consuming project has different nullable
  settings, because generated-code nullability errors should remain visible in
  tests.
- Preserve nullable annotations, including oblivious state where applicable.
- XML documentation uses `inheritdoc` when source documentation exists and a
  useful generated summary otherwise. Constructor and constructor-member
  documentation describes the DSL behavior. Destination default parameter
  values are documented even though wrapper parameters use `null` to mean
  "use the destination default".
- Copy `ObsoleteAttribute` from destination members. Other attributes are not
  copied unless a future user scenario requires them.
- Inherited members are emitted base-first and in declaration order. Ambiguous
  members inherited from unrelated interfaces are skipped.
- Unsupported member forms such as ref-like, pointer, function-pointer, and
  error types are skipped for now. Diagnostics will be designed later.

## Compatibility decisions

- Minimum consuming-project language version: C# 9.
- The generator itself may be built with a newer language version.
- Newer destination syntax can be tested explicitly, for example record
  structs with C# 10 and file-local types with C# 11.
- Generated source must remain valid C# 9 unless a feature fundamentally
  requires a newer consuming language version and that policy is explicitly
  changed.

## Test organization and philosophy

Completed template-type categories currently cover:

- shape;
- destination constructors and constructor-members helpers;
- properties, fields, inheritance, accessibility, nullability, and attributes;
- XML documentation;
- naming, nested scopes, identity, hint-name collisions, and deterministic
  64-bit hint hashes;
- destination-type support.

Constructor, member, documentation, and naming tests have their own folders
under `TemplateTypeTests`. The destination support category currently lives in
`TemplateTypeDestinationSupportTests.cs` and contains 39 cases.

Each category is an independent behavioral specification. In particular:

- do not rely on constructor tests to prove that a destination kind is
  supported;
- do not rely on member tests to make documentation tests shorter;
- include complete expected generated output where it makes the behavior
  easier to understand;
- overlap is preferred over an implicit dependency between categories;
- evaluate missing cases from a user's perspective rather than by chasing code
  coverage.

Expected-source helpers may remove mechanical boilerplate, but they must not
hide the behavior the category is meant to document.

## Next task: built-in destination types

Template surface is not useful for C# built-in scalar/reference types such as
`int`, `string`, and `object`. Mapping support for such types is a separate
concern; only template type and template extension generation are suppressed.

The next change should invert the existing positive `int` and `object` tests
and add a complete built-in-type matrix. At minimum consider C# predefined
types with keywords:

- `object` and `string`;
- `bool` and `char`;
- signed and unsigned integral types;
- `nint` and `nuint`;
- `float`, `double`, and `decimal`.

Do not blindly broaden this decision to every framework scalar. `Guid`,
`DateTime`, `DateOnly`, `TimeOnly`, `Uri`, and similar types need an explicit
separate policy. Note that a broad `SpecialType != None` check may cover more
Roslyn special types than the intended C# keyword set, so make the boundary
visible in code and tests.

## Next task: generic destination types

Constructed generic destination types should be supported. Examples include:

```csharp
Envelope<User>
Result<Order>
Container<int>.Destination
```

The preferred design is one generic template per generic original definition,
not one specialized template per closed construction:

```csharp
internal sealed record EnvelopeMorphantTemplate<T>
{
    public global::Morphant.Members.Member<T> Value
    {
        get => null!;
        set { }
    }
}
```

For `Envelope<User>`, generated template extensions should refer to
`EnvelopeMorphantTemplate<User>`. `Envelope<Order>` should reuse the same
generic template definition.

This direction keeps generated code small, produces readable names, and gives
incremental caching a stable definition-level key. It requires the following
architectural split:

- template type definitions are deduplicated by `OriginalDefinition`;
- template extension usages are deduplicated by the constructed destination
  identity, including type arguments;
- `TemplateDestinationTypeInfo` or its replacement must distinguish definition
  data from constructed usage data;
- template and constructor-members models/emission must carry type parameters;
- all required generic constraints must be reproduced so references such as
  `Envelope<T>` compile;
- nested generic containing types must contribute their type parameters and
  constraints;
- nullable type arguments and fully qualified constructed names must be
  preserved;
- hint names must remain deterministic and collision-safe.

Support generic classes, records, structs, abstract classes, and interfaces as
destination definitions. Add a case where multiple constructed destinations
reuse one template definition.

A bare destination type parameter such as `TDestination` remains unsupported
because its members and constructors are unknown. An open constructed
destination such as `Envelope<T>` inside a generic mapper is a separate
follow-up: design the representation so it can be added later, but do not
silently claim support until its generic extension method and constraint
behavior have dedicated tests.

## Destination support boundaries already established

- Public and internal top-level destination types are accessible.
- Accessible nested types are supported, including the internal side of
  `protected internal`.
- Private, protected, and private-protected nested destinations are skipped
  when generated top-level code cannot name them.
- A destination inside an inaccessible containing type is skipped.
- File-local destinations and destinations nested in file-local containing
  types are skipped. The latter case previously exposed a generator bug; the
  full containing-type chain must be checked.
- Arrays, tuples, enums, delegates, nullable value-type destinations, dynamic,
  and a bare type parameter currently do not produce template types.
- Ref structs, pointers, function pointers, `void`, anonymous types, and static
  classes cannot be valid destination generic arguments for the current
  `MapperBuilder.Map<TSource, TDestination>` API; do not add tests whose only
  behavior is a compiler error unless diagnostics are explicitly in scope.

## Deferred work

- Generator diagnostics are a separate project phase. Do not introduce an
  incomplete diagnostic policy while extending template surface.
- After destination support is settled, the next planned template-type
  category is generated-code actualization when `Configure` or the destination
  model changes.
- Incremental pipeline caching/tracking tests follow actualization tests.
- Broader attribute propagation and scalar/framework-type policy remain
  demand-driven.

## Verification in a fresh Work environment

The normal command is:

```shell
dotnet test src/tests/Morphant.Generator.UnitTests/Morphant.Generator.UnitTests.csproj
```

The previous Work sandbox did not have `dotnet` on `PATH`; a .NET SDK was
downloaded into `/tmp/dotnet`, and MSBuild needed single-node execution:

```shell
DOTNET_CLI_HOME=/tmp/morphant-dotnet-home \
NUGET_PACKAGES=/tmp/morphant-nuget-packages \
DOTNET_SKIP_FIRST_TIME_EXPERIENCE=1 \
/tmp/dotnet/dotnet test \
  src/tests/Morphant.Generator.UnitTests/Morphant.Generator.UnitTests.csproj \
  --no-restore -m:1 -nr:false
```

`/tmp` is not durable across Work sessions. A fresh environment may need the
SDK and packages restored again. Run a focused fixture while iterating and the
full project immediately before committing.
